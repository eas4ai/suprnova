## In

Iteration 005 performs the atomic move from the dedicated development
repository into the Suprnova workspace and implements the complete RenderCache
foundation assigned to this iteration by Iteration 004. The move includes the
engine, browser runtime, generated artifacts, fixtures, tests, benchmarks,
implementation documentation, normative specification set, and structural
checker. After the cutover commit, `suprnova/crates/suprnova-live/` is the sole
maintained product and specification authority; the standalone repository is
historical development evidence and receives no parallel product changes.

The imported engine remains an internal crate. Applications consume Live and
RenderCache only through documented `suprnova::live`, `suprnova::view`, route,
configuration, macro, CLI, and testing surfaces. The internal engine does not
depend on the public framework crate, and generated application code never
names `suprnova_live` or another internal package.

The committed standalone implementation baseline is commit `59395ec`, the
final standalone `main`. Its history entered the workspace as the subtree
import of commit `6d19d02` followed by a subtree merge of the later standalone
commits. Uncommitted standalone files, ignored dependencies, local references,
optional handoff archives, and captured future-iteration notes are not
migration input. The import preserves committed history under
`crates/suprnova-live/` rather than flattening the project into an untraceable
copy.

### Render representations, variance, and storage

- Implement route and route-group RenderCache policy with deterministic
  inheritance, explicit eligibility, concrete-response safety checks, bypass,
  stale behavior, storage selection, and observability. Live works unchanged
  when RenderCache is disabled, unavailable, or bypassed.
- Implement bounded versioned Complete and Composite entry codecs. Complete
  entries hold immutable final response bytes and replayable safe metadata;
  Composite entries hold an integrity-protected typed segment graph and stitch
  slots whose final bytes, headers, CSP data, content length, and validator are
  computed only after current-request assembly.
- Implement canonical bounded lookup identities from trusted route, normalized
  parameters and query, negotiated representation, application and view build,
  and declared variance. Raw secrets, arbitrary cookies, unstable process IDs,
  and unbounded attacker-controlled dimensions never become keys or diagnostics.
- Implement public shared, public shell with private stitched segments, private
  cached, and uncacheable classification with automatic safety downgrades from
  observed identity, session, authorization, tenant, feature, configuration,
  locale, and request context.
- Implement opaque revocable private key dimensions and bounded retention.
  Anonymous and authenticated output, tenants, principals, permission versions,
  sessions, and private application contexts cannot collide or leak through
  bodies, metadata, keys, logs, metrics, or inspection output.
- Implement typed deterministic server stitching with bounded acyclic segment
  ownership, current authorization, request-specific metadata, duplicate DOM or
  island identity detection, and explicit fail-document, safe-fallback, or omit
  slot outcomes. Private content is never injected by the browser to complete
  initial rendering.
- Implement immutable in-process L0 plus atomic file-backed and database-backed
  L1 stores. Add one conforming externally accelerated Redis-backed profile by
  reusing Suprnova's established Redis facilities behind the RenderStore,
  instance-ledger, and rebuild-coordinator contracts. Provider selection does
  not route RenderCache bytes through the generic application value cache.
- Implement strong or weak represented-byte validators, conditional 304
  handling, safe header replay, content-encoding separation, private defaults
  for shared caches, and explicit bounded `s-maxage` or supported purge policy.
  Composite structural validators are never replayed as final HTTP validators.

### Dependency generations and coherent rebuilding

- Wrap the entire opted-in cacheable handler and rendering pipeline in one
  request-scoped async-safe dependency collector. Framework-owned route,
  locale, feature, configuration, identity, session, ORM, model, relation, and
  query reads register typed observations automatically; explicit custom APIs
  cover external authorities.
- Implement versioned typed dependency identities and durable logically append-
  only generation truth for SQLite, PostgreSQL, and MySQL or MariaDB. The
  application database remains generation authority at every deployment tier;
  memory, files, Redis, hints, and cached bodies cannot prove currentness.
- Integrate create, update, delete, restore, relationship, bulk, and supported
  raw-write paths so generation advancement commits atomically with owned data
  transactions and disappears on rollback. Unknown or insufficiently observable
  reads and writes collapse to broader safe generations or bypass caching.
- Associate rebuild data and generations inside one declared consistent read
  view, close that view after all lazy and template reads complete, then perform
  a fresh current-authority reread before publication. A mismatch discards the
  complete candidate and enters bounded retry, stale, or bypass policy.
- Implement Embedded, Database-coordinated, and Externally accelerated
  deployment profiles over independent RenderStore, LiveInstanceLedger,
  RebuildCoordinator, and GenerationLedger contracts. Tier 0 is the behavioral
  reference and requires no daemon; Tier 1 uses the shared database; Tier 2 uses
  Redis as acceleration while the database remains generation authority.
- Implement bounded validation leases and optional hints. Hints MAY invalidate
  local proof early but never extend validity. Restart, hint loss, accelerator
  eviction, or partition cannot make stale content appear current.
- Implement in-process and distributed singleflight with expiry, cancellation,
  bounded waiters, database-time or provider-time leases, monotonic fencing, and
  atomic publication. The contract guarantees one accepted publication per key
  and coherence fence, not universally one computation during failure.
- Implement explicit fresh, stale-servable, stale-on-error, and dead intervals,
  honest HTTP age and warning metadata, bounded background rebuild, failure
  backoff, negative-cache separation, and privacy-sensitive stale prohibitions.
- Namespace entry and generation formats by application/view build and authority
  epoch so rolling deployments cannot overwrite or reuse incompatible data.
  Provide an emergency epoch advance and bounded cleanup of unreachable entries.

## Out

Out means sequenced build order, not removal from the agreed system.

- Specs 20 through 25 remain the official component-library iteration. This
  iteration MAY scaffold and dogfood unstyled semantic Live views but does not
  implement the Tailwind component catalog, theme tokens, visual catalog, or
  theming studio.
- The captured document work arbiter, multi-island refresh batching, and
  alternative browser enhancement substrate ideas remain unconfirmed material
  under `iterations/next/`. They do not enter the integrated runtime through the
  repository move.
- Alpine, Lit, HTMX, a Stimulus fork, or another browser substrate does not
  replace the currently specified optional Stimulus integration in this
  version. That is a next-version architecture decision, not an Iteration 005
  implementation shortcut.
- No SPA or Turbo-style navigation, Inertia mixing, virtual DOM, browser-rendered
  private shell, streamed trusted HTML, generic RPC protocol, or synthesized
  no-JavaScript action path is introduced.
- No application imports the internal engine crate, macro development crate,
  Askama parser, Redis client, SeaORM internals, or browser implementation
  modules merely to use Live or RenderCache.
- No file in `/home/shawn/workspace2/suprnova-magnetar` is modified. Magnetar
  remains a separate subsystem consumed only through existing Suprnova
  integration boundaries.
- The standalone `suprnova-live` repository is not deleted, rewritten, or used
  as a second maintained branch after cutover. Archiving or removing that
  historical checkout is a separate repository-administration decision.
- Dedicated-environment benchmark qualification is release-checklist work. The
  `U4/16`, `E100/1K`, and `R100` workloads gain qualified S1 and B1 evidence
  only when a dedicated runner supplies it before a release or public
  performance claim; until then the checked baselines keep `qualifiedBaseline`
  null and the release evaluator continues to fail closed.

## Definition of done

1. The Suprnova integration branch starts from the clean released `main`

   imported beneath `crates/suprnova-live/` with traceable ancestry. Protected
   uncommitted and ignored standalone files are absent from the import.

   artifacts, fixtures, tests, benchmarks, implementation documentation, and
   gate logic have one maintained authority under `crates/suprnova-live/`.
   Repository instructions and every checked relative path identify that
   authority; the standalone repository is historical only.
3. Suprnova's root workspace builds the engine and every retained supporting
   crate under workspace edition, MSRV, license, and release policy without a
   nested-workspace conflict, dependency cycle, crates.io publication path, or
   application-facing internal crate dependency.
4. `suprnova::live`, `suprnova::view`, and their required crate-root re-exports

   is limited to `suprnova::live::__private`; application code and generated
   examples name no internal package.
5. Production Live macros live in `suprnova-macros`, retain their standalone UI
   diagnostics and conformance fixtures, and expand successfully in both the
   framework integration tests and a freshly scaffolded application.
6. Real Suprnova routes render canonical Askama-backed documents, mount public
   seeds or identity-bound instances safely, and adapt every Live action,
   fresh-render, upload, SSE, and WebSocket request through current middleware,
   session, CSRF, origin, tenant, authorization, rate, transaction, cancellation,

   cross-session, cross-tenant, cross-origin, unauthorized, duplicate, and
   retired requests fail before protected engine or application work. Adapter
