# RenderCache 世代

大多数缓存靠过期。RenderCache 也会过期，但过期是兜底，而不是机制。机制是
**世代**：一次渲染读过的每一份数据在数据库里都有一个计数器，渲染会把它见到的
那些计数器存下来，而一次写入会推进它所改动的东西的计数器。当一份已存储的表示
见过的那些计数器，仍然与数据库现在持有的计数器相符时，它就是最新的。你不必为
自己的数据写任何失效规则，因为一次普通的 `model.save()` 本身就已经是一条了。

本章从外部讲这套机制：一次渲染被记录为依赖了什么、那些依赖实际上有多粗、框架
看不见因而无法失效的是什么、一致性检查在一次命中上是怎么付账的、当好几个请求
同时想要同一个条目时由哪一个来重建，以及在“不再是最新的”与“已重建”之间的那个
窗口里访客被提供什么。下面每一个论断都由一个具名测试或一份签入的测量结果压住；
自用（dogfood）示例是 `app/src/live/mod.rs` 里的路由，由
`app/tests/live_render_cache.rs` 证明。

## 一次渲染被记录为依赖了什么

在一次渲染运行期间，一个请求范围的收集器会记录下它能指名的每一项依赖：一次表
读取、一次按主键的记录读取、一个查询类别、一个关系、一个配置标识、一个功能、
一个语言环境、一个路由，以及一个每份表示都会观察到的、始终存在的 `Broad` 标识。
通过 ORM 和查询构造器进行的读取会自己记录自己；你什么都不用写。

`/live/todos` 把整个模式浓缩在一个处理程序里：

```rust
pub async fn todos(_request: Request) -> Response {
    let result: Result<HttpResponse, FrameworkError> = async {
        let titles: Vec<String> = Todo::all()
            .await?
            .into_vec()
            .into_iter()
            .map(|todo| todo.title)
            .collect();
        html(&TodosView { count: titles.len(), titles })
    }
    .await;
    result.map_err(failed)
}
```

`Todo::all()` 记录下 `todos` 表。这个处理程序和这个模板里再没有别的东西读取
会话、已登录访客或某条翻译，而这正是这个路由能够一直保持为一份共享表示的原因。

## 一次普通的写入就是那次失效

`an_orm_write_invalidates_the_todos_document_through_generations` 通过运行中的
应用走完了整个循环：

1. 第一个 `GET /live/todos` 渲染并发布。
2. 第二个是一次命中：它从不到达处理程序，不携带 `Warning`，也不调度任何东西。
3. 一个 `POST /todos/random` 写入一行 - 走应用自己的路由，带着一个浏览器会
   发送的会话和 CSRF 令牌。
4. 下一个 `GET` 会带着 `Warning: 110 - "Response is Stale"` 被服务，并且恰好
   调度一次后台重建。它那五分钟的新鲜期才刚刚开始，所以 `todos` 表被推进的
   世代是唯一能解释这两件事的东西。
5. 那次重建真的运行了：这个测试在渲染计数器上等待 - 一道状态屏障，而不是一次
   定时等待 - 直到发生了一次测试自己没有派发的渲染。
6. 写入的那一行确实在列表里。这是**单独的**一步，并且刻意不是对那次后台重建
   自身输出的断言：测试先丢弃 L0 再渲染一次，因为重建的发布落在一个从应用
   触及不到的时刻，所以对碰巧赶上它的那个请求做断言会是一场竞态。
7. 而这个路由会落回到针对重新发布的条目的一次普通命中。

那个序列里没有任何地方指名过一个缓存键。一次在 `DB::transaction` 内部的 ORM
写入，会在同一个事务内部推进它的那些世代，所以一次被回滚的写入什么都不会推进。

## 今天的失效是按表粒度的

这是你在为一个被缓存的路由估算规模之前，最需要知道的一件事。

一次通过 ORM 的点读取，除了记录行标识之外，也会记录**表**标识。`Model::find` 在
查找任何东西之前调用 `observe_table_read(Self::TABLE)`，在把一行水合之后调用
`observe_record_read_json`，所以一个只读了一行的条目依赖的是整张表。因此，对
那张表的任何写入都会使**每一个**从它读过的缓存条目失效，而不只是那些读过被改动
的那一行的条目。

这是安全的 - 它只可能失效得太多，绝不会太少 - 而且它是被测量出来的，不是假定
的。`framework/benches/render_cache_workloads.rs` 里的失效风暴工作负载，在 12 个
记录标识上发布 64 个键，驱动 1,000 次写入，并把它观察到的扇出记录在
`crates/suprnova-live/benchmarks/render-cache-workloads-v1.json` 里（有删节；
记录下来的对象还带有 burst、sweep、hit、rebuild、statement 和 latency 字段）：

```json
"invalidation_storm": {
  "keys": 64,
  "identities": 12,
  "writes": 1000,
  "every_write_invalidates_every_key": true,
  "rebuilds_per_write": 1.28,
  "final_bodies_coherent": true
}
```

请围绕它来做设计。一个由你的应用不断写入的表所支撑的被缓存路由，无论它的新鲜度
窗口怎么说，都会不断重建。一个由“编辑发布点什么才会变”的表所支撑的被缓存路由，
会安安静静地待上好几个小时。如果你需要比表更细的粒度，今天诚实的答案是：你还
没有。

## 框架看不见什么

一项无法被指名的依赖就无法被失效，而对于其中哪些它拒绝存储、哪些它放行，框架
是有意为之的。

**直接拒绝。** 通过 `DB::select`、`DB::select_one`、`DB::scalar` 或
`DB::select_on` 执行的原始 SQL，无法为它那条语句读取的表命名，所以这次渲染会被
标记为不可观察，并且永远不会被存储。响应仍然每一次都会被正确地提供。框架自己的
RBAC 角色与权限检查就是这样读取的，所以一个执行了其中之一的被缓存路由永远不会
存储。通过 `DB::table(..)` 进行的读取知道自己的表，会被正常缓存。

**看不见，而且归你负责。** 通过 `Request::header` 读取的一个请求头、一次
`Config::get` 调用，以及一个从自己的每请求状态出发过滤查询的 Eloquent 全局
作用域，都会在收集器什么也看不到的情况下改变一次渲染产生的内容。请在这样的路由
上声明匹配的差异化维度；这里没有任何机制能替你捕捉这种遗漏。

**已知的缺口。** 当一个功能标志发生变化时，没有任何东西会为它推进一个世代；而
一次由队列工作进程、计划任务或控制台命令做出的写入，什么世代都不会推进，因为
只有运行了 `RenderCache::install` 的那个进程才带有写入侧的埋点。依赖这样一次
写入的页面，只会在它的新鲜度窗口内保持最新；请在一个会改变已缓存页面所显示内容
的作业之后，运行 `render-cache:epoch-advance`。参见
[RenderCache 运维](render-cache-operations.md)。

## 一次命中的代价

一致性检查就是把“我们有字节”变成“这些字节是最新的”的那一步，而它也是一次命中
所做的唯一工作。

一次命中**不运行处理程序、不运行 ORM 查询、不运行模板，也不运行序列化器**，
并且不复制任何正文字节：服务器写进套接字的字节，就是存储持有的那些字节，这一点
在 `framework/tests/render_cache/bypass.rs` 里是按地址而不是按值证明的。剩下的
就是那次证明时效性的数据库读取，而你多久付一次这笔账，取决于策略的
`CoherenceMode`：

| 模式 | 每次热命中的 SQL 语句数 | 它信任什么 |
|---|---|---|
| `Authority`（默认） | 恰好 1 条 | 账本，每一次命中都重新读取 |
| `Lease { max_age_ms }` | 0 条 | 一份本地授予的校验租约，直到它过期为止 |

`an_authority_mode_hit_issues_exactly_one_statement` 把权威模式限制在一次往返
之内：被观察到的那些世代和权威纪元是在一条 `UNION ALL` 里一起读出来的，而不是
两次读取。`a_lease_mode_hit_runs_nothing_and_issues_no_statement` 把租约模式
限制为零，因为键所依据的那个纪元是与那些世代一起被租出去的，而不是每个请求读
一次。

纪元本身是每个进程读一次，而不是每个请求读一次。
`the_epoch_is_read_once_at_first_use` 把一个全新运行时的第一次未命中，与除此
之外完全相同的第二次做对比，发现第一次恰好多付了一条语句 - 也就是那次填充纪元
租约的单次权威读取。此后每一个请求都不再为它付账。

## 当纪元移动时

`render-cache:epoch-advance` 是那次紧急失效，而纪元被烘焙进了每一个查找键，
所以接下来会发生什么，取决于你站在哪里：

- **在运行了这条命令的那个节点上**，紧接着的下一个请求就会看到新纪元。L0 会在
  同一时刻被彻底清空，缓存立即失效。
- **在另一个节点上**，一个 `Authority` 模式的路由会在它紧接着的下一次命中时
  得知。一个 `Lease` 模式的路由会在它下一次权威重读时得知，那最迟是
  `max_age_ms` 之后。

一个带有陈旧可服务窗口的路由，会在重建于请求背后运行的同时，把那个已移动的条目
带着 `Warning` 服务一次；一个没有这种窗口的路由则会在前台重建，请求方要等它。
那个差别正是声明一个陈旧可服务窗口的全部理由，而且它适用于任何一次移动，不只是
一次纪元推进。

`framework/tests/render_cache/middleware.rs` 里有三个测试按名字把这些路径压住：
`an_epoch_advanced_by_another_node_reaches_an_authority_mode_route_on_its_next_hit`、
`an_epoch_advanced_by_another_node_reaches_a_lease_mode_route_when_its_lease_expires`，
以及
`an_epoch_advanced_by_another_node_serves_a_stale_servable_entry_once_then_rebuilds`。

## 每个键一次重建：singleflight 与等待者

当一个条目缺失、或者不再是最新的时候，为它而来的那些请求不会全都去渲染。它们要
经过一个**重建协调器**来准入，而它恰好挑出其中一个：

- **领导者**是那个会渲染、并且可以发布的请求。它在自己渲染的整个时长里，持有
  那个键上的一份租约。
- **等待者**是在领导者持有租约期间，为同一个键而来的那些请求。它们在进程内
  等待，等领导者释放之后，重新评估现在存下来的是什么并服务它。一个等待者从不
  信任这次等待：如果领导者那一轮没能发布，或者发布出来的东西被等待者自己的
  新鲜度检查判为已死，那么这个等待者也会去渲染，而不是服务它找到的东西。
  `framework/tests/render_cache/middleware.rs` 里的
  `a_singleflight_waiter_never_serves_a_superseded_entry_as_fresh` 就是这条
  规则。
- 一个在已经有 `RENDER_CACHE_MAX_WAITERS`（默认 128）个请求在等待之后才到达的
  请求会**绕过**：它去渲染，什么也不发布，而不是让队列无界地长下去。

`concurrent_misses_render_once_and_waiters_reuse_the_publication` 端到端地证明
了普通情形 - 两次并发未命中、一次渲染、完全相同的正文 - 而
`crates/suprnova-live/tests/render_cache_singleflight.rs` 里的
`one_leader_per_key_and_fence_with_bounded_waiters` 则直接针对协调器证明了那个
上限：超过它的等待者限额之后，准入回答 `Bypass`。

无论协调器怎么决定，同一个键的两次发布绝不可能都被接受。领导者会在自己的租约下
铸出一个发布令牌，而存储在写入之前会比较那道栅栏：更旧的纪元，或者纪元相同但
令牌更低的，输。这正是为什么重复*渲染*可以安全接受、而重复*发布*不行；也正是
为什么这里根本没有跨节点等待 - 一个正在被另一个节点重建的键，在这里就是一次
绕过。参见 [RenderCache 部署](render-cache-deployment.md)。

## 在它被重建期间提供些什么

四种新鲜度状态、`FreshnessPolicy` 设定的那些区间，以及一个陈旧响应携带的
`Warning` 和 `Age`，都定义在
[RenderCache 表示](render-cache-representations.md)。这里要紧的是：一次世代
移动会把一个条目提前推进那些区间 - 一个已移动的条目，无论它真实的年龄是多少，
都会按**至少**等于它新鲜区间的有效年龄来评估。而它真实的年龄仍然决定这会把它
落到哪一个区间：

- 真实年龄小于 `fresh_ms + stale_servable_ms`，且这个路由声明了一个陈旧可服务
  窗口：陈旧可服务。已存储的副本会带着 `Warning` 被服务一次，而重建在请求背后
  运行。这就是上面那个写入测试的第 4 步，发生在一个五分钟新鲜期才刚刚开始的
  条目上。
- 真实年龄超过那个界限、但还没到死亡边界：出错时陈旧可服务。请求会等待一次前台
  重建，只有当那次重建失败时才会看到已存储的副本。
- 在一个完全没有陈旧可服务窗口的路由上，以及在每一个 `PrivateCached` 路由上
  （它的死亡边界*就是*它的新鲜边界），一次移动就是已死：请求会在前台重建并
  等待。

`stale_service_is_marked_and_rebuilt_in_the_background` 展示的是同一次交接，
只不过是由时钟而不是由一次写入驱动的：越过 `/live/todos` 那 300,000 毫秒的
新鲜期之后、并且还在它 60,000 毫秒的陈旧可服务期之内，访客会拿到手头那份副本，
带着 `Warning: 110 - "Response is Stale"` 和 `Age: 300`，恰好有一次重建被调度，
而且那次重建真的运行了。

出错时陈旧回退，既覆盖领着一次重建的那个请求，**也**覆盖排在一个重建失败的
领导者后面的等待者。两者的应答方式是一样的：带 `Warning` 的陈旧字节，而不是那次
失败。`framework/tests/render_cache/races.rs` 分别证明了每一条分支 -
`a_waiter_behind_a_failed_leader_is_served_the_stale_entry_it_was_waiting_on` 和
`a_waiter_that_re_evaluates_onto_a_stale_on_error_entry_falls_back_to_it` - 而
第二条是靠撤销来证明的：把这条等待分支上的回退去掉，它最后那些断言就会从 `200`
变成 `500`。

缝合路由是例外，而且是刻意的例外。一个 `Composite` 条目绝不会被出错时陈旧回退
所服务，也绝不会触发一次后台重建：在一次重建失败之后还去服务一个已存储的外壳，
等于应答一个这个路由自己的授权链根本没机会把关的请求；而一次后台重建不携带这个
请求的任何授权状态，所以它的外壳会是这个页面为“没有人”渲染出来的样子。在一个
缝合路由上，客户端看到的就是那次失败重建自己的结果。

## 被缓存的路由是读路径

领导者的渲染运行在一个数据库事务里，这个事务在 PostgreSQL 和 MySQL 上以
`REPEATABLE READ` 打开，所以它记录下的那些世代与它读到的数据共享同一个快照。
由此有两个后果。

一个被缓存路由的处理程序如果**执行写入**，就会为同一些行与并发写入者竞争；
并且在 PostgreSQL 上，一个更新了某一行、而这一行在渲染开始之后被另一个事务
改动过的处理程序，会遇到一次序列化失败。把被缓存的路由设计成读路径。

一次在任何事务之外完成的写入 - 单独调用 `model.save()` - 会先提交它那一行，
再在紧随其后的一个事务中推进它的那些世代。两者之间的那个瞬间是“新数据，旧
世代”：它的代价是多一次重建，而绝不会提供陈旧内容。

最后，在渲染结束之后，那些被观察到的依赖和纪元会在渲染自己的事务视图之外被再读
一次。渲染期间移动过的任何东西，都会让这个候选被丢弃，而不是被发布。这就是为
什么一次落在渲染中途的写入，代价是一次重建，而不是一个错误的页面。

### 为什么 Suprnova 有所不同

Laravel 的缓存是一个键值存储，而它的响应缓存包是建在它之上的，所以失效是你自己
要写的东西。你去调用 `Cache::forget`，或者给条目打上标签再刷掉一个标签，或者
注册一个模型观察者，去清掉你认为那个模型供养的那些键。这里每一样都是一份你手工
维护的映射，而它的失败模式是静默的：那个谁都没想起来要 forget 的页面，会一直
服务到它的 TTL 走完为止。

Suprnova 把方向反了过来。渲染记录它读了什么，写入推进它改了什么，而两者是在一个
数据库账本里相会，而不是在你脑子里。没有哪个 `forget` 调用可以被忘掉。代价是被
记录下来的依赖是一张表而不是一行，所以一张繁忙的表会让它的依赖者频繁重建；以及
通过原始 SQL 的读取会被拒绝存储，而不是带着一个谁也叫不出名字的依赖被缓存下来。
这两点都是可见并且被测量过的 - 前者是签入的风暴工作负载里的扇出，后者是你自己
那个缺失的 `Age` 头 - 而不是一个你从客户那里才得知的陈旧页面。
