# 贡献指南

Suprnova 以 MIT 许可证开源，最有价值的贡献是一份**好的报告**。该项目不接受拉取请求：这个框架从头到尾都由维护者编写，每一次变更都要经维护者之手落地，从而让整个表面保持同一种形态。这是一种刻意的、永久的姿态 - 不是 1.0 之前的阶段性做法。

MIT 意味着您永远不需要许可，就可以自行把这份代码继续往前推进：**尽情复刻**。一个朝着自己的方向成长的复刻，是一个健康的结果，不是一种竞争。

这在实践中意味着：

- **缺陷报告** - 欢迎，通过 [GitHub issues](https://github.com/eas4ai/suprnova/issues)。
- **功能请求** - 欢迎，通过 issue。请描述使用场景，而不是实现方式；往往已经有一个计划好的形态（通常是 Laravel 对应功能的样子）。
- **文档缺陷** - 欢迎，通过 issue。如果某一章说某个 API 存在，而您却找不到它，那就是一个文档缺陷 - 请说明是哪一章，以及您原本期望的是什么。
- **安全问题** - 私下报告，通过邮件（见下文）。绝不要以公开 issue 的形式报告。
- **拉取请求** - 不接受。拉取请求会被关闭，并附上指向本章的链接；请改为开一个 issue，这样修复就能在上游落地，或者复刻并自行携带这个变更。

## 提交一份能被快速修复的缺陷报告

金标准是从一个全新的脚手架给出的一次复现：

```bash
suprnova new repro-app --frontend vue --no-interaction
# …展示这个缺陷所需的最小改动…
```

包含：

1. **您做了什么** - 命令和代码，裁剪到最少
2. **您原本期望什么** - 一句话
3. **实际发生了什么** - 实际的输出或错误，原样粘贴
4. **版本** - 框架的 tag（`suprnova --version`，或者您 `Cargo.toml` 里的 `tag =`）以及您的 Rust 版本（`rustc --version`）

一个失败的测试比文字描述更好。如果您能把这个缺陷表达成一个针对框架的测试，就把它粘贴进 issue - 它通常会成为修复落地时随之带上的那个回归测试。

## 从源代码构建（用于调查一份报告）

您不需要这一步来*提交* issue，但针对这个工作空间进行复现，往往能让报告更精确：

```bash
git clone https://github.com/eas4ai/suprnova.git
cd suprnova
cargo check --workspace          # 对一切进行类型检查
cargo test --workspace           # 运行完整的测试套件（大约 3400 个测试）
```

这个工作空间的布局：`framework/`（即 `suprnova` crate）、`suprnova-cli/`（即 `suprnova` 二进制文件）、`suprnova-macros/`（过程宏）、`app/`（内部自用（dogfood）应用）、`crates/`（支付和 Web 推送适配器），以及 `manual/`（本手册）。

## 代码所遵循的标准

这不是贡献者规则 - 但了解这个标准能帮助您校准报告的粒度（来自库代码的一次 panic、一个缺失的失败模式测试，或者一个强制您使用 `unwrap()` 的 API，永远值得报告）：

- **只接受完整的实现。** 没有 TODO，没有半成品脚手架。一个修复要连同钉住它的回归测试一起落地。
- **公开表面的代码返回 `Result`，不会 panic。** 凡是发布了一个 Laravel 风格的不可失败名称的地方，都会随之发布一个 `try_*` 对应函数。
- **除环境启动之外，不允许出现 `unsafe`。** 这个框架在非测试代码里只有两处 `unsafe` 块，都在 `config/env.rs::load_dotenv` 里，都包裹着 `std::env::set_var` / `remove_var` - 这两个函数在 2024 版本中变成了 `unsafe` - 并且都带着一条针对它们所依赖的启动期单线程不变量的 SAFETY 说明。其余的都只用于测试。在别处引入新的 `unsafe` 都需要在审查中给出书面理由，而驱动程序、处理程序或宏展开里的 `unsafe` 不会被接受。
- **`cargo fmt` 以及在 `-D warnings` 下运行的 clippy 是权威标准。**

完整的错误契约请参见 [错误模型](error-model.md)。

## 安全

请把安全问题私下报告给 **shawn@eas4ai.com**（项目维护者）。我们会在几天之内回执，在一个私有分支上做修复，并与您协调披露事宜。

在修复发布之前，请不要把安全问题作为公开的 GitHub issue 提交。

### 依赖公告

`cargo audit` 会在发布关卡里运行。如果一条公告没有可用的修复，而那段有漏洞的代码在默认构建里又不可达，它可以被加进审计忽略列表 - 但每一条条目都需要三样东西，缺了关卡就会失败：

```toml
# OWNER: name <email>
# EXPIRES: YYYY-MM-DD
"RUSTSEC-XXXX-XXXX",
```

- 一个**负责人**，好让这条例外属于某个人；
- 一个**期限**，过期之后，关卡就会拒绝运行，直到这条条目带着一个明说的理由被续期，或者被删除；
- 一段**写下来的可达性论证** - 是哪条路径把它拉进来的，以及为什么一次默认构建不会链接它。

可达性的说法会被核实，而不是被信任。如果您的论证是“这在一个默认关闭的 feature 后面”，发布关卡就会去解析真实的依赖树，并断言这个 crate 在默认那棵树里不存在、在开启之后那棵树里存在。一条无人核实其理由的例外，会在第一次有人添加依赖时，悄无声息地不再成立。

一次忽略，就是一个发布已知问题的决定。它读起来也应该像一个决定。
