# Tipos TypeScript

`suprnova generate-types` varre seu código-fonte Rust à procura de structs
`#[derive(InertiaProps)]` e `#[derive(Data)]` e escreve declarações
TypeScript que o frontend pode importar. Execute-o depois de mudar props
ou rotas; `suprnova serve` o executa para você na inicialização, a menos
que você passe `--skip-types`.

## O que é gerado

Três arquivos, escritos em `frontend/src/types/`:

| Arquivo | Conteúdo |
|---|---|
| `inertia-props.ts` | Um `export interface` por struct de prop - sempre escrito |
| `routes.ts` | Um objeto `controllers` e um mapa de busca nomeado `routes` derivados de `src/routes.rs` - escrito somente com `--routes` |
| `lang-keys.ts` | Uma união de literais de string `MessageKey` de todo id de mensagem Fluent no catálogo da locale padrão, pais de fallback incluídos - escrito somente quando `lang/` produz algum id (veja [Chaves de mensagem](#chaves-de-mensagem)) |

Os três começam com um comentário de cabeçalho marcando-os como
gerados automaticamente. Não os edite manualmente - suas mudanças são
sobrescritas na próxima execução.

## Executando-o

```bash
# Uma execução única
suprnova generate-types

# Re-emite a cada mudança em um arquivo Rust
suprnova generate-types --watch

# Saída customizada para o arquivo de props
suprnova generate-types --output frontend/src/types/props.ts
```

O caminho do arquivo de rotas é fixo em `frontend/src/types/routes.ts` e o
do arquivo de chaves de mensagem em `frontend/src/types/lang-keys.ts`;
somente o caminho do arquivo de props é configurável. O watcher monitora
`src/` e regenera o arquivo de props a cada mudança em `.rs`; quando o
projeto tem um diretório `lang/`, ele também observa aquela árvore e
regenera `lang-keys.ts` a cada mudança em `.ftl`.

## Props de página

O formato esperado: um struct Rust por página Inertia, derivando
`InertiaProps`, pareado com um componente de página que tipa suas props a
partir da interface gerada.

```rust
// src/controllers/home.rs
use suprnova::{InertiaProps, Request, Response, inertia_response};

#[derive(InertiaProps)]
pub struct HomeProps {
    pub title: String,
    pub message: String,
    pub count: i64,
    pub tags: Vec<String>,
    pub avatar_url: Option<String>,
}

pub async fn index(req: Request) -> Response {
    inertia_response!(&req, "Home", HomeProps {
        title: "Welcome".into(),
        message: "Hello".into(),
        count: 3,
        tags: vec!["new".into(), "featured".into()],
        avatar_url: None,
    })
}
```

`suprnova generate-types` emite:

```typescript
// frontend/src/types/inertia-props.ts
// This file is auto-generated by Suprnova. Do not edit manually.
// Run `suprnova generate-types` to regenerate.

export interface HomeProps {
  title: string;
  message: string;
  count: number;
  tags: Array<string>;
  avatar_url: string | null;
}
```

Consuma-a da mesma forma independentemente do framework de frontend - a
linha `import type` é idêntica entre Svelte, React e Vue:

```svelte
<!-- frontend/src/pages/Home.svelte (o scaffold padrão) -->
<script lang="ts">
  import type { HomeProps } from '../types/inertia-props'

  let { title, message, count, tags, avatar_url }: HomeProps = $props()
</script>

<h1>{title}</h1>
<p>{message} - {count} items</p>
{#if avatar_url}<img src={avatar_url} alt="" />{/if}
```

Veja [Componentes de página](frontend-pages.md) para os equivalentes em
React e Vue.

## Mapeamento de tipos

| Rust | TypeScript | Notas |
|---|---|---|
| `String`, `&str` | `string` | |
| `i8`..`i128`, `u8`..`u128`, `isize`, `usize`, `f32`, `f64` | `number` | Todos os primitivos numéricos colapsam para `number` |
| `bool` | `boolean` | |
| `Option<T>` | `T \| null` | |
| `Vec<T>` | `Array<T>` | O gerador de props emite `Array<T>`; o gerador de rotas emite `T[]` para campos de form request |
| `HashMap<K, V>`, `BTreeMap<K, V>` | `Record<K, V>` | |
| `Field<T>` (de `#[derive(Data)]`) | `field?: T \| null` | Field é opcional na rede |
| `Prop<T>` (lazy / deferred) | `field?: T` | Props lazy omitem a metade `null` |
| Qualquer outra coisa | identificador puro | Veja "Tipos customizados" abaixo |

## Tipos customizados

O visitor reconhece os primitivos na tabela acima. Tudo o mais é emitido
como seu nome de tipo Rust puro. Duas consequências decorrem disso:

**Um struct aninhado só recebe sua própria interface se ele derivar
`InertiaProps` ou `Data`.** Um struct `#[derive(Serialize)]` puro é
invisível para o gerador - a interface emitida vai referenciá-lo pelo
nome, mas nenhuma declaração é produzida:

```rust
use serde::Serialize;
use suprnova::{Data, InertiaProps};

#[derive(Serialize)]
pub struct Address {  // NÃO capturado - sem derive de InertiaProps/Data
    pub street: String,
    pub city: String,
}

#[derive(Data)]      // OU InertiaProps - qualquer um funciona
pub struct Company {
    pub name: String,
    pub address: Address,
}

#[derive(InertiaProps)]
pub struct ProfileProps {
    pub user_name: String,
    pub company: Company,
}
```

Saída gerada:

```typescript
export interface Company {
  name: string;
  address: Address;          // pendente - nenhuma interface Address é emitida
}

export interface ProfileProps {
  user_name: string;
  company: Company;
}
```

Para corrigir: adicione `#[derive(Data)]` (ou `InertiaProps`) a
`Address`. O comportamento de serialização em tempo de execução não é
afetado pela escolha de derive no struct aninhado - o `serde_json` ainda
vai emitir o struct corretamente - mas o TypeScript precisa da declaração
explícita.

**Argumentos genéricos em tipos customizados não são percorridos
recursivamente.** `chrono::DateTime<Utc>`, `uuid::Uuid`,
`rust_decimal::Decimal`, e quaisquer tipos seus que não derivem são
emitidos como o identificador principal puro (`DateTime`, `Uuid`,
`Decimal`). Eles serializam para strings JSON na rede, mas a declaração
TypeScript não vai dizer isso. Duas formas de lidar com isso:

```typescript
// frontend/src/types/runtime-types.ts - escrito à mão ao lado do arquivo gerado
export type DateTime = string;        // chrono::DateTime<_> serializa como RFC 3339
export type Uuid = string;
export type Decimal = string;         // padrão do serde_with; rust_decimal::Decimal
```

Então, no `tsconfig.json`, garanta que eles sejam capturados pelo seu
glob de `include`, ou `import type { DateTime } from './runtime-types'`
onde for necessário. O framework não te entrega esses aliases porque a
escolha certa (`string` vs `number` vs tipo com marca) depende das
feature flags do serde que você ativou.

## Structs genéricas

Uma struct genérica em Rust se torna uma interface TypeScript genérica:

```rust
use suprnova::{Data, data::Field};

#[derive(Data)]
pub struct Paginated<T>
where
    T: serde::Serialize + for<'de> serde::Deserialize<'de>,
{
    pub items: Vec<T>,
    pub total: usize,
    pub cursor: Field<String>,
}
```

```typescript
export interface Paginated<T> {
  items: Array<T>;
  total: number;
  cursor?: string | null;
}
```

A cláusula `where` é descartada - genéricos em TypeScript são
irrestritos, a menos que você diga o contrário no lado consumidor.

## Interfaces de entrada/saída divididas

Quando um struct `#[derive(Data)]` mistura campos `#[data(input_only)]`,
`#[data(output_only)]`, ou `#[data(lazy)]`, duas interfaces são emitidas -
o formato de saída (o que o frontend recebe) e uma contraparte
`<Name>Input` (o que ele envia de volta):

```rust
use suprnova::Data;
use suprnova::data::Field;
use suprnova::inertia::Prop;
use validator::Validate;

#[derive(Data, Validate)]
pub struct UserDto {
    pub id: i64,
    pub name: String,

    #[data(input_only)]
    #[validate(length(min = 8))]
    pub password: String,

    #[data(output_only)]
    pub computed_handle: String,

    pub bio: Field<String>,

    #[data(lazy)]
    pub favorite_song: Prop<String>,
}
```

Emite ambas:

```typescript
export interface UserDto {              // servidor -> cliente
  id: number;
  name: string;
  computed_handle: string;
  bio?: string | null;
  favorite_song?: string;
}

export interface UserDtoInput {         // cliente -> servidor
  id: number;
  name: string;
  password: string;
  bio?: string | null;
}
```

Campos `Prop` são somente-saída por natureza, então são removidos do tipo
de entrada mesmo quando `lazy` não é explícito. Para o conjunto completo
de flags `#[data(...)]` e sua semântica de autoria, veja [Data](data.md).

## Rotas com tipos seguros

Com `--routes`, o comando escreve um segundo arquivo,
`frontend/src/types/routes.ts`, gerado a partir de `src/routes.rs`. Ele
expõe um objeto `controllers` cujos formatos de método espelham a árvore
de módulos do seu backend, além de uma busca `routes` indexada por
`.name(...)`:

```rust
// src/routes.rs
use suprnova::routes;

routes! {
    get!("/", controllers::home::index).name("home"),
    get!("/users", controllers::user::index).name("users.index"),
    get!("/users/{id}", controllers::user::show).name("users.show"),
    post!("/users", controllers::user::store).name("users.store"),
}
```

```typescript
// frontend/src/types/routes.ts
import type { Method } from '@inertiajs/core';

export interface RouteConfig<TData = void> {
  url: string;
  method: Method;
  data?: TData;
}

export interface UserShowParams {
  id: string;
}

export const controllers = {
  home: {
    index: (): RouteConfig => ({ url: '/', method: 'get' }),
  },
  user: {
    index: (): RouteConfig => ({ url: '/users', method: 'get' }),
    show: (params: UserShowParams): RouteConfig =>
      ({ url: `/users/${params.id}`, method: 'get' }),
    store: (): RouteConfig => ({ url: '/users', method: 'post' }),
  },
} as const;

export const routes = {
  'home': controllers.home.index,
  'users.index': controllers.user.index,
  'users.show': controllers.user.show,
  'users.store': controllers.user.store,
} as const;
```

`RouteConfig` é intencionalmente moldado para satisfazer a interface
`UrlMethodPair` do Inertia 3, então se encaixa em `router.visit`, no
`submit` do `useForm`, e em `<Link href={...}>` sem um adaptador:

```ts
import { router } from '@inertiajs/svelte'   // ou /react, /vue
import { controllers, routes } from '../types/routes'

router.visit(controllers.home.index())
router.visit(controllers.user.show({ id: '42' }))
router.visit(routes['users.show']({ id: '42' }))
```

Se um caminho tem params (`/users/{id}`), a função gerada exige o objeto
`Params` tipado - o TypeScript captura chaves ausentes ou digitadas
incorretamente em tempo de compilação.

## Chaves de mensagem

Se o app tem uma árvore de catálogo `lang/`, o gerador também escreve
`frontend/src/types/lang-keys.ts`: uma união de literais de string
`MessageKey` de todo id de mensagem Fluent que o frontend pode resolver.
O wrapper `t()` dos starter kits tipa seu argumento de chave como
`MessageKey`, então uma chave digitada errada ou apagada é um erro de
TypeScript apontando para o componente - a mesma promessa que
`inertia-props.ts` faz para props, estendida a traduções.

Os ids vêm de `lang/<APP_LOCALE>/*.ftl`, unidos entre os pais de fallback
configurados da locale (`APP_LOCALE_PARENTS`) - então um catálogo no
estilo delta que guarda apenas as strings que ele sobrescreve ainda gera
o conjunto completo de chaves que o catálogo servido, já achatado pela
cadeia, carrega. `APP_FALLBACK_LOCALE` deliberadamente *não* está
incluído: o catálogo servido também não achata o fallback terminal, e a
união precisa descrever exatamente o que o único catálogo buscado pelo
navegador consegue resolver. Veja [Localização](localization.md) para a
cadeia em si.

O arquivo segue as mesmas regras que os outros dois: caminho fixo,
cabeçalho gerado automaticamente, saída ordenada de forma determinística,
nunca editado manualmente. Quando nenhum arquivo `.ftl` produz algum id,
o arquivo é removido em vez de emitido vazio - um kit que importa
`MessageKey` então falha ao compilar até que o catálogo tenha ids de
novo, o que é alto, como qualquer outro desvio neste pipeline.

## Quando ele executa

`suprnova serve` dispara `generate-types` na inicialização. O fluxo
padrão:

```
suprnova serve
  ├─ varre src/ à procura de structs InertiaProps / Data        → inertia-props.ts
  ├─ varre src/routes.rs à procura de definições de rota        → routes.ts
  ├─ varre lang/ à procura de ids de mensagem Fluent            → lang-keys.ts
  ├─ inicia o backend
  └─ inicia o Vite
```

Passe `--skip-types` para pular ambos. Execute `suprnova generate-types`
manualmente sempre que você mudar código Rust enquanto o backend está em
hot-reload e quiser declarações atualizadas sem reiniciar o servidor.

### Faça commit da saída, e espere um diff limpo

`inertia-props.ts` deve ser versionado - é isso que permite a um revisor
ver uma mudança de contrato de prop no mesmo diff que o Rust que a
causou, e o que evita que o CI precise de uma toolchain Rust para
verificar os tipos do frontend.

A geração é determinística: a mesma origem produz saída idêntica byte a
byte, em qualquer máquina, em qualquer ordem em que os arquivos aconteçam
de estar no disco. Então uma execução que não muda nada não mostra
nenhum diff, e qualquer diff que você vir é uma mudança de contrato real.
(Não era sempre assim - a ordenação se originava da ordem de iteração do
hash, e cada execução reembaralhava as interfaces.)

Duas consequências que vale internalizar:

- **Nenhuma outra coisa pode editar esse arquivo.** Se um componente
  importa um tipo que o gerador não emite, o próximo `generate-types` o
  apaga e o frontend para de compilar. A correção é declarar o tipo em
  Rust, não editar a saída manualmente.
- **Uma página sem rota Rust não tem tipo gerado**, porque não existe
  um struct `#[derive(InertiaProps)]` por trás dela. Declare suas props
  localmente no componente até que um handler exista para tê-las.

## Por que Suprnova diverge

O Laravel não traz geração de tipos para o Inertia porque PHP é
dinamicamente tipado - não há nada no lado do servidor de onde extrair um
contrato. A comunidade Laravel do Inertia preencheu a lacuna com
ferramentas de terceiros (Laravel Typed Inertia, Wayfinder) que leem
anotações PHPDoc ou DocBlock.

O Suprnova tem a informação de tipos em tempo de compilação e no disco,
então nós a extraímos diretamente. O mesmo `#[derive(InertiaProps)]` ou
`#[derive(Data)]` que controla a serialização JSON também guia a saída
TypeScript - uma única fonte de verdade, nunca fora de sincronia com o
que o serde de fato emite.
