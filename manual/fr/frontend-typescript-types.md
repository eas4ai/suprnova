# Types TypeScript

`suprnova generate-types` scanne votre source Rust à la recherche des
structs `#[derive(InertiaProps)]` et `#[derive(Data)]`, et écrit des
déclarations TypeScript que le frontend peut importer. Lancez-la après
avoir changé des props ou des routes ; `suprnova serve` la lance pour
vous à l'amorçage, sauf si vous passez `--skip-types`.

## Ce qui est généré

Trois fichiers, écrits dans `frontend/src/types/` :

| Fichier | Contenu |
|---|---|
| `inertia-props.ts` | Une `export interface` par struct de props - toujours écrit |
| `routes.ts` | Un objet `controllers` et une map de recherche nommée `routes` dérivés de `src/routes.rs` - écrit seulement avec `--routes` |
| `lang-keys.ts` | Une union de littéraux de chaîne `MessageKey` pour chaque id de message Fluent du catalogue de la locale par défaut, parents de repli compris - écrit seulement quand `lang/` produit des ids (voir [Clés de message](#clés-de-message)) |

Les trois commencent par un commentaire d'en-tête indiquant qu'ils sont
auto-générés. Ne les modifiez pas à la main - vos changements seraient
écrasés à la prochaine exécution.

## Le lancer

```bash
# Ponctuel
suprnova generate-types

# Réémet à chaque changement de fichier Rust
suprnova generate-types --watch

# Sortie personnalisée pour le fichier de props
suprnova generate-types --output frontend/src/types/props.ts
```

Le chemin du fichier de routes est fixé à
`frontend/src/types/routes.ts` et celui du fichier de clés de message à
`frontend/src/types/lang-keys.ts` ; seul le chemin du fichier de props
est configurable. Le watcher sonde `src/` et régénère le fichier de
props à chaque changement `.rs` ; quand le projet a un répertoire
`lang/`, il surveille aussi cet arbre et régénère `lang-keys.ts` à
chaque changement `.ftl`.

## Props de page

La forme attendue : une struct Rust par page Inertia, dérivant
`InertiaProps`, jumelée à un composant de page qui type ses props à
partir de l'interface générée.

```rust
// src/controllers/home.rs
use suprnova::{InertiaProps, Request, Response, inertia_response};

#[derive(InertiaProps)]
pub struct HomeProps {
    pub title: String,
    pub message: String,
    pub count: i64,
    pub tags: Vec<String>,
    pub avatar_url: Option<String>,
}

pub async fn index(req: Request) -> Response {
    inertia_response!(&req, "Home", HomeProps {
        title: "Welcome".into(),
        message: "Hello".into(),
        count: 3,
        tags: vec!["new".into(), "featured".into()],
        avatar_url: None,
    })
}
```

`suprnova generate-types` émet :

```typescript
// frontend/src/types/inertia-props.ts
// This file is auto-generated by Suprnova. Do not edit manually.
// Run `suprnova generate-types` to regenerate.

export interface HomeProps {
  title: string;
  message: string;
  count: number;
  tags: Array<string>;
  avatar_url: string | null;
}
```

Consommez-le de la même façon quel que soit le framework frontend - la
ligne `import type` est identique entre Svelte, React et Vue :

```svelte
<!-- frontend/src/pages/Home.svelte (le scaffold par défaut) -->
<script lang="ts">
  import type { HomeProps } from '../types/inertia-props'

  let { title, message, count, tags, avatar_url }: HomeProps = $props()
</script>

<h1>{title}</h1>
<p>{message} - {count} items</p>
{#if avatar_url}<img src={avatar_url} alt="" />{/if}
```

Voir [Composants de page](frontend-pages.md) pour les équivalents React
et Vue.

## Correspondance des types

| Rust | TypeScript | Notes |
|---|---|---|
| `String`, `&str` | `string` | |
| `i8`..`i128`, `u8`..`u128`, `isize`, `usize`, `f32`, `f64` | `number` | Tous les primitifs numériques se réduisent à `number` |
| `bool` | `boolean` | |
| `Option<T>` | `T \| null` | |
| `Vec<T>` | `Array<T>` | Le générateur de props émet `Array<T>` ; le générateur de routes émet `T[]` pour les champs de requête de formulaire |
| `HashMap<K, V>`, `BTreeMap<K, V>` | `Record<K, V>` | |
| `Field<T>` (depuis `#[derive(Data)]`) | `field?: T \| null` | Le champ est facultatif sur le réseau |
| `Prop<T>` (lazy / deferred) | `field?: T` | Les props lazy omettent la moitié `null` |
| Tout le reste | identifiant nu | Voir « Types personnalisés » plus bas |

## Types personnalisés

Le visiteur reconnaît les primitifs du tableau ci-dessus. Tout le reste
s'émet sous son nom de type Rust nu. Deux conséquences en découlent :

**Une struct imbriquée n'obtient sa propre interface que si elle dérive
`InertiaProps` ou `Data`.** Une struct `#[derive(Serialize)]` nue est
invisible pour le générateur - l'interface émise la référencera par
son nom, mais aucune déclaration n'est produite :

```rust
use serde::Serialize;
use suprnova::{Data, InertiaProps};

#[derive(Serialize)]
pub struct Address {  // PAS repérée - pas de derive InertiaProps/Data
    pub street: String,
    pub city: String,
}

#[derive(Data)]      // OU InertiaProps - les deux marchent
pub struct Company {
    pub name: String,
    pub address: Address,
}

#[derive(InertiaProps)]
pub struct ProfileProps {
    pub user_name: String,
    pub company: Company,
}
```

Sortie générée :

```typescript
export interface Company {
  name: string;
  address: Address;          // pendante - aucune interface Address émise
}

export interface ProfileProps {
  user_name: string;
  company: Company;
}
```

Pour corriger : ajoutez `#[derive(Data)]` (ou `InertiaProps`) à
`Address`. Le comportement de sérialisation à l'exécution n'est pas
affecté par le choix du derive sur la struct imbriquée - `serde_json`
émettra quand même la struct correctement - mais TypeScript a besoin
de la déclaration explicite.

**Les arguments génériques sur les types personnalisés ne sont pas
parcourus récursivement.** `chrono::DateTime<Utc>`, `uuid::Uuid`,
`rust_decimal::Decimal`, et tout type non dérivé qui vous appartient
s'émettent sous leur identifiant nu de tête (`DateTime`, `Uuid`,
`Decimal`). Ils se sérialisent en chaînes JSON sur le réseau, mais la
déclaration TypeScript ne le dira pas. Deux façons de gérer ça :

```typescript
// frontend/src/types/runtime-types.ts - écrit à la main aux côtés du fichier généré
export type DateTime = string;        // chrono::DateTime<_> se sérialise en RFC 3339
export type Uuid = string;
export type Decimal = string;         // défaut de serde_with ; rust_decimal::Decimal
```

Ensuite, dans `tsconfig.json`, assurez-vous qu'ils sont pris en compte
via votre glob `include`, ou faites
`import type { DateTime } from './runtime-types'` là où c'est
nécessaire. Le framework ne fournit pas ces alias pour vous, car le bon
choix (`string` contre `number` contre type marqué) dépend des
features serde que vous avez activées.

## Structs génériques

Une struct Rust générique devient une interface TypeScript générique :

```rust
use suprnova::{Data, data::Field};

#[derive(Data)]
pub struct Paginated<T>
where
    T: serde::Serialize + for<'de> serde::Deserialize<'de>,
{
    pub items: Vec<T>,
    pub total: usize,
    pub cursor: Field<String>,
}
```

```typescript
export interface Paginated<T> {
  items: Array<T>;
  total: number;
  cursor?: string | null;
}
```

La clause `where` est abandonnée - les génériques TypeScript sont non
contraints, sauf indication contraire du côté consommateur.

## Scission des interfaces entrée/sortie

Quand une struct `#[derive(Data)]` mélange des champs
`#[data(input_only)]`, `#[data(output_only)]` ou `#[data(lazy)]`, deux
interfaces sont émises - la forme de sortie (ce que le frontend reçoit)
et un homologue `<Name>Input` (ce qu'il renvoie) :

```rust
use suprnova::Data;
use suprnova::data::Field;
use suprnova::inertia::Prop;
use validator::Validate;

#[derive(Data, Validate)]
pub struct UserDto {
    pub id: i64,
    pub name: String,

    #[data(input_only)]
    #[validate(length(min = 8))]
    pub password: String,

    #[data(output_only)]
    pub computed_handle: String,

    pub bio: Field<String>,

    #[data(lazy)]
    pub favorite_song: Prop<String>,
}
```

Émet les deux :

```typescript
export interface UserDto {              // serveur -> client
  id: number;
  name: string;
  computed_handle: string;
  bio?: string | null;
  favorite_song?: string;
}

export interface UserDtoInput {         // client -> serveur
  id: number;
  name: string;
  password: string;
  bio?: string | null;
}
```

Les champs `Prop` sont sortie-seulement par nature, ils sont donc
retirés du type d'entrée même quand `lazy` n'est pas explicite. Pour
l'ensemble complet des flags `#[data(...)]` et leur sémantique de
rédaction, voir [Objets de données](data.md).

## Routes type-safe

Avec `--routes`, la commande écrit un second fichier,
`frontend/src/types/routes.ts`, généré depuis `src/routes.rs`. Il
expose un objet `controllers` dont les formes de méthode reflètent
votre arbre de modules backend, plus une recherche `routes` indexée
par `.name(...)` :

```rust
// src/routes.rs
use suprnova::routes;

routes! {
    get!("/", controllers::home::index).name("home"),
    get!("/users", controllers::user::index).name("users.index"),
    get!("/users/{id}", controllers::user::show).name("users.show"),
    post!("/users", controllers::user::store).name("users.store"),
}
```

```typescript
// frontend/src/types/routes.ts
import type { Method } from '@inertiajs/core';

export interface RouteConfig<TData = void> {
  url: string;
  method: Method;
  data?: TData;
}

export interface UserShowParams {
  id: string;
}

export const controllers = {
  home: {
    index: (): RouteConfig => ({ url: '/', method: 'get' }),
  },
  user: {
    index: (): RouteConfig => ({ url: '/users', method: 'get' }),
    show: (params: UserShowParams): RouteConfig =>
      ({ url: `/users/${params.id}`, method: 'get' }),
    store: (): RouteConfig => ({ url: '/users', method: 'post' }),
  },
} as const;

export const routes = {
  'home': controllers.home.index,
  'users.index': controllers.user.index,
  'users.show': controllers.user.show,
  'users.store': controllers.user.store,
} as const;
```

`RouteConfig` est délibérément formé pour satisfaire l'interface
`UrlMethodPair` d'Inertia 3, si bien qu'il s'insère dans `router.visit`,
le `submit` de `useForm`, et `<Link href={...}>` sans adaptateur :

```ts
import { router } from '@inertiajs/svelte'   // ou /react, /vue
import { controllers, routes } from '../types/routes'

router.visit(controllers.home.index())
router.visit(controllers.user.show({ id: '42' }))
router.visit(routes['users.show']({ id: '42' }))
```

Si un chemin a des params (`/users/{id}`), la fonction générée exige
l'objet `Params` typé - TypeScript attrape les clés manquantes ou mal
orthographiées à la compilation.

## Clés de message

Si l'application a un arbre de catalogue `lang/`, le générateur écrit
aussi `frontend/src/types/lang-keys.ts` : une union de littéraux de
chaîne `MessageKey` pour chaque id de message Fluent que le frontend
peut résoudre. Le wrapper `t()` des starter kits type son argument de
clé comme `MessageKey`, si bien qu'une clé mal orthographiée ou
supprimée est une erreur TypeScript qui pointe vers le composant - la
même promesse que `inertia-props.ts` fait pour les props, étendue aux
traductions.

Les ids viennent de `lang/<APP_LOCALE>/*.ftl`, unis avec les parents de
repli configurés pour la locale (`APP_LOCALE_PARENTS`) - si bien qu'un
catalogue de type delta, qui ne porte que les chaînes qu'il redéfinit,
génère quand même l'ensemble complet des clés que porte le catalogue
servi et aplati sur la chaîne. `APP_FALLBACK_LOCALE` n'est
délibérément *pas* inclus : le catalogue servi n'aplatit pas non plus
le repli terminal, et l'union doit décrire exactement ce que l'unique
catalogue récupéré par le navigateur peut résoudre. Voir
[Localisation](localization.md) pour la chaîne elle-même.

Le fichier suit les mêmes règles que les deux autres : chemin fixe,
en-tête auto-généré, sortie triée et déterministe, jamais modifié à la
main. Quand aucun fichier `.ftl` ne produit d'id, le fichier est
supprimé plutôt qu'émis vide - un kit qui importe `MessageKey` échoue
alors à la compilation jusqu'à ce que le catalogue ait de nouveau des
ids, ce qui est bien visible, comme toute autre dérive dans ce
pipeline.

## Quand ça s'exécute

`suprnova serve` déclenche `generate-types` à l'amorçage. Le flux par
défaut :

```
suprnova serve
  ├─ scanne src/ à la recherche des structs InertiaProps / Data   → inertia-props.ts
  ├─ scanne src/routes.rs à la recherche des définitions de route → routes.ts
  ├─ scanne lang/ à la recherche des ids de message Fluent        → lang-keys.ts
  ├─ démarre le backend
  └─ démarre Vite
```

Passez `--skip-types` pour sauter les deux. Relancez
`suprnova generate-types` manuellement chaque fois que vous changez du
code Rust pendant que le backend fait du hot-reload et que vous voulez
des déclarations fraîches sans redémarrer le serveur.

### Committez la sortie, et attendez-vous à un diff propre

`inertia-props.ts` est censé être committé - c'est ce qui permet à un
relecteur de voir un changement de contrat de props dans le même diff
que le Rust qui l'a causé, et ce qui évite que la CI ait besoin d'une
chaîne d'outils Rust pour typer le frontend.

La génération est déterministe : la même source produit une sortie
identique octet pour octet, sur n'importe quelle machine, quel que
soit l'ordre dans lequel les fichiers se trouvent sur le disque. Une
exécution qui ne change rien ne montre donc aucun diff, et tout diff
que vous voyez est un vrai changement de contrat. (Ça n'a pas toujours
été le cas - le tri s'amorçait depuis l'ordre d'itération du hash, et
chaque exécution rebattait les interfaces.)

Deux conséquences à intérioriser :

- **Rien d'autre ne doit modifier ce fichier.** Si un composant importe
  un type que le générateur n'émet pas, le prochain `generate-types` le
  supprime et le frontend arrête de compiler. La correction consiste à
  déclarer le type en Rust, pas à modifier la sortie à la main.
- **Une page sans route Rust n'a pas de type généré**, car il n'y a pas
  de struct `#[derive(InertiaProps)]` derrière elle. Déclarez ses props
  localement dans le composant jusqu'à ce qu'un handler existe pour les
  posséder.

## Pourquoi Suprnova diverge

Laravel ne fournit pas de génération de types pour Inertia, car PHP
est typé dynamiquement - il n'y a rien côté serveur d'où extraire un
contrat. La communauté Laravel d'Inertia a comblé le manque avec des
outils tiers (Laravel Typed Inertia, Wayfinder) qui lisent les
annotations PHPDoc ou DocBlock.

Suprnova a l'information de type à la compilation et sur le disque,
nous l'extrayons donc directement. Le même `#[derive(InertiaProps)]`
ou `#[derive(Data)]` qui contrôle la sérialisation JSON pilote aussi la
sortie TypeScript - une seule source de vérité, jamais désynchronisée
de ce que serde émet réellement.
