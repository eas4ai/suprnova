# コントリビューションガイド

Suprnovaは、MITライセンスの下でオープンソースです。最も価値のある貢献は、**優れたレポート**です。このプロジェクトはプルリクエストを受け付けていません。フレームワークはメンテナーによって最初から最後まで書かれており、あらゆる変更はメンテナーを通じて着地するため、サーフェス全体が一つの形を保ちます。これは意図的で恒久的な姿勢であり、1.0前の一時的な段階ではありません。

MITは、コードを自分自身でさらに発展させるために許可を得る必要が決してないことを意味します。**自由にフォークしてください**。独自の方向に成長するフォークは、対抗ではなく健全な結果です。

それが実際に意味することは：

- **バグ報告** - [GitHub Issue](https://github.com/eas4ai/suprnova/issues)経由で歓迎します。
- **機能リクエスト** - issue経由で歓迎します。実装ではなくユースケースを説明してください。多くの場合、既に計画された形（通常はLaravel相当のもの）があります。
- **ドキュメントのバグ** - issue経由で歓迎します。あるチャプターがAPIの存在を主張しているのに見つからない場合、それはドキュメントのバグです。どのチャプターで、何を期待していたかを教えてください。
- **セキュリティ問題** - 非公開で、メールで（下記を参照）。公開issueとしては決して報告しないでください。
- **プルリクエスト** - 受け付けていません。PRはこのチャプターへのポインタとともにクローズされます。代わりにissueを開いて修正がアップストリームに反映されるようにするか、フォークして自分で変更を持ち運んでください。

## すぐに修正されるバグ報告を書く

理想的なのは、新しいスキャフォルドからの再現手順です：

```bash
suprnova new repro-app --frontend vue --no-interaction
# …バグを示す最小の変更…
```

含めるべきもの：

1. **何をしたか** - 最小限にまで削ぎ落としたコマンドとコード
2. **何を期待していたか** - 一文で
3. **代わりに何が起きたか** - 実際の出力またはエラーを、そのまま貼り付けたもの
4. **バージョン** - フレームワークのタグ（`suprnova --version`、またはあなたの`Cargo.toml`の`tag =`）と、あなたのRustのバージョン（`rustc --version`）

失敗するテストは、文章よりもさらに良いものです。バグをフレームワークに対するテストとして表現できるなら、それをissueに貼り付けてください - たいていの場合、それが修正とともに着地するリグレッションテストになります。

## ソースからビルドする（レポートを調査するために）

issueを*提出する*ためにこれは必要ありませんが、ワークスペースに対して再現することは、レポートをより鋭くすることがよくあります：

```bash
git clone https://github.com/eas4ai/suprnova.git
cd suprnova
cargo check --workspace          # 全体を型チェックします
cargo test --workspace           # フルスイートを実行します（約3400件のテスト）
```

ワークスペースの構成：`framework/`（`suprnova`クレート）、`suprnova-cli/`（`suprnova`バイナリ）、`suprnova-macros/`（procマクロ）、`app/`（内部のドッグフードアプリ）、`crates/`（決済とWeb プッシュのアダプター）、そして`manual/`（このマニュアル）。

## コードに課される基準

コントリビューターのルールではありませんが、この基準を知っておくとレポートの精度を高めるのに役立ちます（ライブラリコードからのパニック、失敗モードのテストの欠落、あるいは`unwrap()`を強制するAPIは、常に報告する価値があります）：

- **完全な実装のみ。** TODOも、部分的なスキャフォルドもありません。修正は、それを固定するリグレッションテストとともに着地します。
- **パブリックサーフェスのコードは`Result`を返し、パニックしません。** Laravel流のインファリブルな（失敗しない）名前が提供される場所には、`try_*`の兄弟も一緒に提供されます。
- **環境ブートストラップの外では`unsafe`を使いません。** フレームワークには、非テストコードにちょうど2つの`unsafe`ブロックがあり、どちらも`config/env.rs::load_dotenv`にあり、どちらも`std::env::set_var` / `remove_var`をラップしています - これはedition 2024で`unsafe`になりました - そして、どちらも、それらが依存するブート時のシングルスレッド不変条件についてのSAFETYノートを伴っています。それ以外はすべてテスト専用です。他の場所で新たに`unsafe`を使うには、レビューで文書化された正当化が必要であり、ドライバー、ハンドラ、あるいはマクロ展開の中の`unsafe`は受け入れられません。
- **`cargo fmt`と`-D warnings`下のclippyが標準です。**

完全なエラー契約については、[エラー モデル](error-model.md)を参照してください。

## セキュリティ

セキュリティ問題は、**shawn@eas4ai.com**（プロジェクトのメンテナー）宛に非公開で報告してください。数日以内に受領を確認し、プライベートブランチで修正に取り組み、開示についてあなたと調整します。

修正が出荷されるまで、セキュリティ問題を公開のGitHub issueとして提出しないでください。

### 依存関係のアドバイザリー

`cargo audit`はリリースゲートで実行されます。あるアドバイザリーに利用可能な修正がなく、かつ脆弱なコードがデフォルトビルドで到達可能でない場合、それを監査の無視リストに追加できます - しかし、すべてのエントリには3つのものが必要であり、それらがなければゲートは失敗します：

```toml
# OWNER: name <email>
# EXPIRES: YYYY-MM-DD
"RUSTSEC-XXXX-XXXX",
```

- **オーナー**。例外が誰かに属するように。
- **有効期限**。それを過ぎると、そのエントリが理由を明記して更新されるか削除されるまで、ゲートは実行を拒否します。
- **書かれた到達可能性の論拠** - どの経路がそれを引き込むのか、そしてなぜデフォルトビルドがそれをリンクしないのか。

到達可能性の主張は、信用されるのではなく検査されます。あなたの論拠が「これはデフォルトでオフのフィーチャーの裏にある」というものであれば、リリースゲートは実際の依存ツリーを解決し、そのクレートがデフォルトのツリーには存在せず、オプトインしたツリーには存在することをアサートします。何も検証しない正当化を持つ例外は、誰かが依存関係を追加した最初のときに、静かに真実でなくなります。

無視することは、既知の問題を出荷するという決定です。そのように読めるべきです。
