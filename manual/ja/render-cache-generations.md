# RenderCache の世代

たいていのキャッシュは期限切れになります。RenderCache も期限切れになりますが、
期限切れは仕組みそのものではなく、最後の受け皿です。仕組みは**世代**です。
レンダリングが読み取ったデータの一つひとつがデータベースの中にカウンターを持ち、
レンダリングは自分が見たカウンターを保存し、書き込みは自分が変えたものの
カウンターを進めます。保存された表現は、それが見たカウンターがいまデータベースの
持つカウンターと一致し続けている間、最新です。自分のデータのために無効化の規則を
書く必要はありません。ごく普通の `model.save()` が、すでにその規則だからです。

この章は、その機構を外側から見ます。レンダリングは何に依存していると記録される
のか、その依存はどれくらい粗いのか、フレームワークに見えず、したがって無効化
できないものは何か、ヒットのときに整合性チェックはどう支払われるのか、複数の
リクエストが同じエントリを同時に欲しがったときにどれが再構築するのか、そして
「もう最新ではない」と「再構築された」のあいだの窓で訪問者は何を配信されるのか。
以下の主張はすべて、名前付きテストか、チェックインされた計測によって押さえられて
います。ドッグフードの例は `app/src/live/mod.rs` のルートで、
`app/tests/live_render_cache.rs` によって証明されています。

## レンダリングは何に依存していると記録されるのか

レンダリングが走っているあいだ、リクエストスコープのコレクターが、名前を挙げ
られる依存を 1 つずつ記録します。テーブルの読み取り、主キーによるレコードの
読み取り、クエリクラス、リレーション、設定のアイデンティティ、フィーチャー、
ロケール、ルート、そしてすべての表現が観測する、常に存在する `Broad` の
アイデンティティです。ORM とクエリビルダーを通じた読み取りは、自分自身を記録
します。あなたが書くものはありません。

`/live/todos` は、そのパターン全体が 1 つのハンドラーに収まっています:

```rust
pub async fn todos(_request: Request) -> Response {
    let result: Result<HttpResponse, FrameworkError> = async {
        let titles: Vec<String> = Todo::all()
            .await?
            .into_vec()
            .into_iter()
            .map(|todo| todo.title)
            .collect();
        html(&TodosView { count: titles.len(), titles })
    }
    .await;
    result.map_err(failed)
}
```

`Todo::all()` は `todos` テーブルを記録します。このハンドラーにもテンプレートにも、
セッションやサインイン済みの訪問者や翻訳を読むものはほかにありません。それが、
このルートを共有表現のままでいさせているものです。

## ごく普通の書き込みが無効化そのもの

`an_orm_write_invalidates_the_todos_document_through_generations` は、動作中の
アプリケーションを通してこのサイクル全体を歩きます:

1. 最初の `GET /live/todos` がレンダリングして公開します。
2. 2 回目はヒットです。ハンドラーには決して届かず、`Warning` を運ばず、何も
   スケジュールしません。
3. `POST /todos/random` が、アプリケーション自身のルートを通じて、ブラウザーが
   送るのと同じセッションと CSRF トークンを添えて、行を書き込みます。
4. 次の `GET` は `Warning: 110 - "Response is Stale"` とともに配信され、
   バックグラウンドの再構築をちょうど 1 つスケジュールします。5 分の新鮮な区間は
   始まったばかりなので、そのどちらをも説明できるのは、進んだ `todos` テーブルの
   世代だけです。
5. その再構築は本当に走ります。テストはレンダリングカウンターを（時間による待機
   ではなく状態バリアとして）待ち、テスト自身が投げたのではないレンダリングが
   起きるまでとどまります。
6. 書き込まれた行は、本当に一覧に載っています。これは**別の**手順であり、
   バックグラウンド再構築自身の出力についての表明ではないことは意図的です。
   再構築の公開は、アプリケーションから観測可能にする手立てのない瞬間に着地する
   ため、たまたまそれを捕らえたリクエストに対して表明すれば競合になるからです。
   そこでテストはまず L0 を落とし、もう一度レンダリングします。
7. そしてルートは、再公開されたエントリに対する素のヒットへ落ち着きます。

この一連の流れの中で、キャッシュキーはどこにも名指しされていません。
`DB::transaction` の内側での ORM の書き込みは、その同じトランザクションの内側で
自分の世代を進めるので、ロールバックされた書き込みは何も進めません。

## 無効化がどれほど狭いか

これは、キャッシュ対象のルートのサイズを見積もる前に知っておくべき、いちばん
重要なことです。

行を返す主キーによる 1 点の読み取りは、テーブルそのものではなく、その
**行**のアイデンティティとテーブルの**キーなし書き込み**アイデンティティを
記録します。`Model::find`、`Model::find_or_fail`、`Model::find_many` は、
それぞれハイドレートした行ごとに 1 つのレコードアイデンティティと、その
隣に 1 つのキーなし書き込みアイデンティティを観測します。そのため、
テーブルの他の場所への行単位の書き込みはエントリを最新のままにしますが、
一括の `update_all` や `delete_all`、`DB::table(..)` への書き込み、
テーブルへの生のステートメントは、依然としてエントリに届きます。行を
返さない 1 点の読み取りは、代わりにテーブルを観測します。欠けている行を
挿入することが、答えを変えることになるからです。

それ以外のすべての読み取りはテーブル粒度です。`Model::all`、あらゆる
`Builder` のターミナル、そしてあらゆるリレーションのロードはテーブル
全体を記録するため、そのテーブルへのどんな書き込みも、そこから読んだ
すべてのキャッシュエントリを無効化します。これは安全です。多すぎる
無効化しか起こせず、少なすぎる無効化は決して起こせません。そしてこれは
想定ではなく計測されています。
`framework/benches/render_cache_workloads.rs` の無効化ストームのワークロードは、
12 のレコードアイデンティティにまたがる 64 個のキーを公開し、1,000 回の書き込みを
駆動し、観測したファンアウトを
`crates/suprnova-live/benchmarks/render-cache-workloads-v1.json` に記録します
（抜粋です。記録されるオブジェクトは、バースト、スイープ、ヒット、再構築、
ステートメント、レイテンシーの各フィールドも運びます）:

```json
"invalidation_storm": {
  "keys": 64,
  "identities": 12,
  "writes": 1000,
  "every_write_invalidates_every_key": false,
  "point_read_invalidation_ratio": 0.09375,
  "rebuilds_per_write": 1.28,
  "final_bodies_coherent": true
}
```

`every_write_invalidates_every_key` が `false` なのは、1 点の読み取りが
もはやテーブル全体に依存しないからです。`point_read_invalidation_ratio` が、
注視する価値のある数値としてそれに取って代わりました。

これを前提に設計してください。アプリケーションが絶えず書き込むテーブルに支えられた
キャッシュ対象のルートは、鮮度ウィンドウが何と言おうと、絶えず再構築します。
編集者が何かを公開したときに変わるテーブルに支えられたキャッシュ対象のルートは、
何時間もじっとしています。テーブルより細かい粒度が必要なら、正直な答えは、
今日それは手に入らない、です。

## フレームワークに見えないもの

名前を挙げられない依存は無効化できません。そしてフレームワークは、そのうちどれの
保存を却下し、どれを通すのかについて意図的です。

**問答無用で却下されるもの。** `DB::select`、`DB::select_one`、`DB::scalar`、
`DB::select_on` を通じた生の SQL は、その文が読み取ったテーブルの名前を挙げられ
ないため、そのレンダリングは観測不能と印を付けられ、決して保存されません。
レスポンスは、毎回、正しく配信されます。
フレームワーク自身の RBAC のロールと権限のチェックは、自らが読み取る五つの
テーブル - `roles`、`permissions`、`role_permissions`、`model_roles`、
`model_permissions` - を明示しているため、それを評価するキャッシュ対象の
ルートは正確に観測され、通常どおりキャッシュされます。
`DB::table(..)` を通じた読み取りは自分のテーブルを把握しており、
通常どおりキャッシュされます。

**見えないもの、そしてあなたの責任。** `Request::header` を通じたリクエスト
ヘッダーの読み取りと `Config::get` の呼び出しは、いずれもコレクターに何も
見せないまま、レンダリングの生み出すものを変えます。そうしたルートには、
対応するバリエーションディメンションを宣言してください。ここに挙げた仕組
みのどれも、宣言漏れを代わりに検出してはくれません。

**グローバルスコープ。** Eloquent のグローバルスコープは、自分のフィルターが
何に依存しているかを宣言します。`ScopeDependency::Constant` を返す
`GlobalScope` は何も記録せず、キャッシュヒットを一切損ないません。デフォルト
である `ScopeDependency::PerRequest` は、スコープの `apply` が
`suprnova::live::current_tenant()`、`Auth::id()`、`Lang::locale()`
といった計測対象のアクセサを通じてその状態を読み取ることを要求します。
そのどれも読み取らないリクエストごとのスコープは、レンダリングを
`Uncacheable` に狭め、却下の中で自分自身の名前を挙げます。そのため、
見えないテナントフィルターは、訪問者同士に互いの行を見せてしまう代わりに、
あなたからキャッシュを奪います。

**フィーチャーフラグ。** `features` テーブルが保持しているフラグの読み取りは -
グローバルのデフォルトを含む、どのスコープキーであっても - そのフラグ自身の
世代を観測します。`DatabaseEvaluator::set_flag` は、新しい値が読み手に見え
るようになったあとにそれを進め、`DatabaseEvaluator::reload()` は、保存されて
いるルールが変わったすべてのフラグについてそれを進め、どのフラグだったのか
をキャッシュ対象のエバリュエーターに伝えます。テーブルが保持していないフラグ
は何も記録しません。そのレンダリングは、保存された状態ではなく `is_enabled!`
にコンパイルされたデフォルト値に依存していたということです。

**書き込み側。** 設定で RenderCache が有効になっていて、データベースに
RenderCache のマイグレーションが存在するすべてのプロセスは世代を進めるため、
キューワーカー、スケジュールされたタスク、コンソールコマンドによる書き込みは、
サーバーでの同じ書き込みが無効化するものと寸分違わず無効化し、
`RenderCache::bump_permission_version()` はそれらのどのプロセスからでも機能
します。`RENDER_CACHE_ENABLED=false` のプロセス、またはデータベースに
マイグレーションが存在しないプロセスは、何も世代を進めず、RenderCache の SQL
を一切発行しません。[RenderCache の運用](render-cache-operations.md)を参照して
ください。

## ヒットの費用

整合性チェックは、「バイト列がある」を「このバイト列は最新だ」に変えるものであり、
ヒットが行う唯一の仕事です。

ヒットは**ハンドラーも、ORM のクエリも、テンプレートも、シリアライザーも走らせ
ません**。そして本文のバイト列をコピーしません。サーバーがソケットへ書き込む
バイト列は、ストアが保持しているバイト列そのものであり、それは
`framework/tests/render_cache/bypass.rs` で値ではなくアドレスによって証明されて
います。残るのは、最新であることを証明するデータベースの読み取りだけであり、
それを何回払うかはポリシーの `CoherenceMode` が決めます:

| モード | 熱いヒット 1 回あたりの SQL 文数 | 何を信頼するか |
|---|---|---|
| `Authority`（既定） | ちょうど 1 | 台帳。ヒットのたびに読み直す |
| `Lease { max_age_ms }` | 0 | ローカルに付与された検証リース。期限切れまで |

`an_authority_mode_hit_issues_exactly_one_statement` は、権威モードを 1 回の
ラウンドトリップに押さえます。観測された世代と権威エポックは、2 回の読み取りでは
なく、1 つの `UNION ALL` の中で一緒に読まれます。
`a_lease_mode_hit_runs_nothing_and_issues_no_statement` はリースモードを 0 に
押さえます。キーが導出されたときのエポックは、リクエストごとに読まれるのではなく、
世代とともにリースされているからです。

エポック自体は、リクエストごとではなくプロセスごとに 1 回読まれます。
`the_epoch_is_read_once_at_first_use` は、新しいランタイムの最初のミスを、それ以外
は同一の 2 つ目のランタイムと比べ、最初のほうがちょうど 1 文だけ多く払うことを
測ります。それが、エポックリースを埋める 1 回の権威読み取りです。それより後の
すべてのリクエストは、そのために何も払いません。

## エポックが動くとき

`render-cache:epoch-advance` は緊急時の無効化であり、エポックはすべての
ルックアップキーに焼き込まれています。したがって、次に何が起きるかは、あなたが
どこに立っているかによります:

- **コマンドを実行したノードの上では**、まさに次のリクエストが新しいエポックを
  見ます。L0 は同じ瞬間に完全にクリアされ、キャッシュは即座に無効化されます。
- **別のノードの上では**、`Authority` モードのルートは、まさに次のヒットで学び
  ます。`Lease` モードのルートは次の権威の読み直しで学び、それは遅くとも
  `max_age_ms` 後です。

古くても配信可のウィンドウを持つルートは、再構築がリクエストの背後で走るあいだ、
動いたエントリを `Warning` 付きで一度だけ配信します。それを持たないルートは
フォアグラウンドで再構築し、要求した人はそれを待ちます。その違いこそ、古くても
配信可のウィンドウを宣言する理由のすべてであり、それはエポックの前進に限らず、
あらゆる移動に当てはまります。

`framework/tests/render_cache/middleware.rs` の 3 つのテストが、これらの経路を
名前で押さえています。
`an_epoch_advanced_by_another_node_reaches_an_authority_mode_route_on_its_next_hit`、
`an_epoch_advanced_by_another_node_reaches_a_lease_mode_route_when_its_lease_expires`、
そして
`an_epoch_advanced_by_another_node_serves_a_stale_servable_entry_once_then_rebuilds`
です。

## キーごとに再構築は 1 つ: シングルフライトと待機者

エントリが存在しないか、もう最新ではないとき、そこへ到着したリクエストが全部
レンダリングするわけではありません。**再構築コーディネーター**を通して受け入れ
られ、そのうちのちょうど 1 つが選ばれます:

- **リーダー**は、レンダリングして公開してよい唯一のリクエストです。自分の
  レンダリングの長さのあいだ、そのキーのリースを保持します。
- **待機者**は、リーダーがそれを保持しているあいだに同じキーへ到着した
  リクエストです。プロセス内で待ち、リーダーが手放したら、いま保存されている
  ものを評価し直してそれを配信します。待機者は待機そのものを信頼しません。
  リーダーのサイクルが公開に失敗した場合や、公開したものが待機者自身の鮮度
  チェックで死亡と判断された場合、待機者は見つけたものを配信するのではなく、
  自分もレンダリングします。`framework/tests/render_cache/middleware.rs` の
  `a_singleflight_waiter_never_serves_a_superseded_entry_as_fresh` が、その規則
  です。
- すでに `RENDER_CACHE_MAX_WAITERS`（既定 128）が待機している状態で到着した
  リクエストは、**バイパス**します。際限なく伸びるキューを育てるのではなく、
  レンダリングして何も公開しません。

`concurrent_misses_render_once_and_waiters_reuse_the_publication` は、ごく普通の
ケースをエンドツーエンドで証明します。同時に 2 つのミス、1 回のレンダリング、
同一の本文です。そして
`crates/suprnova-live/tests/render_cache_singleflight.rs` の
`one_leader_per_key_and_fence_with_bounded_waiters` は、コーディネーターに対して
直接その上限を証明します。待機者の上限を超えると、受け入れは `Bypass` と答えます。

1 つのキーに対する 2 つの公開が、コーディネーターの判断がどうであれ、両方とも
受理されることは決してありません。リーダーは自分のリースのもとで公開トークンを
鋳造し、ストアは書き込む前にそのフェンスを比べます。より古いエポック、あるいは
同じエポックでより小さいトークンは、負けます。それが、重複した*レンダリング*は
受け入れて安全なのに、重複した*公開*はそうではない理由であり、ノードをまたいだ
待機がまったく存在しない理由でもあります。別のノードが再構築中のキーは、ここでは
バイパスです。[RenderCache のデプロイメント](render-cache-deployment.md)を参照
してください。

## 再構築のあいだ何かを配信する

4 つの鮮度状態、`FreshnessPolicy` が設定する帯、そして古いレスポンスが運ぶ
`Warning` と `Age` は、[RenderCache の表現](render-cache-representations.md)で
定義されています。ここで重要なのは、世代の移動がエントリを早めにそれらの帯へ
入れるということです。動いたエントリは、実際の経年がどうであれ、**少なくとも**
その新鮮な区間の実効経過時間で評価されます。どの帯に落ちるかは、実際の経年が
決めます:

- 実際の経年が `fresh_ms + stale_servable_ms` 未満で、古くても配信可の
  ウィンドウを宣言しているルートの場合: 古くても配信可です。保存済みコピーが
  `Warning` 付きで一度配信され、再構築がリクエストの背後で走ります。それが、
  上の書き込みテストの手順 4 であり、5 分の新鮮な区間が始まったばかりの
  エントリの上での話です。
- 実際の経年がそれを過ぎ、しかしまだ死亡の境目に達していない場合:
  エラー時に配信です。リクエストはフォアグラウンドでの再構築を待ち、その再構築が
  失敗したときにだけ保存済みコピーを見ます。
- 古くても配信可のウィンドウをまったく持たないルート、およびすべての
  `PrivateCached` ルート（その死亡の境目は新鮮さの境目そのものです）では、
  移動は死亡です。リクエストはフォアグラウンドで再構築し、待ちます。

`stale_service_is_marked_and_rebuilt_in_the_background` は、書き込みではなく
クロックによって駆動される、同じ受け渡しを示します。`/live/todos` の 300,000
ミリ秒の新鮮な区間を過ぎ、その 60,000 ミリ秒の古くても配信可の内側では、訪問者は
手元のコピーを `Warning: 110 - "Response is Stale"` と `Age: 300` とともに
手渡され、再構築はちょうど 1 つスケジュールされ、その再構築は本当に走ります。

エラー時のフォールバックは、再構築を率いるリクエスト**と**、再構築が失敗した
リーダーの後ろにいる待機者の両方をカバーします。どちらも同じ方法で答えられます。
失敗ではなく、古いバイト列を `Warning` 付きで、です。
`framework/tests/render_cache/races.rs` は、それぞれの腕を別々に証明します。
`a_waiter_behind_a_failed_leader_is_served_the_stale_entry_it_was_waiting_on`
と `a_waiter_that_re_evaluates_onto_a_stale_on_error_entry_falls_back_to_it`
であり、2 つ目は差し戻しによっても証明されます。待機する側の腕から
フォールバックを外すと、その最後の表明が `200` から `500` へ変わるのです。

ステッチされたルートは例外であり、それは意図的なものです。`Composite` の
エントリが、エラー時のフォールバックで配信されることは決してなく、
バックグラウンドの再構築を引き起こすこともありません。再構築の失敗のあとに
保存済みシェルを配信すれば、ルート自身の認可チェーンが門番をする機会のなかった
リクエストに答えてしまいますし、バックグラウンドの再構築はリクエストの認可状態を
何も運ばないので、そのシェルは誰でもない人向けにページがレンダリングするものに
なってしまいます。ステッチされたルートでは、失敗した再構築自身の結果が、
クライアントの目にするものです。

## キャッシュ対象のルートは読み取り経路

リーダーのレンダリングはデータベースのトランザクションの内側で走り、PostgreSQL と
MySQL では `REPEATABLE READ` で開かれるため、記録される世代と読み取ったデータは
1 つのスナップショットを共有します。ここから 2 つの帰結が出てきます。

**書き込みを行う**キャッシュ対象ルートのハンドラーは、同じ行をめぐって同時に
書き込む他のトランザクションと競合し、PostgreSQL では、レンダリングの開始後に
別のトランザクションが変更した行を更新するハンドラーは、シリアライズ失敗に
遭遇します。キャッシュ対象のルートは読み取り経路として設計してください。

どんなトランザクションの外で行われた書き込み（単独の `model.save()`）も、まず
自分の行をコミットし、直後に続くトランザクションでその世代を進めます。両者の
あいだの瞬間は「新しいデータ、古い世代」です。それは余分な再構築 1 回の費用が
かかるだけで、古くなった内容を配信することは決してありません。

最後に、レンダリングが終わったあと、観測された依存とエポックは、レンダリング
自身のトランザクションの視界の外でもう一度読まれます。レンダリング中に動いた
ものがあれば、候補は公開されずに破棄されます。それが、レンダリングの途中で
着地した書き込みが、間違ったページではなく再構築 1 回の費用で済む理由です。

### Suprnovaが異なる設計を選んだ理由

Laravel のキャッシュはキーバリューストアであり、そのレスポンスキャッシュの
パッケージはその上に構築されているので、無効化はあなたが書くものです。
`Cache::forget` を呼ぶか、エントリにタグを付けてタグをフラッシュするか、その
モデルが供給していると自分が信じるキーを消すモデルオブザーバーを登録します。
そのどれもが、手で保守する対応づけであり、その失敗の仕方は無言です。誰も忘れる
のを思い出さなかったページは、TTL が尽きるまで配信され続けます。

Suprnova は向きを逆にします。レンダリングは読み取ったものを記録し、書き込みは
変えたものを進め、その 2 つは、あなたの頭の中ではなくデータベースの台帳で出会い
ます。忘れるべき `forget` の呼び出しはありません。その代償は、記録される依存が
行ではなくテーブルなので、忙しいテーブルはそれに依存するものを頻繁に再構築する
ことと、生の SQL を通じた読み取りが、誰も名前を挙げられない依存とともに
キャッシュされるのではなく保存を却下されることです。そのどちらも、目に見えて
計測されています。チェックインされたストームのワークロードにおけるファンアウトと、
自分の手元で `Age` ヘッダーが欠けていることによる却下です。顧客から知らされる
古いページではありません。
