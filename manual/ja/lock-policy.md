# ロック ポリシー

Suprnovaは、短命なPHPワーカーの群れではなく、単一の長寿命なTokioプロセスです。起動時にバインドしたプロセスグローバルなレジストリ、シングルトン、共有キャッシュはすべて、それに触れるあらゆるリクエストよりも長く生き続けます。これにより、`std::sync::Mutex` や `std::sync::RwLock` の使い方について、小さいながらも重大な変化が生じます - ガードを保持したままパニックすると、そのロックはプロセスの寿命が尽きるまで*ポイズニングされ*、次の呼び出し元はそれにどう対処するかを決めなければなりません。この章は、その判断のためのプロジェクト全体のポリシーです - 承認された2つのパターン、どちらを選ぶべきか、そしてなぜフレームワークやアプリケーションのコードで生の `.lock().unwrap()` を使うべきではないのか、を扱います。

## この章が存在する理由

Laravelでは、ポイズニングされたロックについて考える必要は一度もありませんでした。なぜなら、そもそも存在しなかったからです。PHPはshared-nothingです - 致命的エラーは1つのリクエストのプロセスを破棄し、次のリクエストは新しいプロセスで始まり、破損するようなメモリ内状態は何も生き残りません。Suprnovaはその正反対のやり方で動きます。プロセスは一度だけ起動し、レジストリはデータで満たされ、それらはバイナリの生存期間全体にわたって生き続けます。プロセスグローバルな `RwLock` の書き込みガードを保持したままパニックするハンドラは、そのロックを*ポイズニングされた*状態にしてしまいます - 誰かが明示的に回復させない限り、それ以降のすべての `.read()` と `.write()` は永遠に `Err(PoisonError)` を返し続けます。

Rustのデフォルトのイディオムである `.lock().unwrap()` は、その `Err` をパニックへと変換します。それは、コールスタックのどこか上位で、また別のポイズニングされたロックになります。そしてそれが、それに触れる次のサブシステムを道連れにします。1つの悪いリクエストが連鎖し、半ば死んだプロセスへとつながっていきます。

以下のポリシーは、その連鎖を防ぎます。

> **範囲。** これは、ポイズン状態を持つ `std::sync::Mutex` と `std::sync::RwLock` に適用されます。`tokio::sync` にある非同期版の親戚（`Mutex`、`RwLock`、`Semaphore`）はポイズニング*しません* - `tokio::sync::Mutex` のガードを保持したままパニックしても、ガードはきれいにドロップされ、次の `.lock().await` は成功します。あなたのホットパスが非同期であり、かつ同期コンテキスト（`Drop` の実装、フレームワークのコールバック、CLIのサブコマンド）からガードを取得する必要がないのであれば、Tokio版を優先してください。そうすれば、この問題そのものがなくなります。

## 承認された2つのパターン

フレームワーク内で `std::sync` のロックを保持している箇所はすべて、正確に2つのうちどちらかのパターンを使っています。あなた自身のコードでも、同じように選んでください。

### パターン1 - ポイズンをエラーとして返す

呼び出し元がすでに `Result<_, E>` を返しており、もう1つ `?` を足してもその形が変わらないのであれば、ポイズンをエラーとして表面化させ、リクエストをきれいに失敗させます。フレームワークは、内部の `pub(crate)` ヘルパー（`lock::read`、`lock::write`、`lock::lock`）を使っており、これらはポイズニングされたガードを `FrameworkError::internal("<context> lock poisoned")` に変換します。その際、呼び出し元が指定したラベルを埋め込むため、すべての呼び出し箇所でエラー自体をラップしなくても、ログを見ればどのサブシステムがポイズニングされたのかが分かります。

これらのヘルパーが体現しているパターンは、あなたのアプリケーションコードにインラインで書けるほど短いものです。

```rust
use std::collections::HashMap;
use std::sync::RwLock;
use suprnova::FrameworkError;

static FEATURE_FLAGS: RwLock<HashMap<String, bool>> = RwLock::new(HashMap::new());

pub fn enable(flag: &str) -> Result<(), FrameworkError> {
    let mut guard = FEATURE_FLAGS
        .write()
        .map_err(|_| FrameworkError::internal("feature flags lock poisoned"))?;
    guard.insert(flag.to_string(), true);
    Ok(())
}

pub fn is_enabled(flag: &str) -> Result<bool, FrameworkError> {
    let guard = FEATURE_FLAGS
        .read()
        .map_err(|_| FrameworkError::internal("feature flags lock poisoned"))?;
    Ok(guard.get(flag).copied().unwrap_or(false))
}
```

ハンドラの内部では、`is_enabled(...)?` は、他のあらゆるフレームワークエラーが使うのと同じ `FrameworkError → HttpResponse` の経路を通って収束します - クライアントは `{"message": "Internal Server Error"}` というサニタイズされた500を受け取り、構造化ログにはラベル付きのポイズンメッセージが記録され、リクエストIDは最初から最後まで保持され、プロセスの残りの部分はトラフィックを提供し続けます。変換経路の全体については、[エラーハンドリング](errors.md) の章を参照してください。

このパターンを使うのは、次のような場合です。

- 呼び出し元がすでに `Result` を返している場合（失敗しうる操作の大半がそうです）。
- ポイズニングされたロックが、サブシステムの本物の、回復不能な失敗を表している場合 - フォールバック先となるような、まともな「部分的な真実」が存在しないケースです。
- 次にそのサブシステムに触れたときに、オペレーターがログの中でポイズンを*目にできる*ようにしたい場合。ラベル付きのメッセージは、あなたが残す捜査の手がかりです。

フレームワークの通知ディスパッチャー、メール送信、メーラブルレジストリ、DBイベントリスナー、そして名前付き接続レジストリは、いずれもこのパターンを使っています。これらのいずれかでパニックが起きても、そのレジストリに触れる次のリクエストで500として表面化するだけで、それ以外はすべて動き続けます。

### パターン2 - `into_inner()` でその場で復旧する

呼び出し元のシグネチャが失敗しうるもの*ではない*場合（`bool` のルックアップ、ホットパスのルーティングチェック、リクエストライフサイクルが依存している経路）、あるいは共有状態が部分的な書き込みの後でも構造的に安全に使い続けられる場合は、ガードを復旧させてそのまま処理を続けます。

```rust
use std::collections::HashMap;
use std::sync::RwLock;

static ALLOWED_INCLUDES: RwLock<HashMap<&'static str, Vec<&'static str>>> =
    RwLock::new(HashMap::new());

pub fn allows(dto: &str, field: &str) -> bool {
    ALLOWED_INCLUDES
        .read()
        .unwrap_or_else(|e| e.into_inner())
        .get(dto)
        .map(|fields| fields.contains(&field))
        .unwrap_or(false)
}

pub fn register(dto: &'static str, fields: &'static [&'static str]) {
    let mut guard = ALLOWED_INCLUDES
        .write()
        .unwrap_or_else(|e| e.into_inner());
    guard.insert(dto, fields.to_vec());
}
```

`PoisonError::into_inner()` は、ポイズニングされていてもガードを返します。それ以降の読み取りと書き込みは通常どおり進みます - `is_poisoned()` への問い合わせに対してはロックがポイズニングされたままになりますが、データの流れは復旧します。

フレームワークは、このパターンを `data::registry`（すべてのJSON:APIレスポンスで読まれるインクルードセットの許可リスト）、`auth::manager`（名前付き認証プロバイダーのマップ）、`app::paths`（解決済みパスのキャッシュ）、メールとイベントのテスト用フェイク、そしてconfig内の読み込み済み環境変数キーのマップで使っています。これらはいずれも、呼び出し元の誰も返すべき `Result` を持たないか、あるいは状態が追記専用であり、構造的に安全に使い続けられる場所です。

このパターンを使うのは、次のような場合です。

- 呼び出し元のシグネチャが素のもの（`bool`、`&str`、保存された値のクローン）であり、それを `Result` に変更すると、すべての呼び出し元 - 時にはフレームワークのすべてのサブシステム - に伝播を強いることになる場合。
- 共有状態が部分的な書き込みに耐えられる場合。追記専用のマップやキャッシュが典型的な形です - 最悪のケースはエントリの欠落や陳腐化であり、それは呼び出し元がすでに処理しています（デフォルトで拒否する、プライマリにフォールバックする、再計算する）。
- ホットパスが十分に頻繁に実行されるため、それ以降のすべてのリクエストでエラーを返すことが、動作を劣化させるよりも運用上悪くなってしまう場合。

## 両者をどう使い分けるか

判断基準を一文で言うと: **ポイズン後の状態を使った場合の最悪のケースが、実害を伴う誤った答えであるならエラーに変換し、呼び出し元がすでに処理しているエントリの欠落や陳腐化であるなら、その場で復旧します。**

順を追って見ていきましょう。

1. **呼び出し元のシグネチャは `Result<_, E>` でしょうか。** もし違うなら、その場で復旧するしかありません - `bool` に `Result` を追加することは、たいていプロジェクト全体に及ぶリファクタリングになり、ポイズンという小さなエッジケースのためにやる価値はありません。
2. **もし書きかけの値が観測された場合、アプリケーションは実世界に影響を及ぼす誤った判断を下すでしょうか。** 誤った顧客に課金する、認可されていないincludeを許可する、誤ったテナントにアクセスを許可する - これは「はい、エラーに変換する」です。「この名前は登録されているか」に対して `false` を返し、プライマリプールにフォールバックする - これは「いいえ、その場で復旧する」です。
3. **その状態は追記専用か、あるいは再登録に対して自然にべき等でしょうか。** はいであれば、その場での復旧は安全です。書き込みが以前の値に依存する状態機械の遷移であるなら、破損を重ねてしまわないよう、エラーへの変換を優先してください。

迷ったときは、エラーに変換してください。500を返すリクエストは、あなたが直せる大きな信号ですが、静かな誤った答えはそうではありません。

## `.lock().unwrap()` に決して手を伸ばさないこと

禁じられている形です。

```rust
// 決して書かないこと - 下の呼び出しグラフのどこかで1度パニックが起きれば
// この行はロックをポイズニングし、以降のすべての呼び出し元が
// そのポイズンをまた別のパニックへと変えてしまいます。
let mut guard = SOMETHING.lock().unwrap();
```

`.expect("…")` も、より親切なメッセージが付いているだけで同じことです。どちらも、ポイズニングされたロックの `Err` を、リクエストライフサイクルの `AssertUnwindSafe(...).catch_unwind()` というネットが捕捉して500に変換するパニックへと変えてしまいます - そのネットは*最後の防衛線*であって、上記の判断を省略してよいという許可証ではありません。公開されているフレームワークのAPIおよびアプリケーションコードは、承認された2つのパターンのうちどちらかを選ばなければなりません。

`std::sync` のロックに対して `.unwrap()` が許容される、2つの例外があります。

- **ポイズニングに到達したことをあえて確認したいテストのセットアップ** - `framework/src/lock.rs` 自身のポイズン誘発ヘルパーは、パニックするスレッドの内部で意図的に `.unwrap()` を使っています。
- **すでに失敗しているポイズニング操作のエラーパス** - `poison_rw(...)` のスレッドの内部にいる時点で、パニックそのものが*目的*なのです。

そのどちらにも当てはまらないのであれば、上のセクションからパターンを選んでください。

## 自分の関数が `bool` を返す場合はどうすればよいか

これは `ConnectionRegistry::has` が置かれている状況そのものです。これは、エグゼキューターのリードレプリカ振り分けのホットパス上にある `bool` のルックアップであり、`if ConnectionRegistry::has("read_replica").await { … }` のようにインラインで呼ばれます。これを `Result<bool, FrameworkError>` に広げてしまうと、エグゼキューター内のすべての呼び出し元に `?` での伝播を強いることになり、単に「はい/いいえ」だけを求めているルーティングの判断の中に、内部エラーのコードパスを持ち込んでしまいます。

その場で復旧するパターンが、これに対応します - `false` を返し、呼び出し元のフォールバックロジックを働かせます（ここではエグゼキューターがプライマリプールに戻りますが、これはどのみち安全な挙動です）。それでもオペレーターがこの状況を確実に把握できるよう、ポイズンが最初に観測された時点で、一度限りの `tracing::warn!` を発行します。

```rust
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::RwLock;
use std::collections::HashMap;

static REGISTRY: RwLock<HashMap<String, ()>> = RwLock::new(HashMap::new());
static POISON_WARNED: AtomicBool = AtomicBool::new(false);

pub fn has(name: &str) -> bool {
    match REGISTRY.read() {
        Ok(g) => g.contains_key(name),
        Err(_) => {
            // 競合に対して安全です。最初に観測した1つだけがログを出します。
            if !POISON_WARNED.swap(true, Ordering::SeqCst) {
                tracing::warn!(
                    target: "myapp::registry",
                    "registry lock poisoned - `has({name})` degrading to false",
                );
            }
            false
        }
    }
}
```

この `swap` ベースのゲートが重要です - `RwLock` のポイズンは一度発生すると自然には解消しないため、このゲートがなければ、それ以降のすべての呼び出しが警告を再発火させ、あなたのログを溢れさせてしまいます。このゲートがあれば、プロセスごと・レジストリごとに、警告はちょうど1回だけになります。そして同じレジストリ上の、対応する `Result` を返すゲッター（`get`、`register`）は、ルックアップの成功を*実際に必要とする*何かが現れた次の瞬間に、そのポイズンを表面化させます。これによりオペレーターは両方の信号を得られます - 早い段階での「何かがおかしい」という警告と、リクエストが本当にそのレジストリに依存した瞬間のハードな500です。

## フレームワークがすでに保護しているもの

フレームワークが所有する状態に対して、このポリシーを自分で適用する必要はありません - すでに整備されています。具体的には次のとおりです。

- 名前付き接続レジストリ（`ConnectionRegistry::register`、`get`、`has`）は、書き込みと `Result` を返す読み取りにおいて、ポイズンを `FrameworkError::internal` に変換します。`has` は、一度だけ警告するゲートとともに `false` へと縮退します。
- 通知ディスパッチャーとファクトリーレジストリ、メーラブルレジストリ、メール送信、メールのメモリキャプチャ、そしてDBイベントリスナーは、いずれもポイズン時に `FrameworkError::internal` を返します。
- `data::registry` のインクルード許可リスト、`auth::manager` のプロバイダーマップ、`app::paths`、読み込み済み環境変数キーのキャッシュ、そしてインメモリのテスト用フェイクは、いずれもその場で復旧します。

これらのサブシステムに、その公開API（`Notification::send`、`Mail::send`、`Auth::user`、`DB::connection`、JSON:APIのレスポンス経路）を通じて触れる限り、ポイズニングされたフレームワークのロックはきれいな500として表面化します - あなたの呼び出し箇所でパニックが起きることは決してありません。

## Suprnovaが異なる設計を選んだ理由

Laravelにロックポリシーが存在しないのは、長寿命な共有状態を持たないからです。各PHPリクエストは、自分自身のプロセス、自分自身のメモリ、すべてのシングルトンの自分自身のコピーを手に入れます。ポイズニングされうるメモリ内レジストリは存在せず、「次のリクエスト」が前のリクエストから損傷を引き継ぐという概念も存在しません - ランタイムがまっさらな状態を保証します。

SuprnovaはTokioの上に構築されており、これはまさに、PHPが排除している長寿命な共有状態を与えてくれます。安価なWebSocket、インメモリキャッシュ、再構築のコストを払わずに済む接続プール - これらはすべて、単一のリクエストよりも長く生きるプロセスグローバルなレジストリを必要とします。その能力こそが、このスタイルのアプリのためにRustへ移行することの意義そのものです（フレームワークの全体的な動機については[はじめに](introduction.md)を参照してください）。その能力を持つことの代償は、パニックしたスレッドが共有状態をガードされた状態のまま残したときに何が起きるかを、今や考えなければならないということです - なぜなら、残すべき共有状態が*実際に存在する*からです。

この2パターンのポリシーは、その能力を保ちながら代償を取り除く、最小の答えです。状態を使い続けても安全な場所ではその場で復旧し、誤った答えよりもきれいな500の方がよい場所ではエラーに変換します。どちらの選択肢でも、プロセスの残りの部分はトラフィックを提供し続けます。どちらも、パニックしたunwrapが上位のサブシステムを道連れにするのを待ち構えているような状態を残しません。

これは、到達不能なキャッシュやレートリミットのバックエンドに対してフレームワークが適用している[フェイルオープンかフェイルクローズかの判断](rate-limiting.md)と同じ形です - デフォルトではなく、呼び出し箇所での明示的なポリシー選択です。至るところが非同期であることが、あなたに長寿命な状態を与えます。フレームワークは、それを誠実に保つための指針を与えてくれます。

## 次のステップ

- [エラーハンドリング](errors.md) - `FrameworkError::internal` が、クライアントが受け取るサニタイズされた500へとどのように変わるか。ラベル付きのポイズンメッセージは、構造化ログの中に保存されたままになります。
- [サービス コンテナ](container.md) - このポリシーが保護しているプロセスグローバルなレジストリが実際にどこに存在するか、そしてtask-local/thread-localのスコープが、なぜテスト同士のバインディングの継承を防いでいるのか。
- [リクエスト ライフサイクル](lifecycle.md) - *最後の手段*としてのunwrapを捕捉して500に変換するパニック境界（`execute_chain_safely`）について。これにより、安全網が実際に何をしているのか、そしてそれがなぜ上記のポリシーを省略してよい理由にはならないのかを、正確に理解できます。
- [レート リミット](rate-limiting.md) - ポイズニングではなく*到達不能*になりうるバックエンドのための、並行する `BackendErrorPolicy` の話。明示的に選ぶという原則は同じですが、失敗のモードが異なります。
- [テスト](testing.md) - `TestContainer::fake` とthread-localなコンテナ層が、どのように並行するテスト同士がお互いのレジストリを汚染し合うのを防いでいるか。これは、ポイズン処理の話に対するテスト時の対応物です。
