# 画像

Suprnovaは、Laravelの形をした画像パイプラインを出荷します。ハンドラの中でそれを組み立て、望む操作をチェーンし、バイト列、レスポンス、あるいは保存されたファイルを手渡す終端で仕上げてください。

```rust
use suprnova::{Image, OutputFormat, Response, handler};

#[handler]
pub async fn thumbnail() -> Response {
    Ok(Image::from_path("storage/photos/hero.jpg")
        .cover(320, 320)
        .to_format(OutputFormat::WebP)
        .quality(80)
        .to_response()
        .await?)
}
```

このハンドラは、JPEGをデコードし、320x320のボックスを埋め、はみ出した分を中央から切り取り、WebPへエンコードし、`Content-Type: image/webp` を伴う `200` を返します。

このサブシステムは、デフォルトで有効な `media` フィーチャーの背後、`suprnova::media` にあります。あなたが普段手を伸ばすもの - `Image`、`OutputFormat`、`ImageDriver`、`ImageConfig` - はすべてクレートルートへ平らに再エクスポートされているため、必要なインポートは `use suprnova::Image;` です。モジュール名が意味の上で複数形なのは意図的です。OxideAVに支えられた音声と動画の表面も、ここに置かれることになるからです。

アップグレードするなら、以前 `Image` と呼ばれていたアップロードのバリデーターが `ImageFile` になったことに注意してください。これにより、素の名前がこのパイプラインの型のために空きました。これは、バリデーションのルールが `ImageFile`、加工の型が `Image` であるLaravelを映しています。バリデーターについては[リクエスト](requests.md)を参照してください。

## パイプラインはレイジーです

`Image` の構築は、何も読まず、何もデコードしません。操作は自分自身を記録するだけで、ソースが開かれるのは終端が走るときだけです。したがって、これには何のコストもかかりません:

```rust
use suprnova::Image;

let pipeline = Image::from_disk("uploads", "avatars/42.png").resize(64, 64);
```

まだ何もディスクに触れていません。`Image` は `Clone` であり、クローンは結果を共有するのではなく、自身のソースからパイプラインを走らせ直します。

2つのコンストラクターはイーガーでなければならず、そのドキュメントにもそう書かれています: `from_upload`（アップロードの一時ファイルはリクエストより長くは生きません）と `from_stream`（ストリームは一度しか消費できません）です。

## 構築

| コンストラクター | ソース | イーガー? |
|---|---|---|
| `Image::from_bytes(bytes)` | `Into<Bytes>` を満たすもの何でも | いいえ |
| `Image::from_path(path)` | ファイルシステム | いいえ |
| `Image::from_disk(disk, path)` | `Storage` のディスク | いいえ |
| `Image::from_upload(&file).await?` | `UploadedFile` | はい |
| `Image::from_stream(stream).await?` | `Stream<Item = io::Result<Bytes>>` | はい |

`from_stream` は、収集し*ながら* `IMAGE_MAX_ALLOC_BYTES` を強制するため、終わりのないストリームは、すでにメモリを埋め尽くした後に発覚するのではなく、途中で断ち切られます。

## 操作

| メソッド | 効果 |
|---|---|
| `resize(w, h)` | 正確な寸法にします。アスペクト比は無視します |
| `resize_width(w)` / `resize_height(h)` | 片方の寸法を指定し、もう片方はアスペクト比から導きます |
| `scale(w, h)` | アスペクト比を保ったままボックスの中に収めます。**決して拡大しません** |
| `scale_width(w)` / `scale_height(h)` | 指定した片方の寸法を上限として縮小します。決して拡大しません |
| `crop(w, h, x, y)` | 矩形を切り出します。画像の外へ出る場合はエラーになります |
| `cover(w, h)` | ボックスをちょうど埋め、はみ出した分を中央から切り取ります |
| `contain(w, h)` | アスペクト比を保ったままボックスの中に収めます。パディングはしません |
| `rotate(degrees)` | 任意の角度で時計回りに回転させ、収まるようキャンバスを広げます |
| `flip_vertically()` / `flip_horizontally()` | Laravelの `flip` と `flop` です |
| `blur(amount)` | ガウシアンブラー、`0..=100`。`0` は何もしません |
| `sharpen(amount)` | アンシャープマスク、`0..=100`。`0` は何もしません。`50` が古典的な強さです |
| `grayscale()` | 彩度を落とします。綴りはLaravel流です |
| `to_format(format)` | 出力のコンテナを選びます |
| `quality(q)` | エンコードの品質。`1..=100` にクランプされ、デフォルトは `70` です |

意味をなさない値は、拒否されるのではなくクランプされます: `blur(500)` は `100` を、`quality(0)` は `1` を記録します。画像の外へ出るクロップは、クランプではなく本当のエラーです。誰かのクロップの枠を黙って動かすほうが、そう伝えるより悪いからです。

`rotate` は任意の角度を取ります。90度の倍数は、リサンプリングなしの正確な軸に沿った経路を通ります。それ以外はバイリニアであり、どのピクセルも切り取られないようキャンバスが広がります。露出した隅は、出力フォーマットがアルファチャネルを持つ場合には透明になります。

## 終端メソッド

どの終端も `async` であり、`Image` を消費し、デコード、変換、エンコードの作業をブロッキングスレッドの上で走らせるため、ランタイムを止めることは決してありません。ソースのI/Oはその跳躍より前に起こるため、遅いディスクがブロッキングワーカーを占有することもありません。

| 終端 | 返すもの |
|---|---|
| `to_bytes()` | エンコードされたファイルの `Vec<u8>` |
| `to_response()` | 正しい `Content-Type` を伴う `HttpResponse` |
| `save(path)` | ファイルシステムへ書き込みます |
| `store(disk, path)` | `Storage` のディスクへ書き込みます |
| `dimensions()` | **処理後の**画像の `(width, height)` |
| `mime_type()` | **処理後の**画像のメディアタイプ |
| `dominant_color()` | 平均の色。`#rrggbb` として |

`dimensions()`、`mime_type()`、`dominant_color()` はいずれも、ソースではなく仕上がった画像を記述します - Laravelと同じ契約です。mimeタイプを尋ねるだけでもパイプラインは走ります。実際には生成できない画像についてタイプを報告することは、呼び出し元が後になってはじめて気づく嘘だからです。

```rust
use suprnova::{FrameworkError, Image, OutputFormat};

async fn describe() -> Result<(), FrameworkError> {
    let banner = Image::from_path("hero.png").resize(1200, 400);

    // ソースの寸法ではなく、(1200, 400) を読みます。
    let (width, height) = banner.clone().dimensions().await?;
    println!("{width}x{height}");

    let accent = banner.to_format(OutputFormat::Jpeg).dominant_color().await?;
    println!("{accent}");

    Ok(())
}
```

## フォーマット

今日読み書きできるのは5つのフォーマットです: **PNG、JPEG、WebP、GIF、BMP**。

| フォーマット | 読み込み | 書き出し | 品質の指定 |
|---|---|---|---|
| PNG | はい | はい | 無視されます（可逆） |
| JPEG | はい | はい | 尊重されます |
| WebP | はい | はい（可逆） | 今日のところ効果はありません |
| GIF | はい | はい | 無視されます（パレット） |
| BMP | はい | はい | 無視されます（可逆） |

AVIFは、まだ読むことも書くこともできません。それが依存する自社製のAV1エンコーダーがまだ公開されておらず、常に失敗する `OutputFormat::Avif` を出荷することは、フレームワークが守れない約束になるからです。それは、その公開とともに、新しいenumのバリアント1つだけを伴って到着します。

GIFの出力は、エンコードの前にFloyd-Steinbergのディザリングを伴って最大256色へパレット量子化されるため、写真をソースにしてもエラーになるのではなくきれいに変換されます。

WebPは可逆で書き出されるため、`quality()` は今のところWebPの出力には効果がありません。サイズと品質のトレードオフを調整したいときはJPEGを使ってください。

## ストレージ

`from_disk` と `store` は、登録されているどの `Storage` のディスクに対しても働くため、リサイズして保存し直す往復がローカルのパスに触れることは決してありません:

```rust
use suprnova::{FrameworkError, Image};

async fn make_web_copy() -> Result<(), FrameworkError> {
    Image::from_disk("uploads", "originals/42.png")
        .scale(1024, 1024)
        .store("uploads", "web/42.png")
        .await
}
```

ディスクの登録については[ファイルシステムとストレージ](filesystem.md)を参照してください。

## デコードの上限

デコードは、敵対的な入力が害をなす場所です: わずか数キロバイトが40000x40000のキャンバスを宣言し、サーバーにそのための6ギガバイトの割り当てを求めることができます。Suprnovaは、何かを割り当てる前にそれを拒否します。

| 変数 | デフォルト | 用途 |
|---|---|---|
| `IMAGE_MAX_DIMENSION` | `16384` | 幅と高さのピクセル数の上限 |
| `IMAGE_MAX_ALLOC_BYTES` | `268435456`（256 MiB） | デコード後のRGBAのフットプリントと、ソースファイル自体のサイズの上限 |
| `IMAGE_MAGICK_TIMEOUT_SECS` | `30` | 1回のImageMagickの起動に対する実時間の上限（`magick` ドライバーのみ） |

フレームワークは、入力自身のヘッダー - 数十バイトで、割り当てはありません - をパースし、宣言された寸法を読み、デコーダーが構築されるより前に大きすぎる入力を拒否します。同じ上限はリサイズの目標値にも適用されます。`resize(50_000, 50_000)` は、その数字が攻撃者から来ようとタイプミスから来ようと、同じだけ割り当てるからです。

上限に触れたことは、4xxの形をした `FrameworkError::param` になります。大きすぎる入力はサーバーの落ち度ではなく、クライアント側の問題だからです。

範囲外の設定は、起動を失敗させるのではなく警告を伴ってクランプされます: `IMAGE_MAX_DIMENSION=0` は、アプリケーション内のあらゆる画像を拒否してしまい、それは誰も設定するつもりのなかったものだからです。

### 設定できない境界が1つある

WebPは、実際のデコード後のサイズをキャンバスのヘッダーではなく、最も内側のビットストリームのチャンクの中で宣言します。そのため、フレームワークはそれを見つけるためにコンテナを歩きます。その歩みは**レベルあたり4096チャンク**で止まり、ネストは**2レベルの深さ**までたどります。そのどちらかを超えるファイルは、測られるのではなく端から拒否されます。

測るのではなく拒否するのは意図的です。ファイルの末尾まで到達しなかった歩みから数字を報告することは、十分な量の詰め物のチャンクを積めば回り込めるゲートになってしまうため、終えられなかった歩みには返せる答えがありません。

どちらの数字も調整できず、どの `IMAGE_MAX_*` 変数もそれらに影響しません - エラーメッセージが「設定されている」と言わずにそう述べるのは、まさに、誰かが午後をまるごと費やして `IMAGE_MAX_ALLOC_BYTES` を引き上げ、何も変わらないのを眺めることがないようにするためです。実際には、意図的に敵対的なファイルだけがそこに近づきます: 300フレームのアニメーションは余裕をもって通り、4100フレームのものは通りません。

## バックエンド

Laravelと同じく、画像の表面は2つのドライバーであり、`IMAGE_DRIVER` で選びます。

| ドライバー | 値 | 必要なもの | 読めるもの |
|---|---|---|---|
| OxideAV | `oxideav`（デフォルト） | なし | PNG、JPEG、WebP、GIF、BMP |
| ImageMagick | `magick` | ホスト上のImageMagick 7 | ホストのデリゲートが提供するもの |

### `IMAGE_DRIVER=oxideav`

デフォルトです。純粋なRustで、[OxideAV](https://github.com/OxideAV)のコーデックファミリーの上に構築されています: ネイティブライブラリはなく、インストールするものも、設定するものもありません。ほとんどすべてのアプリケーションにとって正しい選択であり、スキャフォルドされたアプリが手にするものです。

### `IMAGE_DRIVER=magick`

オプトインです。ホストにインストールされたImageMagick 7のバイナリを走らせ、画像をstdinから流し込み、結果をstdoutから読み戻します - 一時ファイルはありません。バイナリ名は `IMAGE_MAGICK_BINARY` から来て、デフォルトは `magick` です。バイナリが見つからない場合は、黙ってフォールバックするのではなく、最初の使用時に明確なエラーになります。

純粋なRustのドライバーが運ばない入力フォーマットが必要なときに、これを選んでください - よくあるのはHEICです。その代償はホスト側の依存関係です: オペレーターがImageMagickとそのデリゲートをインストールし、そのライセンスを引き受けます。フレームワークはどちらの場合も、ネイティブなものを何もリンクせず、何もコンパイルしません。

引数は常に、プロセスへそのまま手渡される固定の配列であり、シェルの文字列になることは決してありません。そして、数値の引数はすべて、すでに検証済みのフィールドから整形されます。ユーザーの入力が到達できる引数の位置は、1つもありません。

フレームワークが入力を認識できるとき、デコーダーはコマンドラインの上で名指しされます - 素の `-` ではなく `png:-` です。これは重要です: 素の `-` を渡されると、ImageMagickは手渡されたバイト列からコーダーを選ぶため、マジックがMVGやMSLだと言っているファイルは、あなたのアプリケーションが何を受け付けているつもりであったかにかかわらず、*スクリプト*として読まれます。コーダーを固定することで、ラベルの間違ったファイルは、別のものになるのではなく失敗するようになります。

**フレームワークが名指しできない入力は、今もあなたの `policy.xml` に依存します。** それらのフォーマットを読むことこそがこのドライバーの存在理由であるため、その経路ではコーダーを固定できません。`IMAGE_DRIVER=magick` の下で任意のアップロードを受け付けるなら、ホストのImageMagickのポリシーを堅くしてください - 最低限、`MVG`、`MSL`、`URL`、`HTTPS`、`EPHEMERAL`、`TEXT` のコーダーを無効にしてください。

このドライバーの下では、デコードの上限は2度強制されます。フレームワークがパースできる5つのフォーマットについては、上記のヘッダーの検査がプロセスを起動する前に走ります。それ以外のすべてについては事前のパースが不可能であるため、すべての起動が、同じ設定から導かれたImageMagick自身の `-limit` フラグを、実時間の `-limit time` を含めて運びます。

そのフラグだけでは話は終わりません。ImageMagickはそれを自身のリソースモニターで強制しますが、そのモニターが働き出すより前にデリゲートの内側で動かなくなったプロセスは、決してそれに引っかからないからです。そのためSuprnovaは、自身の期限も保持します: `IMAGE_MAGICK_TIMEOUT_SECS`（に加えて、IM自身の上限が先に発火するための数秒の猶予）を過ぎると、プロセスグループを - 起動したプロセスだけでなく、デリゲートも含めて - killし、パイプで待つのをやめます。したがって、停止したデリゲートがワーカーのスレッドを固定してしまうことはありません。プロセスグループの中に留まるデリゲートは、それとともに死にます。グループから抜け出したもの、あるいは `kill` のバイナリを持たないホストでは、リクエストより長く生き延びることがあります - そうした残存プロセスにこそ、ホスト側のプロセス監視が備えられています。

killは、リクエストがそれを引き起こしたものであっても、4xxではなく5xxの `FrameworkError::internal` として表面化します。何かが画像の経路を、killが必要なほどひどく詰まらせたのであり、それはオペレーターの目に触れるサーバーエラーの監視に属します - それをクライアントのエラーに分類することは、ここでページャーを鳴らす価値のある唯一の状態を、しまい込んでしまうことになります。

## カスタムドライバー

`ImageDriver` が拡張点です: `&[u8]` が入り、`Vec<u8>` が出て、コーデックの型が境界をまたぐことはありません。

```rust
use suprnova::{FrameworkError, ImageDriver, ImagePipeline};

struct MyDriver;

impl ImageDriver for MyDriver {
    fn process(
        &self,
        contents: &[u8],
        pipeline: &ImagePipeline,
    ) -> Result<Vec<u8>, FrameworkError> {
        // `contents` をデコードし、`pipeline.transformations` を再生し、
        // `pipeline.quality` で `pipeline.format` へエンコードします。
        todo!()
    }

    fn dimensions(&self, contents: &[u8]) -> Result<(u32, u32), FrameworkError> {
        todo!()
    }

    fn dominant_color(&self, contents: &[u8]) -> Result<String, FrameworkError> {
        todo!()
    }

    fn name(&self) -> &'static str {
        "mine"
    }
}
```

最初の画像が処理されるより前に、`bootstrap()` の中でインストールしてください:

```rust
use suprnova::FrameworkError;

pub fn register() -> Result<(), FrameworkError> {
    suprnova::media::set_default_driver(Box::new(MyDriver))
}
```

適合するドライバーは、デコードのために割り当てる前に、設定された `ImageConfig` の上限を強制します。フレームワークはデコード後のバッファを決して見ないため、ドライバーに代わってそれを行うことはできません。

### より多くのフォーマットへ届く

組み込みの5つでは足りないのなら、あなたが引き受ける手間の多さのおおよその順に、3つの道があります:

1. **組み込みの `magick` ドライバー。** `IMAGE_DRIVER=magick` を設定してください。フォーマットの幅はホストのImageMagickのデリゲートから来て、管理すべきビルドの依存関係はありません。
2. **libvipsを包むカスタムドライバー。** 例えば [libvips-rust-bindings](https://github.com/olxgroup-oss/libvips-rust-bindings) クレート（MIT）を介するものです。libvipsはNodeの `sharp` の背後にあるエンジンで、非常に幅広いフォーマットに対応し - JPEG、JPEG XL、TIFF、PNG、WebP、HEIC、AVIF、PDF、SVG、GIFなど、さらにImageMagickへの委譲も含みます - ストリーミングの性能も強力です。libvipsのCライブラリをバインドするため、あなたのアプリはビルド時と実行時にlibvipsをインストールし、その依存関係を引き受けます。まさにそれが、これがフレームワークの中ではなくトレイトの背後に属する理由です。実務上の注意が1つ: このバインディングの `VipsImage` はスレッドセーフではありませんが、`process()` の呼び出しごとに1枚の画像というドライバーの形が、すでにそれを受け止めています。
3. **任意のCLIツール。** `magick` ドライバーと同じやり方で包んでください: `std::process::Command` へ手渡す固定の引数の配列、stdinから入り、stdoutから出る画像のバイト列、そして決してシェルの文字列にはしないことです。

Suprnovaが是認するのはトレイトの境界であって、その背後の特定の依存関係ではありません。その背後に何を置くかはあなたの判断であり、そのライセンスもまたそうです。

## テスト

このサブシステムは、ディスク上のフィクスチャを必要としません - デコードとエンコードが往復できるようになれば、それ自身がフィクスチャの製造装置です:

```rust
use suprnova::{FrameworkError, Image, OutputFormat};

/// 1x1のバイトリテラルのフィクスチャを、テストが必要とするどんなサイズにも育てます。
async fn fixture(source: &[u8]) -> Result<Vec<u8>, FrameworkError> {
    Image::from_bytes(source.to_vec())
        .resize(4, 2)
        .to_format(OutputFormat::Png)
        .to_bytes()
        .await
}
```

デコードの上限を狭めるテストは、直列化しなければなりません。上限はプロセス全体で共有されるため、並行して走る別のテストが、狭められた上限の下でデコードしてしまうからです。

### Suprnovaが異なる設計を選んだ理由

**デフォルトのドライバーにHEICはなく、その理由は特許です。** HEICの中にあるコーデックであるHEVCは、特許に縛られています - とりわけAccess Advanceのプールです。Suprnovaはネイティブライブラリを一切インストールしないため、組み込みのデコーダーは純粋なRustでなければならず、その露出を直接抱え込むことになります。そして、信頼できる唯一の純粋なRustのデコーダーはAGPL-3.0/商用のデュアルライセンスであり、これはアプリケーションごとの法的な義務であって、MITのフレームワークが誰かをデフォルトで巻き込んでよいものではありません。

どちらのフレームワークもHEICをホストの調達の問題にしています。Suprnovaの版は、動く部品が1つ少ないだけです。LaravelのデフォルトのドライバーであるGDはHEICをまったく読めず、そのImagickの経路は、libheifのデリゲートがシステムのImageMagickのバイナリとPHPの `imagick` 拡張の**両方**にコンパイルされていることを必要とします。Suprnovaでは、デフォルトのドライバーはHEICを読まず、`IMAGE_DRIVER=magick` は、ホストのImageMagickがlibheifのデリゲートを運んでいればいつでもそれを読みます - あいだに拡張の層はありません。したがって、HEICの取り込みは今日でも動きます: パッケージマネージャーからlibheif付きのImageMagickをインストールし、環境変数を切り替えてください。ライセンスは、それが属する場所、すなわちホストに置かれます。

`oxideav` ドライバーがHEICのファイルに出会ったときは、汎用の「サポートされていないフォーマット」を返すのではなく、名指しでそう述べ、この章を指し示し、前に進む2つの道の両方を挙げます。

**AVIFは保留であって、見送りではありません。** ロイヤリティフリーであり、私たちが求めている現代的なフォーマットの答えです。ただ、自社製のAV1エンコーダーがまだ公開されていないだけです。それまでのあいだは、WebPが現代的なフォーマットの経路です。

**base64やURLのコンストラクターはありません。** Laravelの `ImageManager` には `->read($base64)` と `->read($url)` があります。`from_bytes` は、[HTTPクライアント](http-client.md)を含め、そのバイト列を作ったものが何であれ、それと合成できます。そして、URLの取得を画像のサブシステムの外に保つことは、そのタイムアウト、リトライ、SSRFのポリシーを2か所ではなく1か所にまとめておくことになります。

**`from_stream` はイーガーで、上限を伴います。** Laravelのcontentsはレイジーなクロージャです。ストリームは再生できないため、こちらは構築の時点で汲み出され、その過程でバイト数を `IMAGE_MAX_ALLOC_BYTES` に対して数えます。

**`contain` はパディングをしません。** 画像をボックスの中に収めて、そこで止まります。背景の上にレターボックス表示することはありません。背景が必要なら、自分で合成してください。

**リサイズはバイリニアのリサンプリングを使います。** バックエンドのフィルターの一式には、最近傍とバイリニアが出荷されており、自然画像に対してはバイリニアがその文書化されたデフォルトです。

**画像は決してシリアライズできません。** Laravelは `__serialize` で例外を投げますが、Suprnovaは単にそれを実装していません。パスかディスクのキーを保存して、パイプラインを組み立て直してください。
