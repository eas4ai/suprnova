# RenderCache の運用

見えないキャッシュは、信頼できないキャッシュです。RenderCache は、保存されたページを一度も印字することなく、運用担当者の 2 つの問いに直接答えます。
**このノードはこのキーのもとで何を保持していて、それはまだ最新なのか。**そして
**どうすればすべてを止められるのか。**3 つ目の問い、「このルートは、そもそも保存済みコピーから配信されているのか」には、コマンドではなくテレメトリと `Age`
ヘッダーを通じて答えます。その問いは 1 つのエントリについてではなく、トラフィックについてのものだからです。コンソールコマンドが 2 つ、テレメトリのカウンターが
9 つ、境界付きのディスクスイープが 1 つ、そして緊急のレバーが 1 つあります。

この章は、その運用の表面です。コマンドと、それが正確に何を印字し、何を見られるのか。カウンターと、その閉じた結果の集合。ファイル階層がどうディスクを回収するのか。単に応答しているのではなく本当にキャッシュしていることをテストが証明するように、キャッシュ対象のルートをどうテストするのか。データベースの復元が必要とする複数ノードの手順を含め、何かがおかしいときに何をすべきか。そして、キャッシュ自身の性能はどう計測され、その数字が正直なところどれだけの価値を持つのか。コマンドの例は、`app/tests/live_render_cache.rs` の
`the_operator_commands_inspect_without_a_body_and_advance_the_epoch` が、このリポジトリ自身のコンソールのエントリーポイントを通じて駆動しているものです。

## 2 つのコンソールコマンド

どちらも隠しコマンドで、フレームワークが登録し、ほかのコマンドと同じようにプロジェクトの `console` バイナリを通じて到達できます。どちらも、保存された本文や生の依存アイデンティティを印字することは決してありません。

```bash
cargo run --bin console -- render-cache:inspect rk1.<43 base64url characters>
cargo run --bin console -- render-cache:epoch-advance
```

**`render-cache:inspect <key>`** は、保存されている 1 つのエントリの姿を報告します。その表現クラス、その `body_bytes`、そのほかのメタデータ、そしてその横に現在の権威エポックです。これにより、いま見ているエントリがまだ生きた権威なのか、それともすでに足元から期限切れになっているのかを判別できます。キーが自分には見えない何かを指しているときは `no entry (current epoch: {epoch})` と印字し、解析できないキーや、ランタイムがインストールされていない場合には、成功を報告するのではなく失敗します。

**これはこのプロセスのプロセス内 L0 だけを読み、ほかは何も読みません。**
`RenderCache::inspect` はキーを L0 の中だけで引き、L1 階層を参照することは決してありません。データベースプロファイルや Redis プロファイルでは、それが意味を持ちます。ほかのノードが、あるいは再起動前のこのノード自身が公開した、
`suprnova_render_entries` や Redis の中で生きているエントリは、このプロセスが起動してからそれを配信していない限り、ここでは `no entry` と印字されます。この報告は「このノードがメモリに持っているもの」として読み、「このデプロイが保存しているもの」として読んではいけません。L0 の占有量と現在のエポックを報告する `RenderCache::store_inspection` についても同じです。

キーは、ルックアップ自身が使うテキストです。`rk1.` に 43 文字の base64url が続いたもので、これはアプリケーションのログとテレメトリが表示できるものです。それは何かの二度目のハッシュではないので、運用担当者が手にしたキーは、ちょうど 1 つのエントリを名指しします。

本文を含まないというこの主張は、単に述べられているだけでなく検査されています。テストは実際に配信されたドキュメントを取り、それを行に分割し、その**すべての**
自明でない行が inspect の報告の印字内容に含まれていないことを要求します。

**`render-cache:epoch-advance`** は緊急時の無効化です。権威エポックを進め、
`epoch advanced to {epoch}` と印字します。エポックはすべてのルックアップキーに焼き込まれているので、これは、列挙するものも削除するものもないまま、保存済みエントリを手の届かないところへ移します。テストは、印字される行と、それから重要な帰結を表明します。このコマンドのあと、そのルートは再びレンダリングします。

**それを実行したノードの上では**効果は即座です。コマンドはそのプロセスのエポックリースを手放し、そのプロセス内階層をクリアするので、まさに次のリクエストは新しいエポックのもとでキーを導出し、何も見つけません。（この最後の一節が成り立つのは、エポックが前へしか動かないあいだ、つまりごく普通の場合です。データベースの復元後は、進めた値がそのデプロイで以前に使われたものである可能性があるので、下の「データベースを復元する」を参照してください。）
**それ以外のどのノードの上でも**、台帳は動いていますが、そのプロセスはまだ自分の古いリース済みエポックと自分の L0 を保持しており、次の権威読み取りで追いつきます。`CoherenceMode::Authority` のもとでは即座に、
`CoherenceMode::Lease` のもとでは遅くとも `max_age_ms` 後です。各ノードでこのコマンドを実行するか、実行しなかったノードを再起動してください。下の「データベースを復元する」に、完全な手順とその裏にあるテストがあります。

キャッシュされた内容に何か問題があり、個々のエントリの期限切れを待てないとき、そしてキャッシュされたページの表示内容を変えたジョブのあとに、これを使ってください（[RenderCache の世代](render-cache-generations.md)の「既知の欠落」を参照）。

## 権限の変更

`RenderCache::bump_permission_version().await?` は、アプリケーションが手で行う唯一の無効化の呼び出しであり、本当のところ運用コマンドではありません。それは、サインイン済みのユーザーが何を許可されているかを変えるコード経路に属します。これは、プリンシパルでキー付けされたすべてのレンダリングが参照する永続化された世代を進め、再起動を越えて保持され、ロールの変更を実行するトランザクションがある場合にはそれに参加します。これがないと、権限が変わったばかりのユーザーは、以前の権限セットのもとでキャッシュされた内容に一致し続けてしまいます。

## テレメトリ

閉じた 9 つのカウンター名があり、そのどれもが階層、プロバイダー、バックエンドを名指ししません:

| カウンター | 属性 |
|---|---|
| `suprnova.render_cache.lookups` | `outcome`。`outcome="declined"` のときは `reason` も |
| `suprnova.render_cache.hits` | `outcome` |
| `suprnova.render_cache.publications` | なし |
| `suprnova.render_cache.rebuilds` | なし |
| `suprnova.render_cache.stitch.assemblies` | `outcome` |
| `suprnova.render_cache.stitch.slots` | `outcome` |
| `suprnova.render_cache.stitch.nested` | `outcome`、`cause` |
| `suprnova.render_cache.hints` | `outcome` |
| `suprnova.render_cache.epoch_rewinds` | なし |

`lookups` と `hits` は、8 つの結果からなる同じ閉じた集合を運びます:

- `l0`、`l1`: プロセス内階層または共有階層から配信された新鮮なエントリ。
- `conditional`: `If-None-Match` が一致し、`304` で答えられた新鮮なヒット。
- `stale`: 即座に配信された、古くても配信可のエントリ。または、フォアグラウンドの再構築が失敗したあとのエラー時のフォールバック。
- `miss`: 何も見つからなかったか、エラー時に配信するための再構築が進行中か、死亡したエントリ。
- `bypass`: 宣言されていないクエリパラメータ、解決できない宣言済みバリエーションディメンション、または使い切られた待機者の一覧。
- `moved`: レンダリング後の読み直しで、依存かエポックが変わっていたことが判明した。候補は破棄され、公開はされなかった。
- `declined`: レンダリングが保存できませんでした。理由は下記 38 個のうちのいずれかで、`outcome` の隣にある `reason` 属性に載って運ばれます。
  `reason` が出るのは `outcome="declined"` のときだけで、それ以外の結果には一切運ばれません。この理由は、実際に却下したその分岐において型付きの値から計算されるのであって、あとからレスポンスを見て再構成されるのではありません。つまり、実際にレンダリングを拒んだ契約の名前がそのまま出ます:

  - 適格性（`policy.eligibility`。エンジン自身の `DeclineReason` を映し取ります）: `policy_uncacheable`、`method`、`status`、
    `streaming`、`sets_cookie`、`unsafe_header_name`。
  - 観測（コレクターのレポートとトランザクション内でのレジャー読み取り）:
    `observation_overflowed`、`ledger_read_failed`、`handler_not_begun`。
  - `Uncacheable` へ絞り込まれた分類: `session_value_read`、
    `secret_context_read`、`undeclared_context`。
  - Live ドキュメントの事実: `identity_bound_without_stitching`、
    `invalid_stitch_capture`、`no_store_intent`、
    `unresolvable_seed_deadline`。
  - キーに関する不変条件（レンダリング自身の観測が、ルックアップキーがすでに組み立てられていた値と一致するかどうか）:
    `unreasoned_private_class`、`principal_undeclared`、
    `principal_divergent`、`tenant_undeclared`、`tenant_divergent`、
    `locale_undeclared`、`locale_divergent`。
  - 公開: `seed_deadline_elapsed`、`unsafe_header_value`、
    `composite_capture_invalid`、`composite_slot_count_mismatch`、
    `composite_too_many_slots`、`composite_digest_mismatch`、
    `composite_empty_slot`、`composite_slot_not_found`、
    `composite_slot_ambiguous`、`composite_nested_unauthorizable`、
    `composite_nested_wider_class`、`composite_nested_longer_freshness`、
    `composite_nested_depth_exceeded`、`composite_nested_cycle`、
    `composite_nested_unresolvable`。

`hits` が増えるのは `l0`、`l1`、`conditional`、`stale` のときだけです。
`publications` が数えるのは、ストアが「公開した」と答えたときだけで、フェンスされた試みや拒否された試みは決して数えません。`rebuilds` は、起動されたバックグラウンド再構築 1 つにつき 1 を数えます。

アイランドステッチの 2 つのカウンターは、それぞれ独自の集合を運びます。組み立てについては `assembled` と `fail_document`、スロットについては
`rendered`、`omitted`、`fallback`、`failed` です。

`suprnova.render_cache.stitch.nested` は、名前付きの内側のキャッシュ済みセグメント自身の結果を、アイランドのスロットの結果とは区別します。
`Segment::Nested` の解決を試みるたびに 1 増えます。`outcome` 属性が取り得るのは `resolved`、`omitted`、`fallback`、`failed` のいずれか 1 つだけです。`cause` 属性が取り得るのは `none`（`outcome="resolved"` のときだけ使われます）、`fetch_failed`、`version_mismatch`、`length_mismatch`、
`depth_exceeded`、`cycle`、`unauthorized` のいずれか 1 つだけです。どちらの属性も、キーやルート名、アイデンティティダイジェストを運ぶことは決してありません。失敗した、または劣化したセグメントは、それを含むグラフが宣言したポリシー（`FailDocument`/`Omit`/`Fallback`）を通じて必ず解決され、これはアイランドのスロット自身の失敗とまったく同じです。`outcome="failed"`
（`FailDocument` ポリシーによるもの）はドキュメント全体の組み立てを放棄し、ルート自身の未キャッシュのハンドラへフォールバックします。

`epoch_rewinds` が数えるのは検出であって、エントリではありません。ノードが、権威自身のエポックより上に刻印されたエントリまたはリース済みエポックに出会うたびに 1 増え、そのつど台帳のエポックをその刻印より先へ引き上げ、自分自身の
L0 をクリアします。データベースの復元のあとに 0 でない値が出ることは、復元が気づかれたというシグナルです。それ以外のときに 0 でない値が出ることは、誰も意図していない理由で権威が後退したことを意味します。

`hints` は、このノードが階層 2 の Pub/Sub チャネルで扱った信頼できる世代ヒントを数え、受け取ったメッセージごとに 1、購読が終わるごとに 1、そして発行キューが満杯で送れなかった通知ごとに 1 増えます。ここで唯一、デプロイが自分の選択で恒久的にゼロのままにできるカウンターです。ヒントは Redis
プロファイル、または `RENDER_CACHE_HINTS=redis` が有効にしないかぎりオフであり、オフのノードはオンのノードとまったく同じものを配信します。その
`outcome` 属性は、`applied`
（メッセージが、このノードの検証リースが観測しているダイジェストを名指し、該当するリースがすべて短縮された）、`ignored_unknown_key`（このノードがリースを持っているものを何も名指さなかった。このノードがまったく読めないメッセージもここに含まれます）、`dropped_over_bound`（64 個を超えるダイジェストを運んでいたため、切り詰めではなく丸ごと破棄された。切り詰められたヒントは、黙って間違っているヒントだからです）、`subscriber_dropped`（このノードの購読が、遅れを取ったか接続が失敗したために終了し、再確立中である）、
`dropped_publish_queue_full`（このノードに通知すべき前進があったのに、自身の発行キューが満杯だったため、そのメッセージは、それを生んだ書き込みを待たせる代わりに破棄された。通知できなかったメッセージ 1 件につき 1 回）のうち、ちょうど 1 つの値を取ります。どの属性も、ルート、キー、依存関係の識別子を運ぶことは決してありません。

ヒントにできるのは、このノードがすでに保持している検証リースを短くすることだけです。リースを延長することも、作り出すことも、世代台帳の代わりを務めることもできず、ヒットは今も必ずその台帳を読みます。したがって `subscriber_dropped` の上昇が意味するのは、このノードが可能な時期よりも遅く再検証しているということ -
最悪でもリース自身の `max_age_ms` と同じ遅さであり、それはそのルートがすでに宣言している陳腐化の上限です - であって、整合性チェックが拒否したはずのものが配信されているということでは決してありません。

**`declined` の割合が高いことが、アラートを立てる価値のあるシグナルです。**
それは、あなたが組み込んだルートが、正しくレンダリングして配信しながら、決して保存されていないことを意味し、しかもレスポンスはどちらの場合も同じに見えます。いちばん速いローカルの確認は、2 回続けてリクエストを送ることです。2 回目に
`Age` ヘッダーがなければ、何も保存されていません。

## ディスクの衛生

スイープが必要なのはファイル階層だけで、しかもそれはほとんど自分でスイープします。

`FileRenderStore` は、`RENDER_CACHE_L1_DIR` の直下に平らに、キーごとに 1 つのファイルを保存します。エントリが死亡するのは、公開からの経過時間が、それが公開されたときの保持期間に達したとき、またはそのフェンスエポックが現在のエポックより古いときです。保持期間は、生きた鮮度チェックが使うのと同じクラスを意識した死亡の境目から来るので、私的なエントリのファイルは公開のものより早く退役し、スイープが鮮度チェックと、エントリが本当に死んでいるかについて食い違うことは決してありません。

`sweep` は 1 回の呼び出しにつき最大 64 エントリを、公開の古い順に取り除き、まだ残りがあるかどうかを返します。これは公開 256 回ごとに自動で走るので、健全なディレクトリは手をかける必要がありません。`RenderCache::sweep()` は、そうしたいときに明示的にそれを駆動し、1 回の呼び出しの上限より大きい滞留分は、1 回の長い走査でブロックするのではなく、あとの起動をまたいで捌かれます。

このスイープが**そうではない**ものが 2 つあります:

- **エポックの前進は L1 に触れません。** それは L0 を完全にクリアします。それは照合すべき相手のないプロセス内メモリだからです。そして、エポック前のすべてのファイルは、スイープが回収するまでディスク上に残ります。それは正しさの問題ではなくディスクの衛生上の問題です。ファイルはすでに、ルックアップからは到達できません。
- **データベース階層には自動のスイープがなく**、`RenderCache::sweep()` を通じてのみ回収されます。Redis 階層にはスイープが不要です。そこに保存されるすべてのエントリは期限を運び、Redis が自分でバイト列を回収します。

公開はクラッシュに対して安全です。一時ファイルを書き、それを fsync し、対象の上へリネームし、親ディレクトリを fsync するので、読み手が目にするのは、以前の完全なファイルか、新しい完全なファイルのどちらかだけです。オープン時に、ストアは残された一時ファイルと、フレームの検査に失敗したファイルを取り除き、破れた書き込みを、永久に汚染されたエントリではなく自己修復するものとして扱います。

## キャッシュ対象のルートをテストする

キャッシュ対象のルートが正しく応答することを表明するテストは、そのレスポンスがストアから出てきたのか、新しいレンダリングから出てきたのかにかかわらず合格してしまいます。すべての主張は、保存済みエントリが実際に配信されたときにしか生まれないものに対して行わなければなりません。それを行うパターンが 4 つあり、このリポジトリ自身のドッグフードのテストは 4 つすべてを使っています。
`app/tests/live_render_cache.rs` と、`app/tests/live_support/mod.rs` のハーネスです。

**1. キャッシュのハンドラ側でレンダリングを数える。** 数えるミドルウェアを
`RenderCache::install` の*あと*に登録します。登録は追加なので、それは
`RenderCacheMiddleware` よりハンドラに近いところへ着地し、キャッシュが答えたリクエストは、それを呼ぶ前に戻ります:

```rust
let router = app::live::routes_with_render_cache_with_config(routes::register(), config)
    .await
    .expect("install the routes and the RenderCache middleware");
// After the install, so it only sees requests the cache forwarded.
render_counter::register();
```

`render_counter::renders()` の 2 回の読み取りの差は、キャッシュが避けられなかったレンダリングの回数そのものであり、それ以外の何ものでもありません。同一の本文や
`Age` ヘッダーとは違います。どちらも、キャッシュ以外の正直な説明がつきうるからです。`an_orm_write_invalidates_the_todos_document_through_generations` のヒットに関するすべての表明は、これに乗っています。自分が投げていないレンダリング（バックグラウンドの再構築）を待つときは、スリープではなく、カウンター自身のバリアである `wait_until_renders_at_least` を使ってください。

**例外は `PublicShellStitched` のルートで、しかもそれは小さな例外ではありません。** ステッチされたヒットは、意図的にルートのチェーン全体を通して転送されます。その認可ガードはもう一度走らなければならず、そのチェーンの末尾にある Live
の完了ミドルウェアだけがそのヒットを配信するからです。インストールのあとにグローバルに登録された、数えるミドルウェアは、ルート自身のチェーンの外側に座っているので、ステッチされたヒットでも、ミスのときとまったく同じように到達されます。そうしたルートでは、このカウンターは「ハンドラは走らなかった」という主張をまったく担えません。

代わりに、ストアが何を保持しているか、配信されたドキュメントが何からできているか、そしてそれがどれだけ古いかに対して表明します。それが `the_dashboard_is_stitched_per_principal_from_one_shared_shell` のやっていることです。保存されるエントリは、期待どおりのスロット数を持つ
`EntryKind::Composite` であること（`inspect_route_for_test`）、2 人のプリンシパルのドキュメントが、アイランドのタグでは異なり、それ以外のどこでも異ならないこと、そして 2 人目のプリンシパルへのレスポンスが、シェルが公開されてから経過した秒数ちょうどの `Age` を報告することです。

最後のものが、このテストの拠って立つ証拠であり、ストアから配信されたことの局所的な証明の、厳密な形です。`Age` ヘッダーそれ自体は、この章が上のほうで警告した弱い信号です。レンダリングもまた 1 つ付けるからです。ただし 0 で。数値のほうは弱くありません。レンダリングはレスポンスとエントリを同じ瞬間に公開するので、時計がどれだけ進んでいても、レンダリングされたレスポンスは 0 を報告します。一方、組み立ては、組み立て元となったシェルの古さを報告します。テストは、読み取るものが偶然ではなく厳密になるよう、ルートの鮮度ウィンドウの十分内側で調整可能な時計を進めます。

レスポンスは `Cache-Control: private, no-store` も運びますが、それはあるがままに読んでください。これは、このクラスでスロットを持つルートが運ぶディレクティブであり、シェルを公開するレンダリングでも、そのあとのすべての組み立てでも同じように固定されます。この値は、どの経路がバイト列を生み出したかではなく、バイト列が何を保持しているかに従うからです。「スロットを持つ」がここでの肝心な言葉です。スロットが 0 個の `Composite` は、代わりにこのクラスの私的な `max-age` を保つので、このディレクティブが語るのは、アイランドを持つルートについてであって、持たないルートについてではありません。そのテストはヒットに対して `renders() == before + 1` を表明し、それが失敗ではなく正直な読み方である理由を、自分自身の注記の中で述べています。

**2. エントリを読み戻す。** 2 つのファサードの呼び出しは、ごく普通の公開 API
です。`RenderCache::store_inspection()` は L0 の占有量、バイト数、現在のエポックを報告し、`RenderCache::inspect(key_text)` は 1 つのエントリの、本文を含まないメタデータを報告します。それらと並んで、フレームワークは隠れたテスト用の継ぎ目を公開しています。`#[doc(hidden)]` であり、アプリケーションの API と取り違えられないよう `_for_test` という名前が付いています:

| 継ぎ目 | テストに何を与えるか |
|---|---|
| `RenderCache::key_for_route_for_test(pattern, params, login)` | ミドルウェアが**エポック 1**で導出するキーのテキスト。マイグレーションがシードする値 |
| `RenderCache::key_for_route_at_epoch_for_test(pattern, params, login, epoch)` | 同じもの。ただし名指ししたエポックのもとで |
| `RenderCache::inspect_route_for_test(pattern)` | そのエポック 1 のキーの L0 エントリ。クラス、種類、ステータス、`body_bytes`、スロット |
| `RenderCache::inspect_l1_for_test(pattern, params, login)` | 同じもの。ただし設定された L1 階層から |
| `RenderCache::clear_l0_for_test()` | L0 を空にし、L1、エポック、コーディネーターには手を触れない |

エポックが重要なのは、それがキーの一部だからです。`key_for_route_for_test` はエポック 1 をハードコードしているので、エポックを進めたテストは（このノードでであれ、台帳を通じて別のノードでであれ）、`key_for_route_at_epoch_for_test` で新しいエポックを名指ししなければなりません。そうしないと、何も公開されていないキーを引くことになります。

`the_public_document_is_a_hit_whose_seed_still_promotes` は `store_inspection` と
`inspect_route_for_test` を使って、エントリが存在すること、そして宣言されたクラスのもとで保存されていることを表明します。
`the_database_profile_serves_a_hit_through_the_sql_stores` は
`inspect_l1_for_test` を使い、それから `clear_l0_for_test` を使います。あとのリクエストが、メモリからではなく L1 から出てきたことを証明する方法は、これしかありません。

**3. 待つのではなくクロックを動かす。** ランタイムが読むクロックは
`RenderCacheConfig` の上で設定でき、`from_env` からは決して設定されないので、鮮度の帯を必要とするテストは自分のクロックをインストールします:

```rust
let clock = Arc::new(AdjustableTestClock::new(unix_now_ms()));
// Bound to its own name first: passing `Arc::clone(&clock)` inline leaves
// the compiler inferring the trait object as the clone's return type.
let for_runtime = Arc::clone(&clock);
let config = RenderCacheConfig::from_env()?.with_clock_for_test(for_runtime);
// ... install through the application's own configuration seam, then:
clock.advance_ms(300_001);
```

`AdjustableTestClock` は `suprnova::live::testing` から来ており、`unix_now_ms`
はハーネス自身の壁時計の読み取りなので、調整可能なクロックは、プロセスのほかの部分が同意しないような時間原点からではなく、システムクロックのある場所から始まります。（それはクロックのゼロ点であって、この章がそれ以外の場所でこの語に込めている権威エポックではありません。）ハーネスはこの組を
`setup_app_with_clock` と `advance_clock_ms` として包んでおり、2 つ目は、起動がシステムクロックを取ってしまったときに、黙って何もしないのではなくパニックします。
`stale_service_is_marked_and_rebuilt_in_the_background` がそのテストです。

**4. SQL 文を数える。** ハンドラは飛ばしたのに、ヒットのたびにデータベースを参照するキャッシュは、ハンドラ側のどのカウンターも満たしつつ、なおラウンドトリップの費用を払っています。`DbConnection::observe_statements_for_test` は
SeaORM のメトリックコールバックを自前のカウンターへ向け、それはプールの上でも、そこから始まったすべてのトランザクションの上でも、文を見ます:

```rust
// Immediately after connecting, before the connection is cloned or bound
// into the container: installing needs sole ownership of the pool, and the
// call reports `false` rather than counting nothing silently.
let installed = conn.observe_statements_for_test(|| {
    STATEMENTS.fetch_add(1, Ordering::SeqCst);
});
assert!(installed, "the statement observer needs an unshared connection");
```

このコールバックは、その文について何も告げられません。SQL のテキストも、バインドされた値もです。回数こそがすべてだからです。
`framework/tests/render_cache/bypass.rs` は、まるごとこのパターンの上に書かれています。`a_lease_mode_hit_runs_nothing_and_issues_no_statement` はリースモードのヒットを 0 文に押さえ、
`an_authority_mode_hit_issues_exactly_one_statement` は権威モードのヒットを
1 文に押さえ、`the_epoch_is_read_once_at_first_use` は 2 つのミスを互いに比べて、エポックがランタイムごとに 1 回の読み取りの費用であることを示します。

守る価値のある習慣が 2 つあります。ハーネスは、手で組み立てたルーターではなく自分のアプリケーション自身の設定の継ぎ目を通して起動してください。そうすれば、テストはサーバーと同じルート、ポリシー、ミドルウェアの順序をインストールします。そして、時間による待機を決して足さないでください。上のバリアはすべてカウンターの上の状態バリアであり、それがこれらのテストを不安定ではなく再現可能にしているものです。

## 何かがおかしいとき

- **ページが、古いとわかっている内容を表示している。** そのルートがそもそも保存しているかを確かめてください（2 回リクエストして `Age` を探します）。設定で RenderCache が有効になっていて、データベースに RenderCache のマイグレーションが存在するすべてのプロセスは、自分自身の書き込みについて世代を進めるため、キューワーカー、スケジュールされたタスク、コンソールコマンドは、サービングプロセスと同じ世代を無効化します。書き込みを行ったプロセスに実際に RenderCache が有効化・マイグレーション済みかどうかを確認してください。そうでないプロセスは何も進めません。
  `CoherenceMode::Lease` の下では、古くなったが保存済みのエントリーは、即座にではなく `max_age_ms` 以内に自然に追いつきます。それ以外の場合は、
  `render-cache:epoch-advance` を実行してください（ノードごとに。最後の項目を参照）。
- **キャッシュされると思っていたページが、`Age` ヘッダーを一度も運ばない。**
  それは失敗しているのではなく、却下されています。まず `declined` のルックアップにある `reason` ラベルを読んでください。それは、上記の「テレメトリ」にある閉じた集合の中から、レンダリングを実際に拒んだ契約を名指しします。そのうえで、分類によって絞り込まれた理由のひとつについては、
  [RenderCache](render-cache.md) の分類の一覧を順に当たってください。セッションの読み取り、`Principal` バリエーションのないルートでのアイデンティティの読み取り、`Locale` バリエーションのないロケールの読み取り、認可のチェック、あるいは生の SQL の読み取りです。
- **バックエンドに到達できない。** `RENDER_CACHE_FAILURE` が決めます。`open`
  （既定）はルートを未キャッシュのまま配信し、`closed` は素の `503` を返します。起動時にバックエンドが欠けている場合は、代わりに起動が止まり、直すべきマイグレーションか変数を名指しする 1 文が出ます。
- **Redis がフラッシュされた、または再起動した。** エントリはミスになり、再レンダリングされます。古いものが最新だと証明されることはありません。最新であることは、バイト列を保持していた階層に対してではなく、データベースの世代台帳に対して証明されるからです。
- **再構築のリーダーが再構築の途中で死んだ。** そのリースは、ストアの時刻が期限を過ぎた時点で引き継がれ、元のリーダー自身の公開は、新しいリーダーと競争するのではなくフェンスで締め出されます。それは何も公開しませんが、そのリクエストのレスポンスは変わらず配信されます。
- **L1 のファイルが、クラッシュやディスク満杯で破れた。** それを配信するものは何もありません。各ファイルは自身のフレームに対するダイジェストを運ぶので、切り詰められたファイルや変えられたファイルはその検査に失敗してミスになります。ストアは次にオープンするときに、それと、残された一時ファイルを取り除きます。ここでは破れた書き込みは、永久に汚染されたエントリではなく自己修復するものです。
- **データベースがバックアップから復元された。** これには 1 文ではなく手順があります。下の「データベースを復元する」を参照してください。
- **いますぐ、すべてを消したい。** `render-cache:epoch-advance` です。ノードが複数あるときは、各ノードで実行するか、実行しなかったノードを再起動してください。この前進はデプロイ全体について台帳のエポックを動かしますが、L0 をクリアし、リース済みエポックを手放すのは、それを実行したプロセスの中だけです。下の復元手順が、その理由を詳しく述べています。

## データベースを復元する

世代台帳は、すべてのヒットが照合される権威なので、データベースを復元することは、すでに保存されているすべてのエントリにとって「最新」が何を意味するかを変えます。保存済みエントリが次に何をするかを決めることが 2 つあり、そのどちらも「静かに捨てられる」ではありません。

**それはあなたのために処理されます。** 復元後の最初の権威読み取りが、復元後の値より上に刻印されたエポックまたはエントリに出会うと、そのエントリをきっぱりと拒否します。`Warning` 付きで一度でも配信されることはなく、どんな経過時間でも、ルートの新鮮さのポリシーが何を言っていようと関係ありません。そのうえで再構築し、台帳のエポックを見た最も高い刻印より 1 つ先へ引き上げ、そのノードのエポックリースを引き上げた値に置き換え、そのノードの L0 をクリアします。ほかのすべてのノードは、それぞれ次の権威読み取りで引き上げられたエポックを目にします。
`CoherenceMode::Authority` のもとでは即座に、`CoherenceMode::Lease` のもとでは
`max_age_ms` 以内にです。`suprnova.render_cache.epoch_rewinds` が検出のたびに数えます。

それがすべてであり、それは運用担当者の `render-cache:epoch-advance` が生むのと同じ収束に、運用担当者なしで到達するものです。
`framework/tests/render_cache/middleware.rs` の 3 つの
`an_epoch_advanced_by_another_node_*` のテストが伝播の限界を測り、
`a_rewound_epoch_refuses_the_entry_rebuilds_and_lifts` が拒否を測ります。

**任意の手順が 1 つだけ残っています。** 古くても配信可のウィンドウを持つルートが、再構築の前に復元前の表現を一度も配信してはならない場合は、共有 L1
階層を空にしてください。それを到達可能にするのは、この引き上げそのものです。引き上げられたエポックより*下に*刻印された L1 エントリは、ふたたび普通の移動したエントリになり、そのようなルート上の移動したエントリは、再構築がリクエストの背後で走るあいだ、一度だけ `Warning` 付きで配信されます。ファイル階層のディレクトリの中身を削除するか、`DELETE FROM suprnova_render_entries`
を実行するか、`<prefix>entry:*` に一致する Redis のキーを削除してください。プロファイルが設定している階層に応じて、いずれかです。これを飛ばした場合の最悪の結果は、そのようなキーごとに `Warning` の印が付いた復元前の本文が 1 つ配信されることです。

## 計測

RenderCache は 2 つのベンチマークを同梱しており、それらは**要求に応じて使う道具であって、ゲートの手順では決してありません**:

```bash
crates/suprnova-live/scripts/run-render-cache-budget.sh
```

これは、エンジンのベンチ（`render_cache_budget`。数えるアロケーターを伴う、熱いヒットとコンポジットの組み立ての計測）を走らせ、次にフレームワークのワークロードのベンチ（`render_cache_workloads`。ミドルウェア全体を通した同じルート）を走らせ、それからチェックインされた結果に対する契約テストを走らせます。どちらも `SUPRNOVA_LIVE_S1_CPUSET` に固定されています。

完全な実行には、使い捨ての PostgreSQL（`PG_TEST_URL`）と使い捨ての Redis
（`REDIS_TEST_URL`）が必要です。チェックイン結果の契約が、記録された 3 つのプロファイルすべてを要求するからです。**部分的な実行では、両方の結果ファイルをリダイレクトしなければなりません。**`SUPRNOVA_LIVE_BENCH_RESULT` と
`SUPRNOVA_LIVE_WORKLOADS_RESULT` を使って `benchmarks/local/` の下に向けます。それをしないと、チェックインされた結果をより短いファイルで上書きし、それから自分自身の契約に失敗します。

`crates/suprnova-live/benchmarks/render-cache-budget-v1.json` と
`render-cache-workloads-v1.json` から取った、チェックイン済みの数字です:

| 計測 | 値 |
|---|---|
| 新鮮な `Complete` の L0 ヒットにおけるエンジンの仕事、p95 | 0.76 マイクロ秒 |
| ヒープ割り当て、新鮮なヒット | 3 |
| ヒープ割り当て、条件付き `304` のヒット | 3 |
| ヒープ割り当て、シード期限で境界付けられたヒット | 4 |
| そのいずれにおける本文のコピー | なし。バッファは共有される |
| 同じルートをミドルウェアを通して、サーバー側、p95 | 14.4 マイクロ秒 |
| 同じリクエストをループバック HTTP の往復で、p95 | 109 マイクロ秒 |
| 熱いヒット 1 回あたりの SQL 文数（リースモード） | 0 |

ミドルウェアの数字は、12 行を読んだレンダリングが生んだ 65,536 バイトの本文についてのもので、観測された依存アイデンティティ 14 件として記録されています。

**これらは、資格を得た証拠ではなく、探索的なものとして読んでください。**
チェックインされた結果はすべて `"classification": "local_exploratory"` と
`"s1_requirements_met": false` を運びます。それらは、CPU を共有し、`powersave`
ガバナーで、ループバックのプロバイダーを使う開発者のワークステーションの上で生み出されました。桁が丸ごと 1 つ落ちるような退行を捕らえるには役立ちますが、それより細かいことには役立ちません。ある数字が資格を得た証拠であるのは、それが専用ランナーの上で、その証明を設定して生み出されたときだけであり、これらはそうではありません。

### Suprnovaが異なる設計を選んだ理由

Laravel のレスポンスキャッシュのパッケージは、運用を下にあるキャッシュストアに任せます。エントリを検査するとは、そのキーを手で見つけて値を読むことであり、その値はレンダリング済みのページなので、それを見るとは誰かの HTML を端末へ印字することです。そしてすべてを無効化するとは、セッションもレート制限もキューも保持しているストアをフラッシュすることです。可観測性は、そのストアのドライバーがたまたま出すものです。

Suprnova は、キャッシュに自分自身の運用の表面を、意図的に狭く与えます。検査は構造上、本文を含みません。したがって運用担当者は、エントリが存在すること、どのクラスのもとで保存されているか、どれくらいの大きさかを、その中身を一度も見せられることなく確かめられます。無効化は、適用に何の費用もかからず、このキャッシュだけに触れるエポックの前進です。あなたのセッションとキューは、その影響範囲に入りません。テレメトリは、閉じた属性集合を持つ閉じた 9 つのカウンターであり、それが、それらの上のダッシュボードを、ずれていく文字列の集合ではなく、リリースをまたいで安定したものにしています。その取り引きの代償は、「このキーを 1 つ削除する」というコマンドが存在しないことです。レバーは、エントリごとで読み取り専用か、エポック全体か、そのどちらかです。
