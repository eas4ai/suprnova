# RenderCache のデプロイメント

自分自身のためだけにキャッシュする 1 つのプロセスに必要なのは、メモリだけです。
ロードバランサーの背後にある複数のプロセスは、何が保存されているのか、誰が
エントリを再構築してよいのか、そして何がいつ真でなくなったのかについて合意する
必要があります。しかも、そのうちの誰も、古くなった内容が最新だとほかを納得させ
られないまま合意しなければなりません。RenderCache はそれに**プロファイル**で
答えます。プロファイルは、プロセスがどのプロバイダーを組み立てるのかを名指しし、
それ以外は何も変えません。ルートの宣言、ポリシー、キー、コレクター、ミドルウェア
の流れ、そしてステッチは、どのプロファイルでも同一であり、アプリケーションに
面する型はどれ 1 つとして異なりません。

この章は、その選び方と配線の仕方です。3 つのプロファイルとそれぞれが提供する
もの、フレームワークの設定が実際に読む環境変数、共有プロファイルが起動する前に
アプリケーションが一覧に挙げなければならないマイグレーション、ブートストラップの
どこにインストールが入るのか、そして各階層が約束すること・しないことを扱います。
このリポジトリのドッグフードアプリケーションは、既定では組み込みプロファイルで
走り、`app/tests/live_render_cache.rs` の
`the_database_profile_serves_a_hit_through_the_sql_stores` によって
データベースプロファイルで起動されます。

## 3 つのプロファイル

| プロファイル | L1 のエントリ | 再構築のリーダーシップ | Live のインスタンスレコード |
|---|---|---|---|
| `embedded`（既定） | キーごとに 1 ファイル、またはなし | プロセス内 | プロセス内 |
| `database` | `suprnova_render_entries` | `suprnova_render_leases` | `suprnova_live_instances`、`suprnova_live_promotions` |
| `redis` | キーごとに 1 つの Redis ハッシュ | キーごとに 1 つの Redis ハッシュと、トークンカウンター | レコードごとに 1 つの Redis ハッシュ |

これらのあいだで**動かない**ものが、世代の真実です。データベースに支えられた
世代台帳が、どのプロファイルでも権威です。どの階層がバイト列を渡したのであれ、
最新であることはデータベースに対して証明されます。`CoherenceMode::Authority` の
もとではヒットのたびにそれを読み直すことで、`CoherenceMode::Lease` のもとでは
それより前の読み取りから付与された検証リースによってです。それが、アクセラレー
ターをアクセラレーターのままに保つものです。Redis は保持しているものをすべて
失っても構いません。古いものが最新だと証明されることはありません。そもそも
Redis が保持しているものは、何一つ最新であることを証明しないからです。

実際に何を共有したいかで選んでください:

- **`embedded`**: 1 つのプロセスのため、そして各自が自分のコピーを持てば満足な
  複数のプロセスのためのものです。`RENDER_CACHE_L1_DIR` を設定すれば、各プロセス
  は自分自身の再起動を越えて生き残るファイル階層を手にします。
- **`database`**: 複数のノードが保存済みエントリを共有し、キーごとに 1 つの
  再構築リーダーを選ぶべきで、しかもデプロイに可動部品をこれ以上増やしたくない
  ときのためのものです。
- **`redis`**: 共有階層のレイテンシーが、その耐久性より重要なときのためのもの
  です。その下では、データベースが変わらず世代の真実を保持します。

## 環境変数

`RenderCacheConfig::from_env` は、`framework/src/render_cache/config.rs` の中で
次のものを読みます:

| 変数 | 既定値 | 意味 |
|---|---|---|
| `RENDER_CACHE_ENABLED` | `true` | `false` と `0` 以外なら何でも有効。`false` は `RenderCache::install` を何もしない処理にする |
| `RENDER_CACHE_PROFILE` | `embedded` | `embedded`、`database`、`redis` のいずれか。下の 2 行を設定する |
| `RENDER_CACHE_L1` | プロファイルのもの | `disabled`、`file`、`database`、`redis` |
| `RENDER_CACHE_COORDINATOR` | プロファイルのもの | `local`、`database`、`redis` |
| `RENDER_CACHE_L0_ENTRIES` | 4,096 | プロセス内のエントリ数の上限 |
| `RENDER_CACHE_L0_BYTES` | 128 MiB | プロセス内のバイト数の上限 |
| `RENDER_CACHE_L1_DIR` | 未設定 | ファイル階層のディレクトリ。`embedded` のもとでは、これを設定することが L1 を有効にする |
| `RENDER_CACHE_L1_BYTES` | 1 GiB | ファイル階層ではディレクトリ全体、データベース階層と Redis 階層では 1 エントリ |
| `RENDER_CACHE_REDIS_URL` | `REDIS_URL`、次に `redis://127.0.0.1:6379` | Redis の両キャッシュ階層が接続する先 |
| `RENDER_CACHE_REDIS_PREFIX` | `suprnova_render:` | Redis の両キャッシュ階層が書き込むキーの名前空間 |
| `RENDER_CACHE_LEASE_MS` | 30,000 | 再構築リースの寿命 |
| `RENDER_CACHE_MAX_WAITERS` | 128 | プロセス内の待機者の上限 |
| `RENDER_CACHE_HINTS` | プロファイルのもの | `disabled` または `redis`。上のエンドポイント経由で `<prefix>hints` に流れる信頼できる世代ヒント |
| `RENDER_CACHE_FAILURE` | `open` | `open` はプロバイダーの障害時にルートを未キャッシュのまま配信し、`closed` は `503` を返す |
| `APP_BUILD_ID` | アプリケーションのパッケージバージョン（下記参照） | すべてのエントリを、それを生成したビルドの名前空間に分ける |

`RENDER_CACHE_HINTS` は、ここで唯一、どの答えも変えないつまみです。`redis`
プロファイルのもとでは既定で `redis`、他の 2 つのもとでは `disabled` であり、
自分専用のエンドポイントは持ちません。上の `RENDER_CACHE_REDIS_URL` と
`RENDER_CACHE_REDIS_PREFIX` に相乗りします。ヒントにできるのは、ノードが
すでに保持している検証リースを短くすることだけです。ですから、ヒントをオフに
したデプロイ、チャネルが死んでいるデプロイ、この機能なしでビルドしたデプロイは、
どれも同じエントリを配信し、同じ再構築を認めます。違うのは再検証の時機だけです。
到達できないヒントのエンドポイントが、到達できないキャッシュ階層とは違って起動を
止めないのも、同じ理由です。

プロファイルは略記であって、錠前ではありません。`RENDER_CACHE_L1` と
`RENDER_CACHE_COORDINATOR` はそれぞれ自分の側を上書きするので、エントリは
データベースに置きたいが再構築のリースはプロセス内に置きたいデプロイは、いちばん
近いプロファイル全体を選ぶのではなく、まさにそのとおりに述べられます。

受け入れる値の集合が閉じている変数に、その外の値が設定されていると、起動は
その変数を名指しするメッセージとともに失敗します。拒否された値がそのメッセージの
中で繰り返されることはありません。環境変数の値は秘密を運びうるからです。

**`APP_BUILD_ID` は、デプロイごとに一度、明示的に設定してください。** これは
すべてのルックアップキーに混ぜ込まれるので、これを変えることが、新しいビルドが
前のビルドの公開したエントリを配信するのを止める手段です。この変数がなければ、
`RenderCacheConfig::from_env` はあなたのアプリケーション自身のパッケージ
バージョンにフォールバックします。`#[suprnova::main]` が、環境を読み込む
その瞬間に、アプリケーションクレート自身のコンパイルから `CARGO_PKG_VERSION`
を記録し、既定値がここでフォールバックする先は、その記録された値です。
`#[suprnova::main]` を一度も展開しないバイナリだけが、さらに先へ、この
**フレームワーク**クレート自身のバージョンへフォールバックします。そう
名指ししているのは、そうしないとアプリケーションのものと混同しやすいから
です。いずれにせよ、値が動くのは誰かがバージョン番号を上げたときだけで、
パッケージバージョンはデプロイごとに変わることはめったにありません。
バージョンを上げずにテンプレートや翻訳やハンドラーを変えたデプロイは、同じ
ビルド識別子のままとなり、前のビルドが公開したエントリを配信しうるのです。
出荷のたびに変わるもの、たとえばコミット識別子やリリース識別子を設定して
ください:

```bash
APP_BUILD_ID=$(git rev-parse --short HEAD)
```

環境を一度も読まないインストールは、コード内で
`RenderCacheConfig::with_build_id` を使って同じ値を設定します。これは、
独自のデプロイごとの識別子をプログラムで導出するアプリケーションのために、
`from_env` が選んだもの、明示的な `APP_BUILD_ID` を含めて、それを上書きします。

どの値を設定するにせよ、それを読む本番バイナリは、Suprnova の
[本番ビルド形](deployment.md#production-build-shape)でビルドされていることが
期待されます。既定の機能は無効で、`testing` は `cargo test` だけのために
取っておかれます。

Live 自身のインスタンス台帳は、別に設定されます。それはキャッシュのストレージ
ではなく Live の権威だからです。`LIVE_LEDGER_DRIVER`（`memory`、`database`、
`redis`）、`LIVE_REDIS_URL`、そして `LIVE_REDIS_PREFIX` です。デプロイは、
キャッシュを 1 つの階層で、台帳を別の階層で走らせても構いません。

## アプリケーションが一覧に挙げなければならないマイグレーション

RenderCache のスキーマは、フレームワークが所有し、アプリケーションが適用します。
あなたの `Migrator` がそれを一覧に挙げるので、`suprnova migrate` があなた自身の
ものと並べてテーブルを用意します:

```rust
Box::new(suprnova::render_cache::migration::Migration),
Box::new(suprnova::render_cache::migration::TierMigration),
```

これは `app/src/migrations/mod.rs` そのままであり、この 2 つは交換可能では
ありません:

- **`Migration`** は、耐久性のある世代の真実を保持する 3 つの `suprnova_render_*`
  テーブルを作ります。現在の世代、追記のみの変更ログ、そして権威エポックです。
  `embedded` を含むすべてのプロファイルがこれを必要とします。世代の真実が
  キャッシュ階層へ移ることは決してないからです。
- **`TierMigration`** は、データベースの L1 ストアとデータベースの再構築
  コーディネーターが読む 4 つのテーブルを作ります。これを必要とするのは、そこへ
  到達するプロファイルだけです。ただし `RenderCache::install` は、これらがない
  データベースプロファイルの起動を拒否するので、これを一覧に挙げることが、
  `RENDER_CACHE_PROFILE=database` を、あなたのアプリケーションが実際に選べる
  設定にします。

`RENDER_CACHE_ENABLED=false` を設定するアプリケーションは、どちらも運ぶ必要が
ありません。インストールはルーターを手つかずのまま返し、何も調べず、ランタイムを
組み立てず、ミドルウェアを登録せず、書き込み側を計装しないままにするので、
切ってあるキャッシュに何かを払うことはありません。

## インストール

`RenderCache::install` は非同期です。何かを組み立てる前に、テーブルの有無を
調べ、その設定が使うことになる個々の Redis エンドポイントすべてに ping を
打つからです。それを収めるフックが `Application::try_routes_async` です。
これは `app/src/live/mod.rs` であり、2 つの関数への分け方は真似する価値が
あります:

```rust
/// [`routes`] followed by the RenderCache middleware. This is the entry
/// point every server in this application uses.
pub async fn routes_with_render_cache(router: Router) -> Result<Router, FrameworkError> {
    routes_with_render_cache_with_config(router, RenderCacheConfig::from_env()?).await
}

#[doc(hidden)]
pub async fn routes_with_render_cache_with_config(
    router: Router,
    config: RenderCacheConfig,
) -> Result<Router, FrameworkError> {
    RenderCache::install(routes(router)?, config).await
}
```

`routes` は同期的な内側の半分です。予約された Live のルート、ドキュメントの
ルート、そしてすべてのキャッシュポリシーを登録し、ミドルウェアは何も
インストールしません。`cmd/main.rs` は `Application::try_routes_async` を通じて
`routes_with_render_cache` に到達し、ブラウザーシナリオのサーバーである
`app/examples/live_dogfood_host.rs` は直接それを待ちます。

その下にある設定の継ぎ目は、飾りではありません。異なるプロファイルや、自分で
動かせるクロックを必要とするテストには、ほかに入り口がありません。そして、
サーバーと*同じ*ルート、ポリシー、ミドルウェアの順序をインストールし、渡した
設定だけが異なることに意味があります。ドッグフードの起動はどちらもこれを
通ります。`the_database_profile_serves_a_hit_through_the_sql_stores` は
データベースプロファイルの設定を渡し、
`stale_service_is_marked_and_rebuilt_in_the_background` は調整可能なクロックを
運ぶ設定を渡します。[RenderCache の運用](render-cache-operations.md)の
「キャッシュ対象のルートをテストする」を参照してください。

順序の規則が 2 つあり、どちらも呼び出し側の責任です:

1. すべてのルートとグループは、`install` の**前に**組み込まれていなければ
   なりません。`install` は、その時点までに登録されている内容を読み取ります。
2. `install` はグローバルなミドルウェアチェーンに追加するので、キャッシュの
   ミドルウェアがルックアップキーを導出する際に読む、リクエストスコープの状態を
   確立するセッション、ロケール、アイデンティティのミドルウェアの**あとに**
   走らせなければなりません。

インストールは 2 つの調査を通じて、閉じる方向に失敗します。設定が到達することに
なるテーブルが存在するかを検査し、設定が使うことになる個々の Redis エンドポイント
に、エンドポイントごとに 1 回 ping を打ちます。どちらかが失敗すれば、直すべき
マイグレーションか変数を名指しする 1 文とともに起動が止まるので、欠けたテーブルや
誰も答えないエンドポイントに対して何かが配信されることは決してありません。
（Live 自身のインスタンス台帳は、リクエストが 1 つも配信される前に `Server::run`
によって別途調べられます。）

## ルートのエントリをどこに置くかを選ぶ

L1 が*何であるか*はプロファイルが決め、どのルートがそれを使うかはポリシーが
決めます。ルートが別のことを宣言しない限りビルダーは L0 のみに保存するので、
共有階層は意図的に埋められます:

```rust
RenderCachePolicy::builder(RepresentationClass::PublicShared)
    .freshness(FreshnessPolicy::new(300_000, 60_000, 300_000)?)
    .layers(StorageLayers::l0_and_l1())
    .build()?
```

`the_database_profile_serves_a_hit_through_the_sql_stores` は、データベース
プロファイルの上で、この往復をエンドツーエンドで証明します。公開済みエントリは、
ミドルウェアが導出したキーのもとで SQL ストアから読み戻され、それから L0 が
空にされ、次のリクエストもレンダリングなしで答えられます。ルートごとの決め方は
[RenderCache の表現](render-cache-representations.md)を参照してください。

## 1 つの適合スイート、すべてのプロバイダー

どのストアも同じスイートに答えます。
`framework/tests/render_cache/store_conformance.rs` は、`RenderStore` トレイト
だけに対して書かれたエンジンのプロバイダーシナリオを、ファイルに支えられた L1、
SQLite・PostgreSQL・MySQL 上の SQL の L1、そして Redis の L1 の上で走らせ、
プロセス内ストアはエンジンクレートの中で同じスイートに答えます。PostgreSQL、
MySQL、Redis は、`scripts/check-postgres.sh`、`scripts/check-mysql.sh`、
`scripts/check-redis.sh` が実サーバーに対して名前で選ぶ、ignored なテストを
通じて走ります。あるプロバイダーがここで「サポートされている」のは、それが存在
するからではありません。ほかのすべてと同じ言葉に合格するからサポートされて
いるのです。

## 各階層が約束すること、しないこと

- **ノードをまたいだ待機はありません。** 別のノードがすでに再構築中のキーは
  バイパスです。このノードはレンダリングし、何も公開しません。ノードをまたいだ
  境界付きの重複計算は受け入れますが、受理される公開が 2 つになることは受け
  入れません。2 つ目を禁じているのは、ストア自身の公開フェンスです。
- **失われたバックエンドはミスであって、決して誤った答えではありません。**
  エビクション、期限切れ、Redis の再起動は、エントリをミスにし、インスタンスを
  行方不明にします。データベースの世代台帳に対する整合性チェックは、どの階層が
  バイト列を配信したのであれ、すべてのヒットで走ります。
- **改竄されたバイト列はミスです。** 行やハッシュの中のエントリのバイト列は
  署名付きのコーデックフレームなので、破れた値、切り詰められた値、変えられた値は
  完全性の検査に失敗し、配信されるのではなくミスとして扱われます。
- **データベース階層と Redis 階層は、場所を空けるためのエビクションを行いません。**
  `RENDER_CACHE_L1_BYTES` は、そこでは 1 エントリの上限であって、テーブルや
  キースペースの上限ではありません。増加は代わりに保持期間で境界付けられます。
  ディレクトリ全体を境界付けるのはファイル階層だけであり、それはそのディレクトリ
  を単独で所有しているからです。
- **Redis のアダプターが対象とするのは、単一の Redis 7 以降のインスタンスです。**
  Redis Cluster は拒否されます。スクリプトは自分が宣言していないキーに触れ、
  スクリプトの内側で `TIME` を使ってストアのクロックを読むからです。
- **MySQL は 8.0.19 以降が必要です。** 重複キーを正確に分類するためです。
  それより古い MySQL と MariaDB は、このビルドがテーブルに帰属させられない形で
  衝突を報告するので、プロバイダー利用不可のエラーへ縮退します。それが安全な方向
  であり、いずれにせよ二重に付与されることはありません。
- **ノードをまたいだ期限切れの判断は、すべてバックエンドのクロックで行われ**、
  それに基づいて動く操作の内側で読まれます。クロックが進みすぎているノードは、
  リースを延ばすことも、生きているエントリをほかから隠すことも、ほかのノードの
  レコードを経過済みだと宣言することもできません。

### Suprnovaが異なる設計を選んだ理由

Laravel のレスポンスキャッシュのパッケージは、すでに設定してあるキャッシュストアを
受け継ぎます。したがって「キャッシュを複数のノードにまたいでデプロイする」とは、
`CACHE_STORE` を Redis に向け、その中にあるものが正しいと信じることです。誰が
エントリを再構築してよいかという別立ての概念はなく、2 つのワーカーが同じキーに
対して食い違うバイト列を公開するのを止めるフェンスもなく、そしていちばん重大な
ことに、ストアの下に権威がありません。Redis がページを持っていれば、その
ページが配信されます。Redis がフラッシュされれば、すべてが再計算されます。
ストア*こそが*真実なのです。

Suprnova は、その 2 つを意図的に切り離します。共有階層はバイト列を保持し、それ
以外は何も保持しません。データベースはどのプロファイルでも世代の真実を保持し、
ヒットが照合される先はそれです。だからこそ、ここで Redis を失うことは正しさでは
なくレイテンシーの費用で済み、だからこそ再構築は競争ではなくリースされ、公開は
フェンスで守られ、そしてだからこそ、同じルートの宣言が、ノートパソコン上の
`cargo run` からデータベースで協調する多数のノードまで、変更なしで走ります。
その代償は、アプリケーションが一覧に挙げなければならないマイグレーションと、
素のキーバリューキャッシュなら払わないヒット経路上のデータベース読み取り（1 文、
検証リースのもとでは 0 文）です。その読み取りが何をもたらすかは
[RenderCache の世代](render-cache-generations.md)を参照してください。
