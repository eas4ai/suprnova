# RenderCache

RenderCache は、`GET` または `HEAD` ルートのレスポンスについて安全性が証明済みの
コピーを保存し、次に一致するリクエストにはハンドラーを一切実行せず、その
コピーから応答します。ルートとグループは明示的に組み込んだものだけが対象になり、
それ以外は今までどおりまったく変わらず動作します。一度も組み込んでいないルートには
いっさい手を加えません。組み込んだルートであっても、その特定のリクエストのどの部分も
キャッシュしても安全だとわからなかった場合には、正しくレンダリングされ正しく
配信されます（ただし保存はされません）。そして、なぜ保存されなかったのかを
調べることもできます。

この章では、キャッシュの有効化、ルートとグループの組み込み、バリエーションの宣言、
追加されるレスポンスヘッダーの読み方、レンダリングが却下される理由、運用上の制御、
そして `suprnova::Cache` との違いを扱います。

## キャッシュの有効化

まず重要になるのは、次の 2 つの環境変数です:

- `RENDER_CACHE_ENABLED`: `false` または `0` に設定しない限り `true` です。
  無効にすると、すべてのリクエストが RenderCache を完全にバイパスします。
  ルックアップも保存もまったく行われません。
- `RENDER_CACHE_L1_DIR`: 既定では未設定で、ディスク上の階層は存在しないことを
  意味します。プロセスが作成・書き込みできるディレクトリを設定すると、保存された
  表現はファイルに裏付けられた第 2 階層でプロセスの再起動を越えて生き残ります。

そのほかいくつかの環境変数が既定値を調整します: `RENDER_CACHE_L0_ENTRIES`
（既定 4,096）と `RENDER_CACHE_L0_BYTES`（既定 128 MiB）はプロセス内階層の
上限を定め、`RENDER_CACHE_L1_BYTES`（既定 1 GiB）はファイル階層の上限を定めます。
`RENDER_CACHE_FAILURE`（既定 `open`、または `closed`）は、ストアやデータベースに
問題が起きたときにルートを未キャッシュのまま配信するか、リクエストを拒否するかを
決めます。`APP_BUILD_ID`（既定では自分のクレート自身のバージョン）は、キャッシュ
された各エントリを、それを生成したビルドの名前空間に分けます。そのため、デプロイが
古いビルドのバイト列を配信することは決してありません。

## ルートやグループの組み込み

指示するまでは何もキャッシュされません。`Router::try_render_cache` は、
すでに登録済みのルートパターンを 1 つ組み込みます。`Router::try_render_cache_group`
は、あるパスプレフィックス配下のすべてのルートを組み込みます。どちらも
`RenderCachePolicy::builder` で構築したポリシーを受け取ります:

```rust
use suprnova::{FrameworkError, Router};
use suprnova::render_cache::{
    FreshnessPolicy, RenderCachePolicy, RepresentationClass, SharedCachePolicy,
};

fn add_render_cache(router: Router) -> Result<Router, FrameworkError> {
    router.try_render_cache_group(
        "/blog",
        RenderCachePolicy::builder(RepresentationClass::PublicShared)
            .freshness(FreshnessPolicy::new(300_000, 60_000, 300_000)?)
            .shared(SharedCachePolicy::SMaxAge { seconds: 300 })
            .build()?,
    )
}
```

`FreshnessPolicy::new(fresh_ms, stale_servable_ms, stale_on_error_ms)` は、
ある表現が新鮮でいられる時間、バックグラウンドでの再構築が走っている間さらに
どれだけ長く配信してよいか、そしてその再構築が完全に失敗した場合にさらに
どれだけ長く配信してよいかを設定します。`RepresentationClass` は共有範囲の
広いものから狭いものへと並びます: `PublicShared`（宣言されたバリエーションに
一致する全員に対して表現を 1 つ共有）、`PublicShellStitched`（将来の合成シェル
表現向けに予約されており、まだ使用できません）、`PrivateCached`（サインイン済みの
訪問者またはテナントごとに表現を 1 つ）、そして `Uncacheable` です。

ルートパターンは組み込む前にすでに登録されていなければならず、ルートとグループの
組み込みは `RenderCache::install`（後述）を呼び出す**前に**すべて終えておく
必要があります。インストール手順は、その時点までに登録されている内容を読み取る
からです。

ルート単位のポリシーは、完全な `RenderCachePolicy` の代わりに `PolicyPatch` を
使って、それを包含するグループを狭めるパッチにすることもできます: グループが
宣言したすべてを継承したうえで、狭めることしかできません（鮮度ウィンドウを
短くする、クラスをより厳格にする）。広げることは決してできません。あるルートを
キャッシュ対象のグループから完全に外すには、クラスを `Uncacheable` に設定する
`PolicyPatch` を使います。

リクエストスコープのロケール、セッション、アイデンティティを確立するミドルウェア
登録がすべて終わったあとに、1 行で RenderCache の組み込みを仕上げます
（RenderCache はルックアップキーを組み立てるためにそれらを読み取るので、それらを
設定する処理のあとに実行する必要があります）:

```rust
use suprnova::RenderCache;
use suprnova::render_cache::RenderCacheConfig;

let router = add_render_cache(router)?;
let router = RenderCache::install(router, RenderCacheConfig::from_env()).await?;
```

## バリエーションの宣言

既定では、キャッシュされた表現はルートパターン、パスパラメータ、そして
アプリケーションのビルドによってのみ分かれます。ハンドラーの出力が実際に
依存するそれ以外のものは、次の 2 つの仕組みで宣言する必要があります:

- **クエリパラメータ。** `.query(QueryPolicy::declared(["page", "sort"]))` は、
  表現を区別するクエリパラメータの名前を挙げます。それ以外のクエリパラメータが
  リクエストに存在すると、黙って無視されるのではなく、そのリクエストに対して
  キャッシュがバイパスされます。
- **バリエーションディメンション。** `.vary(dimension)` で 1 つずつ追加します:
  - `VarianceDimension::Locale` はネゴシエートされたロケールで分割します。
  - `VarianceDimension::Media` はネゴシエートされたメディアタイプで分割します。
  - `VarianceDimension::Host` はリクエストのホストで分割します。デプロイで
    複数のホストに意味がある場合に使います。
  - `VarianceDimension::Tenant` は不透明なキー素材としての現在のテナントで
    分割します。ハンドラーがテナントを読み取ることがあるルートは、これを
    宣言しなければなりません。
  - `VarianceDimension::Principal` は、権限バージョンに紐づいた不透明な
    キー素材としてのサインイン済みの訪問者で分割します（詳しくは後述の
    「エポック、権限、検査」を参照）。`PrivateCached` ルートは `Principal` か
    `Tenant`（あるいは両方）を宣言しなければならず、そうしなければそもそも
    ビルドに失敗します。

`VarianceDimension::FeatureVersion`、`VarianceDimension::ConfigVersion`、
そして独自の `VarianceDimension::Application(name)` は型として存在しますが、
このリリースではリゾルバーがありません: これらのいずれかを宣言したルートは、
ビルドに失敗するのではなく、すべてのリクエストで黙ってキャッシュをバイパス
します。今はまだ宣言しないでください。

## レスポンスヘッダーの読み方

配信されたヒットには、`ETag`（クライアントが `304` を得るために
`If-None-Match` として送り返せる強いバリデータ）、`Cache-Control`（クラスが
`PublicShared` で `SharedCachePolicy::SMaxAge` を設定している場合を除き
`private`。設定している場合は `public` と `s-maxage` も含みます）、`Vary`
（宣言されたディメンションのうち `Vary` を暗に示すもの。`Locale` は
`Accept-Language` を、`Media` は `Accept` を暗に示します）、そして `Age`
（その表現が公開されてから経過した整数秒）が付きます。古くなったまま配信を
許可されたレスポンスには、さらに `Warning: 110 - "Response is Stale"` が
付きます。

## レンダリングが保存されない理由

組み込まれていることは保証ではありません。すべてのレンダリングのあとに
2 つの独立したチェックが走り、どちらも、リクエストを失敗させることなく
保存を却下できます（返ってくるレスポンス自体はどちらの場合も同じで、ただ
キャッシュエントリにならないだけです）:

**適格性**は、`GET` または `HEAD` に対する単純な `200` でないレスポンス、
本文をストリーミングするレスポンス、Cookie を設定するレスポンス、あるいは
ホップバイホップヘッダーやトレーシングヘッダーを持つレスポンスを、問答無用で
却下します。これらはほとんどの場合、設計上考慮すべきものというより偶発的な
もの（リダイレクト、エラーページ、たまたま `Set-Cookie` に触れているレスポンス
など）です。

**分類**は、ハンドラーが実行中に実際に何をしたかに基づいて却下します。
見覚えのある言葉で言うと、次のとおりです:

- **セッションの値を読み取った。** 現在のセッションを読み取る操作
  （`session()`、`session_mut`、またはセッション Cookie を通じて）は、
  ルートがどんなバリエーションを宣言していても、レンダリングを永続的に
  `Uncacheable` にします。これは、匿名の訪問者のアイデンティティがセッションの
  フォールバック経由で解決されるときにも発生します（よくある驚きどころです。
  訪問者は本当に匿名で、結果のキーも正しく `Anonymous` になるのですが、
  それでもその読み取り自体はセッションの読み取りだからです）。
- **`Principal` を宣言していないルートでアイデンティティを読み取った。**
  サインイン済みのユーザーを読み取ると、クラスは `PrivateCached` に狭まります。
  ルートが宣言したバリエーションに `Principal` が含まれていない場合、
  訪問者ごとにエントリをキー付けする方法がないため、共有されるのではなく
  却下されます。
- **`Locale` を宣言せずに翻訳した（あるいはビューエンジンが翻訳した）。**
  ネゴシエートされたロケールを読み取る操作には、必ず `Locale` ディメンションの
  宣言が必要です。さもなければレンダリングは却下されます。Inertia の各ページの
  ドキュメントシェルは、ページ自身のデータが言語と何ら関係があってもなくても、
  `<html lang>` を設定するためにロケールを読み取ります。そのため Inertia
  ルートは、自分自身には翻訳済みコンテンツが一切なくても、そもそもキャッシュ
  されるためには `Locale` の宣言が必要です。
- **認可をチェックした。** `Gate` は常に判定を訪問者ごとのものとして扱うため、
  ゲート自身のチェックがテナント単位であると証明できない限り、`Tenant` だけで
  キー付けされたルートであっても `Principal` の宣言が必要です。RenderCache は
  この違いを自力では見分けられません。
- **ページの背後にあるモデルが、テナントスコープのグローバルスコープを
  持っている。** クエリを絞り込むために自身のリクエストローカルな状態から
  現在のテナントを読み取るグローバルスコープ（Suprnova 自身の `GlobalScope`
  のドキュメントが示しているパターンです）は、RenderCache がその読み取りを
  一度も目にすることなく、クエリが返す内容を変えてしまいます。そうした
  モデルに支えられたルートには `Tenant` のバリエーションを宣言してください。
  ここに挙げた仕組みのどれも、宣言漏れを代わりに検出してはくれません。
- **秘密の設定値、または宣言されていないリクエストコンテキストを読み取った。**
  どちらも `Uncacheable` を強制します。レスポンスが通常のリクエストヘッダーや
  `Config::get` に依存していること自体は、RenderCache には完全に見えません。
  見えないものは却下できないので、対応するバリエーションを宣言するのは
  あなたの責任です。

実際に何が起きているかを確認するのに、特別なツールは必要ありません: 隠し
コマンドの `render-cache:inspect`（後述）は、あるルートのエントリがそもそも
存在するかどうかを示しますし、単に 2 回続けてリクエストを送り、2 回目に
`Age` ヘッダーが付いているかどうかを確認するだけでも構いません。

## キャッシュされるルート

訪問者ごとのコンテンツを持たない、公開の一覧ページです:

```rust
use suprnova::{handler, HttpResponse, Response};

#[handler]
pub async fn index() -> Response {
    let posts = Post::query().order_by_desc("published_at").get().await?;
    Ok(HttpResponse::html(render_post_list(&posts)))
}
```

登録して組み込みます:

```rust
use suprnova::{get, routes};
use suprnova::render_cache::{FreshnessPolicy, RenderCachePolicy, RepresentationClass, SharedCachePolicy};

routes! {
    get!("/blog", controllers::blog::index),
}

router.try_render_cache(
    "/blog",
    RenderCachePolicy::builder(RepresentationClass::PublicShared)
        .freshness(FreshnessPolicy::new(300_000, 60_000, 300_000)?)
        .shared(SharedCachePolicy::SMaxAge { seconds: 300 })
        .build()?,
)?;
```

`index` はセッション、サインイン済みの訪問者、ロケールのいずれにも触れない
ため、最初のリクエストはレンダリングされて公開されます。それから 5 分間の
すべてのリクエストは、その保存済みコピーから、`Age` ヘッダー付きで、すでに
持っているクライアントには `304` で、手前にある CDN には
`Cache-Control: public, max-age=300, s-maxage=300` とともに配信されます。

## 却下されるルート

同じ形のページですが、ハンドラーはフラッシュメッセージを表示するために
セッションを読み取ります:

```rust
use suprnova::session::session;
use suprnova::{handler, HttpResponse, Response};

#[handler]
pub async fn index() -> Response {
    let posts = Post::query().order_by_desc("published_at").get().await?;
    let flash = session().and_then(|s| s.get::<String>("status"));
    Ok(HttpResponse::html(render_post_list_with_flash(&posts, flash.as_deref())))
}
```

上とまったく同じ方法で組み込みます。すべてのリクエストは変わらずレンダリング
され、フラッシュメッセージを含む正しいページを配信しますが、何も保存される
ことはありません: セッションの読み取りが、RenderCache が適格性チェックに
到達するより前にクラスを `Uncacheable` に狭めてしまうため、同じ URL への
2 回目のリクエストも、`Age` ヘッダー付きで返るのではなく、最初から改めて
レンダリングされます。このページをキャッシュさせたいのであれば、修正方法は、
キャッシュされる経路でセッションを読み取るのをやめることです（代わりに
フラッシュをクエリパラメータや別の小さなレスポンスからレンダリングします）。
セッションの読み取りをキャッシュ可能にできるバリエーション宣言は存在しません。
セッションの読み取りは、どんなキーでも安全には分割できない何かにレスポンスが
依存していることを意味するからです。

## エポック、権限、検査

- **`RenderCache::bump_permission_version()`。** サインイン済みのユーザーが
  何を許可されているかをアプリケーションの操作が変更するたび（ロールの変更、
  権限の付与や取り消し）に呼び出します。これを呼ばないと、権限が変わった
  ばかりのユーザーは、以前の権限セットのもとでキャッシュされた内容に一致し
  続けてしまいます。
- **`RenderCache::advance_epoch()`**、または隠しコマンドの
  `render-cache:epoch-advance`。緊急時の無効化です。エポックがルックアップ
  キー自体に焼き込まれているため、現在保存されているすべてのエントリは、
  次のリクエストの時点で即座に、通常のルックアップでは到達できなくなります。
  プロセス内階層も同じ瞬間に完全にクリアされます。ファイルに裏付けられた
  階層は、定期または手動のスイープが回収するまで古いファイルをディスク上に
  残しますが、これは正しさの問題ではなくディスクの衛生上の問題です。
  キャッシュされた内容に何か問題があり、個々のエントリの期限切れを待てない
  ときに使います。
- **隠しコマンドの `render-cache:inspect <key>`** は、アプリケーションの
  ログやテレメトリが表示できるキーのテキストを使って、1 件の保存済みエントリの
  メタデータ（本文は決して含みません）を、現在のエポックとともに報告します。
  これにより、いま見ているものがまだ有効な権威なのか、それともすでに
  足元から期限切れになっているのかを判別できます。

## RenderCache と `suprnova::Cache` の違い

`suprnova::Cache` は、あなたが明示的に呼び出すキーバリューストアです。キーを
選び、何を保存するかを選び、いつ無効化するかを選びます（`Cache::put`、
`Cache::get`、`Cache::remember`、`Cache::forget`）。あなたのコードがキャッシュ
する価値があると判断した任意のデータに対して、設定した任意のバックエンド
（メモリまたは Redis）上で動作します。

RenderCache は汎用のストアではなく、ハンドラーから呼び出すことは決して
ありません。HTTP レスポンス全体をキャッシュし、キーはルートとその宣言された
バリエーションから自動的に導出され、無効化は世代ベースです: ORM やクエリ
ビルダーを通じた通常のデータベースへの書き込みが、そのレンダリングが依存
していた世代を進め、エントリは手動で削除されるのではなく、次に要求された
ときに再計算されます。一度だけ計算して再利用したい特定の値があるときは
`suprnova::Cache` を、レンダリングに費用がかかり共有しても安全なレスポンス
を持つルート全体があるときは RenderCache を使ってください。
