# TypeScript 型

`suprnova generate-types`は、Rustのソースを走査して`#[derive(InertiaProps)]`と`#[derive(Data)]`の構造体を見つけ、フロントエンドがインポートできるTypeScriptの宣言を書き出します。プロップやルートを変更した後に実行してください。`--skip-types`を渡さない限り、`suprnova serve`は起動時にこれを代わりに実行してくれます。

## 生成されるもの

3つのファイルが、`frontend/src/types/`の中に書き出されます。

| ファイル | 内容 |
|---|---|
| `inertia-props.ts` | プロップの構造体ごとに1つの`export interface` - 常に書き出されます |
| `routes.ts` | `src/routes.rs`から導かれる`controllers`オブジェクトと、名前引きの`routes`マップ - `--routes`が付いたときだけ書き出されます |
| `lang-keys.ts` | デフォルトロケールのカタログにあるすべてのFluentメッセージidの、`MessageKey`という文字列リテラルのユニオン型（フォールバック元のロケールも含みます） - `lang/`が何らかのidを生む場合だけ書き出されます（[メッセージキー](#メッセージキー)を参照） |

3つとも、自動生成であることを示すヘッダーコメントで始まります。手で編集しないでください - 次の実行で変更は上書きされます。

## 実行する

```bash
# 単発
suprnova generate-types

# Rustのファイルが変更されるたびに再出力する
suprnova generate-types --watch

# プロップファイルのカスタム出力先
suprnova generate-types --output frontend/src/types/props.ts
```

ルートファイルのパスは`frontend/src/types/routes.ts`に固定されており、メッセージキーのファイルは`frontend/src/types/lang-keys.ts`に固定されています。設定できるのは、プロップファイルのパスだけです。ウォッチャーは`src/`をポーリングし、`.rs`の変更があるたびにプロップファイルを再生成します。プロジェクトに`lang/`ディレクトリがある場合は、そのツリーも監視し、`.ftl`の変更があるたびに`lang-keys.ts`を再生成します。

## ページのプロップ

想定されている形は、Inertiaのページごとに1つのRust構造体が`InertiaProps`をderiveし、生成されたインターフェースからプロップの型を得るページコンポーネントと対になる、というものです。

```rust
// src/controllers/home.rs
use suprnova::{InertiaProps, Request, Response, inertia_response};

#[derive(InertiaProps)]
pub struct HomeProps {
    pub title: String,
    pub message: String,
    pub count: i64,
    pub tags: Vec<String>,
    pub avatar_url: Option<String>,
}

pub async fn index(req: Request) -> Response {
    inertia_response!(&req, "Home", HomeProps {
        title: "Welcome".into(),
        message: "Hello".into(),
        count: 3,
        tags: vec!["new".into(), "featured".into()],
        avatar_url: None,
    })
}
```

`suprnova generate-types`は、次を出力します。

```typescript
// frontend/src/types/inertia-props.ts
// This file is auto-generated by Suprnova. Do not edit manually.
// Run `suprnova generate-types` to regenerate.

export interface HomeProps {
  title: string;
  message: string;
  count: number;
  tags: Array<string>;
  avatar_url: string | null;
}
```

フロントエンドのフレームワークにかかわらず、同じやり方で消費します - `import type`の行は、Svelte、React、Vueのいずれでも同一です。

```svelte
<!-- frontend/src/pages/Home.svelte（デフォルト スキャフォルド） -->
<script lang="ts">
  import type { HomeProps } from '../types/inertia-props'

  let { title, message, count, tags, avatar_url }: HomeProps = $props()
</script>

<h1>{title}</h1>
<p>{message} - {count} items</p>
{#if avatar_url}<img src={avatar_url} alt="" />{/if}
```

Reactと Vueの同等物については、[ページ コンポーネント](frontend-pages.md)を参照してください。

## 型の対応

| Rust | TypeScript | 備考 |
|---|---|---|
| `String`, `&str` | `string` | |
| `i8`..`i128`, `u8`..`u128`, `isize`, `usize`, `f32`, `f64` | `number` | 数値のプリミティブはすべて`number`へ集約されます |
| `bool` | `boolean` | |
| `Option<T>` | `T \| null` | |
| `Vec<T>` | `Array<T>` | プロップのジェネレーターは`Array<T>`を出力します。ルートのジェネレーターは、フォームリクエストのフィールドに対して`T[]`を出力します |
| `HashMap<K, V>`, `BTreeMap<K, V>` | `Record<K, V>` | |
| `Field<T>`（`#[derive(Data)]`から） | `field?: T \| null` | Fieldは、通信上ではオプションです |
| `Prop<T>`（lazy / deferred） | `field?: T` | レイジープロップは、`null`側を省きます |
| それ以外すべて | そのままの識別子 | 下の「カスタム型」を参照してください |

## カスタム型

ビジタは、上の表にあるプリミティブを認識します。それ以外のすべては、そのままのRustの型名として出力されます。そこから、2つの結果が導かれます。

**入れ子になった構造体が自分自身のインターフェースを持つのは、`InertiaProps`か`Data`をderiveしている場合だけです。** 素の`#[derive(Serialize)]`構造体は、ジェネレーターにとって見えない存在です - 出力されるインターフェースはその名前を参照しますが、宣言そのものは生成されません。

```rust
use serde::Serialize;
use suprnova::{Data, InertiaProps};

#[derive(Serialize)]
pub struct Address {  // 拾われない - InertiaProps/Dataのderiveがない
    pub street: String,
    pub city: String,
}

#[derive(Data)]      // あるいはInertiaProps - どちらでも動く
pub struct Company {
    pub name: String,
    pub address: Address,
}

#[derive(InertiaProps)]
pub struct ProfileProps {
    pub user_name: String,
    pub company: Company,
}
```

生成される出力:

```typescript
export interface Company {
  name: string;
  address: Address;          // 宙に浮いている - Addressのインターフェースは出力されない
}

export interface ProfileProps {
  user_name: string;
  company: Company;
}
```

修正するには、`Address`に`#[derive(Data)]`（あるいは`InertiaProps`）を追加してください。実行時のシリアライズの振る舞いは、入れ子になった構造体でのderiveの選び方に左右されません - `serde_json`はそれでも構造体を正しく出力します - しかし、TypeScript側は明示的な宣言を必要とします。

**カスタム型のジェネリック引数は再帰的にたどられません。** `chrono::DateTime<Utc>`、`uuid::Uuid`、`rust_decimal::Decimal`、そしてderiveしていない独自の型はすべて、そのままの先頭の識別子（`DateTime`、`Uuid`、`Decimal`）として出力されます。これらは通信上ではJSON文字列にシリアライズされますが、TypeScriptの宣言はそれを語りません。これに対処する方法は2つあります。

```typescript
// frontend/src/types/runtime-types.ts - 生成されたファイルの隣に手書きする
export type DateTime = string;        // chrono::DateTime<_>はRFC 3339としてシリアライズされる
export type Uuid = string;
export type Decimal = string;         // serde_withのデフォルト。rust_decimal::Decimal
```

その上で`tsconfig.json`では、`include`のglobを通じてそれらが確実に取り込まれるようにしてください。あるいは、必要な場所で`import type { DateTime } from './runtime-types'`としてください。フレームワークはこれらの型エイリアスを代わりに出荷しません。正しい選択（`string`か`number`かブランド型か）は、あなたが有効にしたserdeのフィーチャーフラグに依存するからです。

## ジェネリック構造体

ジェネリックなRustの構造体は、ジェネリックなTypeScriptのインターフェースになります。

```rust
use suprnova::{Data, data::Field};

#[derive(Data)]
pub struct Paginated<T>
where
    T: serde::Serialize + for<'de> serde::Deserialize<'de>,
{
    pub items: Vec<T>,
    pub total: usize,
    pub cursor: Field<String>,
}
```

```typescript
export interface Paginated<T> {
  items: Array<T>;
  total: number;
  cursor?: string | null;
}
```

`where`句は落とされます - TypeScriptのジェネリクスは、消費する側で別途指定しない限り、制約を持ちません。

## 入力と出力に分かれたインターフェース

`#[derive(Data)]`構造体が`#[data(input_only)]`、`#[data(output_only)]`、`#[data(lazy)]`のフィールドを混在させている場合、2つのインターフェースが出力されます - 出力側の形（フロントエンドが受け取るもの）と、それに対応する`<Name>Input`（送り返すもの）です。

```rust
use suprnova::Data;
use suprnova::data::Field;
use suprnova::inertia::Prop;
use validator::Validate;

#[derive(Data, Validate)]
pub struct UserDto {
    pub id: i64,
    pub name: String,

    #[data(input_only)]
    #[validate(length(min = 8))]
    pub password: String,

    #[data(output_only)]
    pub computed_handle: String,

    pub bio: Field<String>,

    #[data(lazy)]
    pub favorite_song: Prop<String>,
}
```

両方を出力します。

```typescript
export interface UserDto {              // サーバー → クライアント
  id: number;
  name: string;
  computed_handle: string;
  bio?: string | null;
  favorite_song?: string;
}

export interface UserDtoInput {         // クライアント → サーバー
  id: number;
  name: string;
  password: string;
  bio?: string | null;
}
```

`Prop`フィールドは、その性質上出力専用であるため、`lazy`が明示されていない場合でも、入力側の型からは取り除かれます。`#[data(...)]`フラグの全体と、その執筆側のセマンティクスについては、[データ オブジェクト](data.md)を参照してください。

## 型安全なルート

`--routes`を付けると、このコマンドは`src/routes.rs`から生成される2つ目のファイル、`frontend/src/types/routes.ts`を書き出します。これは、バックエンドのモジュールツリーをそのままなぞるメソッドの形を持つ`controllers`オブジェクトと、`.name(...)`をキーとする`routes`のルックアップを公開します。

```rust
// src/routes.rs
use suprnova::routes;

routes! {
    get!("/", controllers::home::index).name("home"),
    get!("/users", controllers::user::index).name("users.index"),
    get!("/users/{id}", controllers::user::show).name("users.show"),
    post!("/users", controllers::user::store).name("users.store"),
}
```

```typescript
// frontend/src/types/routes.ts
import type { Method } from '@inertiajs/core';

export interface RouteConfig<TData = void> {
  url: string;
  method: Method;
  data?: TData;
}

export interface UserShowParams {
  id: string;
}

export const controllers = {
  home: {
    index: (): RouteConfig => ({ url: '/', method: 'get' }),
  },
  user: {
    index: (): RouteConfig => ({ url: '/users', method: 'get' }),
    show: (params: UserShowParams): RouteConfig =>
      ({ url: `/users/${params.id}`, method: 'get' }),
    store: (): RouteConfig => ({ url: '/users', method: 'post' }),
  },
} as const;

export const routes = {
  'home': controllers.home.index,
  'users.index': controllers.user.index,
  'users.show': controllers.user.show,
  'users.store': controllers.user.store,
} as const;
```

`RouteConfig`は、Inertia 3の`UrlMethodPair`インターフェースを満たすように意図的に形作られています。そのため、アダプターなしで`router.visit`、`useForm`の`submit`、`<Link href={...}>`にそのまま収まります。

```ts
import { router } from '@inertiajs/svelte'   // あるいは /react、/vue
import { controllers, routes } from '../types/routes'

router.visit(controllers.home.index())
router.visit(controllers.user.show({ id: '42' }))
router.visit(routes['users.show']({ id: '42' }))
```

パスにパラメータがある場合（`/users/{id}`）、生成される関数は型付きの`Params`オブジェクトを要求します - TypeScriptは、欠けているキーやタイプミスをコンパイル時に捕まえます。

## メッセージキー

アプリが`lang/`のカタログツリーを持っている場合、ジェネレーターは`frontend/src/types/lang-keys.ts`も書き出します - フロントエンドが解決できるすべてのFluentメッセージidの、`MessageKey`という文字列リテラルのユニオン型です。スターターキットの`t()`ラッパーは、そのキー引数を`MessageKey`として型付けするため、タイプミスや削除済みのキーは、コンポーネントを指し示すTypeScriptのエラーになります - `inertia-props.ts`がプロップについて果たしているのと同じ約束を、翻訳にまで広げたものです。

idは`lang/<APP_LOCALE>/*.ftl`から来て、そのロケールに設定されたフォールバック元のロケール（`APP_LOCALE_PARENTS`）にまたがってユニオンされます - そのため、上書きする文字列だけを持つデルタ形式のカタログでも、配信される、チェーンで平坦化されたカタログが運ぶキー集合の全体を生成します。`APP_FALLBACK_LOCALE`は意図的に含まれて*いません* - 配信されるカタログも、末端のフォールバックを平坦化しないため、このユニオン型は、ブラウザが取得する1つのカタログが実際に解決できるものを、正確に記述しなければなりません。チェーンそのものについては、[ローカライゼーション](localization.md)を参照してください。

このファイルは、他の2つと同じ規則に従います - 固定されたパス、自動生成のヘッダー、決定的にソートされた出力、そして絶対に手で編集しないこと、です。どの`.ftl`ファイルもidを一つも生まない場合、このファイルは空のまま出力されるのではなく、削除されます - `MessageKey`をインポートしているキットは、カタログが再びidを持つまでコンパイルに失敗するようになります。このパイプラインの他のあらゆるずれと同じように、それは目立つ形で起こります。

## 実行されるタイミング

`suprnova serve`は、起動時に`generate-types`を実行します。デフォルトの流れ:

```
suprnova serve
  ├─ src/ を走査してInertiaProps / Data構造体を探す → inertia-props.ts
  ├─ src/routes.rs を走査してルート定義を探す       → routes.ts
  ├─ lang/ を走査してFluentメッセージidを探す       → lang-keys.ts
  ├─ バックエンドを起動する
  └─ Viteを起動する
```

両方をスキップするには`--skip-types`を渡してください。バックエンドがホットリロード中で、サーバーを再起動せずに新しい宣言が欲しいときは、いつでも`suprnova generate-types`を手動で再実行してください。

### 出力をコミットし、クリーンな差分を期待する

`inertia-props.ts`は、コミットされることを前提としています - それによってレビュアーは、プロップの契約の変更を、それを引き起こしたRustと同じ差分の中で見られますし、CIがフロントエンドの型チェックのためにRustのツールチェーンを必要とすることもなくなります。

生成は決定的です - 同じソースは、どのマシンでも、ファイルがディスク上でどんな順序にあっても、バイト単位で同一の出力を生みます。そのため、何も変わっていない実行は差分を示さず、実際に見える差分はすべて本物の契約の変更です。（かつては常にそうではありませんでした - ソートがハッシュの反復順序から種を得ていたため、実行するたびにインターフェースが入れ替わってしまっていたのです。）

2つの帰結を、心に留めておく価値があります。

- **そのファイルを、他の何かが編集してはいけません。** コンポーネントが、ジェネレーターが出力しない型をインポートしている場合、次の`generate-types`はそれを削除し、フロントエンドはコンパイルできなくなります。修正は、出力を手で編集することではなく、Rust側でその型を宣言することです。
- **Rustのルートを持たないページには、生成される型がありません**。その裏に`#[derive(InertiaProps)]`の構造体が存在しないからです。それを所有するハンドラができるまでは、コンポーネントの中でプロップをローカルに宣言してください。

## Suprnovaが異なる設計を選んだ理由

LaravelはInertiaのための型生成を出荷していません。PHPは動的型付けであり、契約を抽出できるものがサーバー側に何もないからです。InertiaのLaravelコミュニティは、PHPDocやDocBlockの注釈を読み取るユーザーランドのツール（Laravel Typed Inertia、Wayfinder）で、その隙間を埋めてきました。

Suprnovaは、型の情報をコンパイル時に、そしてディスク上に持っているため、それを直接抽出します。JSONのシリアライズを制御しているのと同じ`#[derive(InertiaProps)]`や`#[derive(Data)]`が、TypeScriptの出力も駆動します - 唯一の信頼できる源であり、serdeが実際に出力するものとずれることは決してありません。
