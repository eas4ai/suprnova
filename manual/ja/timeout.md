# リクエスト タイムアウト

`TimeoutMiddleware` は、すべてのHTTPリクエストに厳格な期限を課します。遅いハンドラ - ハングしたデータベースクエリ、応答しないアップストリームAPI、どこかのホットパスにある偶発的な無限ループなど - は、そうでなければ、クライアントが諦めるかOSがプロセスを終了させるまで、hyperのコネクションを開いたままにしてしまいます。タイムアウトミドルウェアはその待ち時間に上限を設け、進行中のハンドラをドロップし、`503 Service Unavailable` を返すことで、アプリケーションがコネクションをサイレントに漏らし続けるのではなく、オペレーターに障害を見えるようにします。

パブリックインターネットとやり取りする何か、サードパーティAPIへファンアウトする何か、あるいは「今日はデータベースが遅くなるかもしれない」がごく普通に起こりうる何かを構築しているなら、これに手を伸ばしてください。

```rust
use suprnova::{global_middleware, TimeoutMiddleware};

pub async fn register() {
    // すべてのHTTPルートが30秒の上限を得る。
    global_middleware!(TimeoutMiddleware::default());
}
```

この1行だけで、アプリケーション全体に、Suprnovaがデータベースの接続タイムアウトに使っているのと同じデフォルトの上限が与えられます - 一度選べば、どこにでも適用されます。ルートごとの上書きは、それぞれ1行で済みます。この章の残りでは、期限が正確に何を制限し、意図的に何を制限しないか、そしてそれがパニック境界、ストリーミングレスポンス、WebSocketとどのように相互作用するかを説明します。

## このミドルウェア

`TimeoutMiddleware` は `suprnova::TimeoutMiddleware` にあります。これは3つのコンストラクタと1つのアクセサーを公開します。

```rust
use std::time::Duration;
use suprnova::TimeoutMiddleware;

let default_30s = TimeoutMiddleware::default();
let custom      = TimeoutMiddleware::new(Duration::from_millis(2_500));
let whole_secs  = TimeoutMiddleware::seconds(5);

assert_eq!(default_30s.duration(), Duration::from_secs(30));
assert_eq!(custom.duration(),      Duration::from_millis(2_500));
assert_eq!(whole_secs.duration(),  Duration::from_secs(5));
```

`TimeoutMiddleware::default()` は30秒の期限を使います。この数字は適当に決めたものではありません - `DB_CONNECT_TIMEOUT`（これも30秒です）と一致させることで、新しいデータベースコネクションを待ってブロックされているリクエストと、ハンドラの内部でブロックされているリクエストが、1つの上限を共有するようにしています。片方を上げるなら、もう片方も上げてください。

`TimeoutMiddleware::seconds(n)` は、よくある「丸い秒数」の場合の省略記法です。`TimeoutMiddleware::new(Duration::…)` は、ミリ秒単位の精度が必要なとき（200msを超えてはならない内部のヘルスチェック、50msの予算を持つ合成プローブなど）のための逃げ道です。

## グローバルにインストールする

グローバルなタイムアウトは、正しい出発点です: 誰かが追加を覚えておく必要なく、すべてのルートに上限を与えます。他のグローバルミドルウェアと並べて、`bootstrap.rs` にインストールしてください。

```rust
// src/bootstrap.rs
use suprnova::{
    global_middleware, CorsConfig, CorsMiddleware, DB, RequestIdMiddleware, TimeoutMiddleware,
};
use crate::middleware::LoggingMiddleware;

pub async fn register() {
    DB::init().await.expect("database connect");

    // 実行順序が重要: まずrequest-id（タイムアウトのログがそれを運べるように）、
    // 次にlogging（遅いリクエストもそれでも観測されるように）、そして
    // timeout自体、という順。
    global_middleware!(RequestIdMiddleware);
    global_middleware!(LoggingMiddleware);
    global_middleware!(TimeoutMiddleware::default());

    global_middleware!(CorsMiddleware::new(
        CorsConfig::allow_origins(["https://app.example"]),
    ));
}
```

順序が重要なのは、グローバルミドルウェアが登録順にチェーンの残りをラップするからです: `RequestIdMiddleware` は入りの経路で最初に、出の経路で最後に実行されるため、タイムアウトが `503` を発火させる間もリクエストIDはスコープの中にあります。タイムアウトをloggingより前に置くと、結局は完了した遅いリクエストがアクセスログから隠れてしまいます。

## ルートごとに絞り込む

30秒というグローバルな上限は、意図的に緩めに設定されています - これは暴走するハンドラを捕まえるためにあり、SLAを強制するためのものではありません。特定のエンドポイントがより速く失敗すべき場合は、ルートごとのタイムアウトを取り付けてください。

```rust
use suprnova::{Router, TimeoutMiddleware};

Router::new()
    // パブリックなレポートエンドポイント: 5秒以内に応答しなければならない。
    // ブロックするより、503を返してクライアントにリトライさせたい。
    .get("/report", controllers::report::show)
    .middleware(TimeoutMiddleware::seconds(5));
```

ルートグループにも、より厳しいタイムアウトを取り付けられます。これは、各リクエストが速くあるべきパブリックAPIのための典型的な形です。その一方でアプリの残りの部分は、30秒のデフォルトを保ちます。

```rust
use suprnova::Router;
use suprnova::TimeoutMiddleware;

Router::new()
    .group("/api", |r| {
        r.get("/users",       controllers::api::users::index)
         .post("/users",      controllers::api::users::create)
         .get("/users/{id}",  controllers::api::users::show)
    })
    .middleware(TimeoutMiddleware::seconds(3));
```

### グローバルは上限であり、ルートごとの設定は厳しくすることしかできない

グローバルミドルウェアは、ルートミドルウェアの**外側**で実行されます。チェーンは内側から外側へ包み込みます。

```
グローバルタイムアウト（30秒） → ルートタイムアウト（3秒） → ハンドラ
```

どちらの `tokio::time::timeout` フューチャーも作動していますが、内側のものは期限が短いため先に発火します。そのため、ルートごとのタイムアウトは、ルートをグローバルより*厳しく*することしかできず、緩めることは決してできません。

1つのエンドポイントが、正当な理由でグローバルなデフォルトより*長く*実行される必要がある場合 - 遅いレポート、大きなアップロード、ロングポーリングのフォールバックなど - には、2つの選択肢があります。

1. グローバルな値を上げる。最も単純ですが、他のすべてのルートについても上限を緩めてしまいます。
2. 長時間かかるエンドポイントを*除外した*ルートグループにグローバルミドルウェアのスコープを絞り、その遅いルートには別個のタイムアウト（あるいはタイムアウトなし）を取り付ける。これなら、他のあらゆる場所では厳格なデフォルトが保たれます。

2番目の選択肢は、1つの例外的なケースに対する正しい形です。1番目が正しいのは、作業のクラス全体がもっと余裕を必要とするときです。

## 期限が実際に制限するもの

期限は、`next(request)` が返すフューチャーと競争します。そのフューチャーは、あなたのハンドラが `HttpResponse` を返した瞬間に解決します - ボディのストリーミングが終わったときではありません。この違いは、決して軽視できません。

- **通常のハンドラ**は、戻る前に本体全体を組み立てるため、期限は実質的にハンドラの合計時間を制限します。JSONのリストをシリアライズしたり、Inertiaのページをレンダリングしたり、HTMLレスポンスを組み立てたりするハンドラは、作業が終わるまでフューチャーを保持し続けます。
- **ストリーミングレスポンス**（`HttpResponse::sse(...)`、`HttpResponse::stream_bytes(...)`）は、遅延ボディを伴って*即座に*戻ります。hyperがストリームからバイトを取り出し始める時点で、ミドルウェアチェーンはすでに完了しているため、期限はボディの寿命を決して観測しません。設計上、SSEのイベントストリームは、30秒のタイムアウトの下でも何時間も開いたままでいられます - ストリーミングのモデルについては[Server-Sent イベント](sse.md)を参照してください。
- **WebSocketのアップグレード**は明示的にスキップされます。次の節を参照してください。

これは、あなたがほぼ確実に望んでいる振る舞いです。長寿命のSSEストリームを30秒のタイムアウトでラップしてしまえば、フレームワークは30秒ごとにストリームの途中でコネクションを引き裂いてしまい、その機能は使い物にならなくなってしまいます。

## WebSocketの例外

ミドルウェアは、期限を作動させる前にリクエストを検査します。

```rust
if is_websocket_upgrade(request.headers()) {
    return next(request).await;
}
```

`Upgrade: websocket` を持つリクエストは、タイムアウトを完全にスキップします。このチェックはトークンの値について大文字小文字を区別しません（`WebSocket`、`websocket`、`WEBSOCKET` はすべて一致します）。そして、`Upgrade: websocket` を伴わない裸の `Connection: upgrade` は、WSアップグレードとして扱われ*ません* - それは通常どおりタイムアウトを通過します。

現在のところ、WebSocketのアップグレードは、グローバルミドルウェアをまったく実行しない別個のサーバー経路を取ります。そのため、このガードは多層防御です - いつかそれが変わる日が来ても、タイムアウトが長寿命の双方向チャネルを制限してしまうことがないようにしています。アップグレードがどのようにディスパッチされるか、そして接続されたソケットの寿命については、[WebSocket](websockets.md)を参照してください。

## 期限に達すると何が起きるか

ハンドラが完了する前に `tokio::time::timeout` が経過すると、ミドルウェアは順に3つのことを行います。

1. **進行中のハンドラのフューチャーをドロップします。** そのフューチャーは `timeout` コンビネーターの内部でポーリングされていました。コンビネーターは `Err(Elapsed)` を返し、フューチャーは最後に中断されていた場所でドロップされます。
2. ルートのパスとタイムアウトの長さ（ミリ秒単位）を伴う**警告をログに記録します**。

   ```
   WARN suprnova::timeout request exceeded its timeout; returning 503 Service Unavailable
       route=/report timeout_ms=5000
   ```

   このログは `WARN` であるため、通常のリクエストの `INFO` アクセスログとは別に、デフォルトでオペレーターのダッシュボードに表面化します。
3. プレーンテキストのボディを伴って**`503 Service Unavailable` を返します**。

   ```
   HTTP/1.1 503 Service Unavailable
   Content-Type: text/plain
   Content-Length: 42

   Service Unavailable: request timed out
   ```

この503は `Err(HttpResponse::…)` でラップされているため、他のあらゆるミドルウェアによって拒否されたリクエストと同じように、チェーンの残りをショートサーキットします。外側のミドルウェア（logging、request-id、CORS）は、それでもレスポンス後側の処理を実行するため、レスポンスは正しいヘッダーを伴って送出されます。

### なぜ503であり504ではないのか

`504 Gateway Timeout` が正しいコードなのは、*あなた自身*がゲートウェイであり、*アップストリーム*がタイムアウトした場合です。`503 Service Unavailable` が正しいコードなのは、*このサービス自身*が時間内にレスポンスを生成できなかった場合です。タイムアウトミドルウェアは*自分自身の*ハンドラを制限しているので、503を返します。別の形（JSONボディ、別のステータス、機械可読なコードなど）が欲しい場合は、タイムアウトの周りに自分自身の外側のミドルウェアをラップし、その503のレスポンスを変換してください。

## キャンセル安全性

期限が経過すると、ハンドラのフューチャーは、現在の `.await` の地点で**ドロップされます**。これは通常のTokioのキャンセルです。クライアントがリクエストの途中でコネクションを閉じたときも、同じことが起きます。await境界をまたいで保持されているものは、その `Drop` 実装によって解放されます。

- **データベーストランザクション**はロールバックします。SeaORMの `DatabaseTransaction` は、背後のコネクションに対して `ROLLBACK` を発行する `Drop` 実装を持っています。
- **MutexとRwLockのガード**は解放されます。標準ライブラリや `parking_lot` のガードはドロップ時に解放され、別の待機者が即座にそれを取得できます。
- **ファイルハンドル**はクローズします。`tokio::fs::File` がドロップされると、OSレベルのディスクリプタが解放されます。
- **ネットワークコネクション**は、プールのドロップ時の振る舞いに応じて、プールへ戻されるかクローズされます。

結果として、タイムアウトしたハンドラは何も宙に浮いたまま残しません - オペレーターは503を目にし、データベースはロールバックを目にし、次のリクエストはきれいなプールを目にします。

### キャンセル*されない*もの

`tokio::spawn` でリクエストから切り離したものは、すべて**デタッチされています**。生成されたタスクは、リクエストのフューチャーではなくランタイムの上で生きているため、リクエストをドロップしてもそれらは止まりません。これは、次のようなコードを書いたときに重要になります。

```rust
pub async fn webhook(req: Request) -> Response {
    let payload: WebhookPayload = req.json().await?;

    // 投げて忘れるバックグラウンド作業。リクエストがタイムアウトしても生き延びる。
    tokio::spawn(async move {
        if let Err(e) = process_webhook(payload).await {
            tracing::error!("webhook processing failed: {e}");
        }
    });

    Ok(HttpResponse::new().status(204))
}
```

リクエストが `spawn` の行が実行される*前に*タイムアウトすれば、そのspawnは決して起こりません。リクエストがspawnの*後に*タイムアウトすれば、バックグラウンドタスクは実行され続けます - それはリクエストと一緒にキャンセルされません。これはwebhook風の作業にとってはほとんどいつも望ましいことですが、それはハンドラ内部の長い `.await` の後の後始末が実行される保証は**ない**ということも意味します。

```rust
pub async fn upload(req: Request) -> Response {
    let temp_path = save_to_temp(&req).await?;

    // これがタイムアウトの原因なら、以下の後始末は実行されない。
    let processed = long_running_processing(&temp_path).await?;

    // タイムアウトの下では保証されない。
    tokio::fs::remove_file(&temp_path).await?;

    Ok(HttpResponse::json(serde_json::to_value(&processed)?))
}
```

解決策はRAIIを使うことです。一時ファイルを、それを削除する `Drop` 実装を持つ構造体でラップしてください。そうすれば、ハンドラが戻るときも、エラーを返すときも、タイムアウトによって `.await` の途中でドロップされるときも、後始末は実行されます。これは、あらゆるキャンセルの源 - クライアントの切断、ランタイムのシャットダウン、パニックからの回復 - に対して適用すべき、同じ規律です。

## パニック境界との相互作用

Suprnovaのサーバーは、ミドルウェアチェーン全体を[`execute_chain_safely`](lifecycle.md)でラップしており、これは `AssertUnwindSafe(...).catch_unwind()` を使ってパニックをサニタイズされた `500 Internal Server Error` へ変換します。タイムアウトしたリクエストはパニックでは**ありません** - フューチャーはきれいにドロップされます - そのため、タイムアウトの `503` は、パニック境界を一切介さずに送出されます。

この2つの境界は、異なる失敗のモードを処理します。

| 失敗 | 境界 | ステータス | ボディ |
|---|---|---|---|
| ハンドラの `.await` が期限を超える | `TimeoutMiddleware` | `503` | `Service Unavailable: request timed out` |
| ハンドラがパニックする（`None` への `.unwrap()` など） | `execute_chain_safely` | `500` | `{"message": "Internal Server Error"}` |
| ハンドラが `Err(HttpResponse)` を返す | 通常の `Response` フロー | ハンドラが設定した通り | ハンドラが設定した通り |

どちらかを選ぶ必要はありません - 両方の境界は常にインストールされています。タイムアウトを超えた*後に*パニックするハンドラでも、それでも503を生成します（パニックが起きる前に、フューチャーはドロップされています）。タイムアウトを超える*前に*パニックするハンドラは、500を生成します。

## 運用上のチューニング

タイムアウトの値を選ぶ際の3つの考慮点です。

1. **データベースの接続タイムアウトに合わせる。** `DB_CONNECT_TIMEOUT=30`（デフォルト）であれば、30秒より短いリクエストタイムアウトは、遅い接続が完了するより前に発火してしまいます - ユーザーは、回復する機会の代わりに `503` を目にします。接続タイムアウトを上げるか、「30秒」が下限であることを受け入れてください。
2. **最も遅い正当なハンドラを考慮する。** あなたの `INFO` レベルのリクエスト所要時間のヒストグラムを見てください。遅いテール側のp99は、クロックのずれやイベントループのジッターの余裕を持って、タイムアウトより十分に下にあるべきです。健全なトラフィックに対して日常的に発火するタイムアウトは、設定ミスであり、機能ではありません。
3. **ルートごとのタイムアウトは可観測性である。** `/api/*` に `TimeoutMiddleware::seconds(3)` で絞りをかけると、劣化したAPIが、じわじわと進行するレイテンシの問題ではなく、目に見えるアラート（WARNで埋まったログ、ロードバランサーでの503）に変わります。SLAがあり、それを外したときにはっきりと失敗させたい場合に使ってください。

フレームワーク自身の統合テストは、期限を決定的に動かすために、ミリ秒単位の長さ（`TimeoutMiddleware::new(Duration::from_millis(50))`）を使っています。本番の期限は、ほとんど常に丸い秒数です。

### Suprnovaが異なる設計を選んだ理由

Laravel + PHP-FPMのデプロイでは、リクエストタイムアウトはアプリケーションの外側にあります: nginxの `proxy_read_timeout`、PHP-FPMの `request_terminate_timeout`、ロードバランサーのアイドルタイムアウトなどです。予算が使い果たされるとPHPプロセスは強制終了され、開いていた状態 - データベースコネクション、ファイルハンドル - は、次のリクエストがそのワーカーを再利用するまで漏れ続けます。

Suprnovaは、それができるからこそ、リクエストをアプリケーションの内側で制限します。ハンドラはPHPプロセスではなくTokioのフューチャーであるため、それをドロップすることは `Drop` 実装をきれいに実行します: トランザクションはロールバックし、ロックは解放され、ディスクリプタはクローズし、コネクションプールは健全なままです。503もまた、*本物のHTTPレスポンスとして*送出されます - クライアントは、アップストリームのリセットの代わりに、正しいステータスコードを目にします。

これは、このミドルウェアがTowerの `Timeout` レイヤーであろうとしない理由でもあります。Towerのレイヤーは、任意のTokioサービスに対して汎用的であり、`tower::timeout::error::Elapsed` を返しますが、呼び出し元はそれをHTTPステータスへ写し取らなければなりません。Suprnovaのミドルウェアは、自分がHTTPリクエストパイプラインをラップしていることを知っています。それは直接 `503` を返し、問題のあったルートをログに記録し、呼び出し元がそれについて考える必要なく、フレームワークのWebSocketとストリーミングの例外を尊重します。Towerのレイヤーは、汎用的なTokioサービスにとって正しいプリミティブです。HTTPリクエストにとっては、これが正しい形です。
