# ワークフロー

ワークフローは、中間状態がクラッシュ、再起動、パニックを生き延びる、永続的で長時間実行される非同期関数です。1つの作業単位が複数のステップにまたがり - それぞれが遅いかもしれず、失敗しうるかもしれず、副作用を持つかもしれない - かつ途中で進捗を失う余裕がないときに、これに手を伸ばしてください。ワークフローの本体は一度だけ走ります。各ステップの出力は永続化されます。リトライは、まだ完了していない最初のステップから再開します。作業がワンショットのジョブであれば[`Queue`](queues.md)と組み合わせ、作業がリクエストタスクの中で同期的に走るのであれば[`Bus`](bus.md)と組み合わせてください。

## クイックスタート

ワークフローとは、`Result<T, FrameworkError>` を返す非同期関数です。その本体は1つ以上の `#[workflow_step]` 関数を呼び出します。`start_workflow!` マクロを介してそれをキューに入れ、ワーカープロセスがそれをドレインします。

```rust
use suprnova::{workflow, workflow_step, start_workflow, FrameworkError};

#[workflow_step]
async fn fetch_user(user_id: i64) -> Result<String, FrameworkError> {
    Ok(format!("user:{}", user_id))
}

#[workflow_step]
async fn send_welcome_email(user: String) -> Result<(), FrameworkError> {
    // … 実際にメールを送る
    Ok(())
}

#[workflow]
async fn welcome_flow(user_id: i64) -> Result<(), FrameworkError> {
    let user = fetch_user(user_id).await?;
    send_welcome_email(user).await?;
    Ok(())
}

// ハンドラや、その他あらゆる非同期コンテキストから:
let handle = start_workflow!(welcome_flow, 123).await?;
```

このマクロは、引数をJSONへシリアライズし、`workflows` テーブルに行を挿入し、キューに入れられたインスタンスを識別する [`WorkflowHandle`](#結果を待つ) を返します。別個のワーカープロセスがその行を拾い上げ、本体を実行し、進むにつれて各ステップの出力を永続化します。

`#[workflow]` は、その関数を、完全修飾パス（`module_path::fn_name`）の下でワークフローのインベントリに集めます。同じ名前での重複登録は、`registry::assert_no_duplicates` を介してワーカーの起動を中止させます - サイレントなシャドーイングはデバッグ不可能になってしまうため、フレームワークははっきりと失敗します。

## スキーマ

ワークフローは2つのテーブルへ永続化されます: `workflows`（インスタンスごとに1行）と `workflow_steps`（`(workflow_id, step_index)` をキーとする、ステップの呼び出しごとに1行）です。フレームワークがスキーマを所有し、あなたはそれをいつ適用するかを選びます。

マイグレーションを配線する方法は2つあります。

### 生成されたマイグレーションファイル

CLIは、フレームワークのマイグレーションのコピーをあなたのアプリへスキャフォルドします。

```bash
suprnova workflow:install
suprnova migrate
```

`workflow:install` は、`src/migrations/` の下に `m_create_workflows_table.rs` と `m_create_workflow_steps_table.rs` を書き出し、それらをあなたの `Migrator` に登録します。スキーマを、他のアプリのマイグレーションと並べてバージョン管理したい場合に使ってください。

### プログラムによる登録

あるいは、フレームワークが所有するマイグレーション構造体を直接登録することもできます。

```rust
use sea_orm_migration::MigratorTrait;
use suprnova::workflow::migrations::{
    CreateWorkflowsTable, CreateWorkflowStepsTable,
};

pub struct Migrator;

impl MigratorTrait for Migrator {
    fn migrations() -> Vec<Box<dyn sea_orm_migration::MigrationTrait>> {
        vec![
            Box::new(CreateWorkflowsTable),
            Box::new(CreateWorkflowStepsTable),
        ]
    }
}
```

どちらの経路も、同一のSQLを生成します。同じ規約が [`features::migrations`](feature-flags.md) と [`payments::migrations`](payments.md) でも使われています。

## ワーカーを実行する

スキャフォルドされたアプリでは、ワーカーはバイナリの `workflow:work` サブコマンドによって開始されます。

```bash
suprnova workflow:work
```

ワーカーは、あなたのHTTPサーバーと同じブートストラップを実行するため、`bootstrap()` に登録されたオブザーバー、リスナー、コンテナのバインディングは、ワークフローのステップからも見えます。`SIGINT` / `SIGTERM` を受けると、ワーカーは新しい行の確保を止め、終了する前に、進行中のすべてのワークフローを待ちます - きれいなシャットダウンでは、ステップの途中で孤児になるワークフローはありません。

確保の経路（`claim_next_workflow`）は、`workflows` テーブルに対して `FOR UPDATE SKIP LOCKED` を使うため、ワーカープロセスは**Postgresを必須とします**。SQLiteとMySQLは、テストや、キューへの投入/永続化の経路では機能しますが、コネクションがPostgresでない場合、ワーカーデーモンは最初の確保の時点でエラーとともに終了します。

## 設定

5つの環境変数がワーカーを調整します。範囲外の値は、`.env` のタイプミスがデーモンを壊さないよう、`tracing::warn!` を伴って安全な最小値に切り詰められます。

| 変数 | デフォルト | 注記 |
|---|---|---|
| `WORKFLOW_POLL_INTERVAL_MS` | `1000` | 空振りの確保ラウンドの間のスリープ |
| `WORKFLOW_CONCURRENCY` | `4` | ワーカーあたり同時実行するワークフローの最大数（最小1） |
| `WORKFLOW_LOCK_TIMEOUT_SECS` | `30` | 別のワーカーが再取得できるようになるまでのリース期間 |
| `WORKFLOW_MAX_ATTEMPTS` | `3` | ワークフローごとの試行回数の予算（最小1） |
| `WORKFLOW_RETRY_BACKOFF_SECS` | `5` | 線形バックオフ: `attempts * value`（最小0） |

（envからパースするのではなく）コードの中で構築するプログラムによる設定については、`WorkflowWorker` を組み立てる前に `WorkflowConfig::validate()` を呼び出し、同じ不変条件について早期に失敗させてください。

## クラッシュリカバリ

3層の保護が、ワーカーの障害によってワークフローが行き詰まってしまうことを防ぎます。

**パニック境界。** ワークフローの本体は `AssertUnwindSafe(...).catch_unwind()` の内側で実行されます。どのステップでのパニックも捕捉され、そのペイロードはエラーカラムに取り込まれ、その行は `Err` が返された場合と同じリトライ/失敗の会計処理を通過します。この境界がなければ、パニックは決着の経路を素通りしてしまい、行を永遠に `status='running'` のまま残してしまいます。

**リースのハートビート。** `WORKFLOW_LOCK_TIMEOUT_SECS` より長く生きる長時間実行のステップは、そうでなければ、自分の足元でリースが失効してしまいかねません。ワーカーは、本体が完了するまで、ロックタイムアウトの半分の間隔で `locked_until` をリフレッシュするハートビートタスクを生成します。このハートビートはドロップ時に中断されるため、`?` によるリターンが更新タスクを漏らし、誰も実行していないワークフローのリースを凍結させてしまうことはありません。

**失効したリースの再取得。** ワーカーがロックを一度も解放せずに死んだ場合（ハードキル、ホストのクラッシュ、カーネルOOM）、その行は `locked_until` が過ぎるまで `status='running'` のままです。確保のクエリは、そうした行を明示的に拾い上げます: リースが失効した `running` 状態のワークフローはすべて、次のラウンドで別のワーカーによって確保可能になり、`attempts` がインクリメントされます。クラッシュリカバリは自動です - スクリプトを書く必要も、覚えておくべき管理コマンドもありません。

## 配信のセマンティクス - 少なくとも1回

ステップの本体は、**少なくとも1回**のセマンティクスで実行されます。ステップは、2つの状況で複数回実行されることがあります。

1. **`Err` が返された場合** - ワークフローは再度キューに入れられます。リトライ時には失敗したステップが再び実行され、それより前のステップはすべてキャッシュから再生されます。
2. **副作用の後、`mark_step_succeeded` がコミットされる前にクラッシュした場合** - リースが失効し、別のワーカーが再取得し、そのステップインデックスにキャッシュされた出力がないことを確認し、本体を再び実行します。

フレームワークはステップの**出力**を永続的に保存しますが、副作用そのものを観測することはできません。ステップの本体をべき等にする責任は、あなたにあります。ほとんどすべてのケースで機能する、2つのパターンがあります。

**条件付き書き込み。** `INSERT ... ON CONFLICT DO NOTHING`、べき等性キーのカラム、あるいは `seen_event_id` マーカーを使ってください。すでにスコープ内にあるデータから、安定したステップごとのキーを導出します: ワークフローの入力引数に、リテラルなステップタグ（`("wf-charge", customer_id)`）を加えたもので十分です。なぜなら、同じ引数はリトライをまたいで同じワークフローの行に対応づくからです。

**外部のべき等性キー。** ほとんどのサードパーティAPI（Stripe、SES、SQS）は `Idempotency-Key` ヘッダーを受け付けます。リトライされたリクエストがプロバイダー側で重複排除されるよう、ワークフローの入力にステップローカルなタグ（`format!("wf-charge-{}", customer_id)`）を加えて導出したキーを渡してください。

`Ok` を返したステップが2度目に実行されることはない、と想定しては**いけません** - クラッシュは、別のホストでの再起動の後を含め、その後に続くどのワーカーの上にも、その2度目の実行を落としうるのです。ステップの本体を包む妥当なラッパーである `Idempotency::once`、`Idempotency::commit_on_success`、`Idempotency::remember` については、[べき等性](idempotency.md)の章を参照してください。

## 決定性の契約

ワークフローは、リプレイをまたいで決定的でなければなりません。各ステップは `(step_name, step_index)` をキーとし、フレームワークはそのシリアライズされた入力を出力と一緒にキャッシュします。同じインデックスのステップが、異なるシリアライズされた入力でリプレイされた場合、フレームワークは、以前の入力からのキャッシュされた出力を返して破損を覆い隠すのではなく、エラーを返します。

実際には、これは次を意味します。

- `#[workflow_step]` の外側で、`Utc::now()`、`rand::random()`、あるいはその他の非決定的な源に基づいて分岐してはいけません。ステップの本体はそれらを自由に呼び出せます - その結果はステップの出力キャッシュに取り込まれます。
- ステップを条件付きで挿入してはいけません。リトライが、あるインデックスより前で異なる数のステップに当たった場合、ステップ名の不一致エラーになります。分岐のロジックはステップの内部に置いてください。
- ステップをリネームせずに、デプロイの間でステップの引数の形を変えてはいけません。リネームは `step_name` を変更し、そのステップのキャッシュを最初からやり直させます。

## 結果を待つ

`WorkflowHandle` は、呼び出し元がその行をポーリングしたり、完了を待ったり、シリアライズされた出力を取得したりできるようにします。

```rust
use std::time::Duration;
use suprnova::{FrameworkError, WorkflowStatus};

let handle = start_workflow!(welcome_flow, 123).await?;

match handle.wait_with_timeout(Duration::from_secs(30)).await {
    Ok(WorkflowStatus::Succeeded) => { /* 完了 */ }
    Ok(WorkflowStatus::Failed) => { /* 永続化されたエラーカラム */ }
    Ok(_) => unreachable!("wait_* only returns terminal status"),
    Err(FrameworkError::Internal { message }) if message.contains("Timed out") => {
        // ワークフローはまだ実行中。非同期UXへフォールスルーする。
    }
    Err(other) => return Err(other),
}
```

`wait()` は無期限にポーリングします - 永遠にブロックしても構わないテストや、短命なスクリプトでのみ使ってください。HTTPリクエストの経路では、`wait_with_timeout(Duration)` は、背後のステータスクエリが止まってしまった場合でも、内部のポーリングループに対して常に勝ちます。タイムアウトエラーは、ワークフローをキャンセル**しません** - ワーカーは続行し、`handle.status().await` は後で最新の状態を返します。

デフォルトが合わない場合は、`wait_with_options(Some(poll), Some(deadline))` が両方のつまみを公開します。

型付きの出力については、ワークフローに `T: Serialize + DeserializeOwned` を返す型を定義し、`handle.output::<T>().await?` を呼び出してください。生のJSONは `output_raw()` を介して利用できます。

## ステップキャッシュの詳細

ステップキャッシュは、**ステップ名 + ステップインデックス**をキーとします。ステップの最初の呼び出しは、その入力JSONを永続化し、本体を実行し、成功時には出力JSONを永続化します。同じインデックスでのリプレイは:

- ステップが `succeeded` であり、リプレイされた入力がキャッシュされた入力と一致する場合、キャッシュされた出力を返します。
- 入力が異なる場合はエラーを返します（決定性の保護機構）。
- ステップが `running` または `failed` の場合は本体を再実行します（返すべきキャッシュされた出力がありません）。

ステップインデックスは、ワークフローコンテキストごとの `AtomicI32` によって割り当てられるため、順序はあなたのワークフロー本体が行う呼び出しによって決まります。リトライ時に同じインデックスで異なるステップを生み出す分岐は、下流のステップをサイレントに破損させるのではなく、ステップ名の不一致エラーとして表面化します。

出力と入力はJSON TEXTとして保存されるため、すべてのステップの戻り値の型と引数は `Serialize + DeserializeOwned` でなければなりません。

## ヘルパーからワークフローコンテキストを検知する

`WorkflowContext::is_active()` は、現在のタスクがワークフローの下で実行されているかどうかを返します。ワーカーの内側と外側で振る舞いを変える必要があるヘルパーから使ってください - 例えば、ワークフローが存在するときだけワークフロータグを付けるロガーなどです。

```rust
use suprnova::workflow::WorkflowContext;

fn maybe_workflow_tagged(message: &str) -> String {
    if WorkflowContext::is_active() {
        format!("[workflow] {message}")
    } else {
        message.to_string()
    }
}
```

ワークフローの外側（テストやハンドラから直接呼び出された場合）でも、`#[workflow_step]` 関数はそれでも実行されます - `WorkflowContext::current()` は単に `None` を返し、本体は永続化なしに実行され、ステップはキャッシュを完全にバイパスします。これは意図的なものです: ワーカーを立ち上げることなく、ステップ関数を個別にテスト可能にします。

### Suprnovaが異なる設計を選んだ理由

Laravelには、第一級のワークフロープリミティブがありません - ジョブが最も近い存在ですが、それらは最後に成功したステップから再開するのではなく、ジョブ本体全体を再実行することでリトライします。Suprnovaは、ワークフローを別個の構成要素として出荷しています。なぜなら、Tokioは「1時間、遅い非同期関数にチェックインしたまま留まる」というパターンを安価にし、そしてステップレベルの永続化は、複数ステップにわたる外部とのやり取り（顧客のプロビジョニング、2つの決済プロバイダーをまたぐサーガの実行、複数の上流APIを含むレポートの生成など）に対する正しい抽象化だからです。

この設計は、キューよりも[DBOS](https://www.dbos.dev/)やCadence/Temporalに近いものです: 永続的な状態、決定的なリプレイ、明示的なステップの境界。Temporalとの違いは運用上の重さです - 別個に実行すべきワークフローサービスは存在しません。ワーカーは、あなたのアプリケーションデータベースに対する、単なる `suprnova workflow:work` です。

## 補足

- ステップの本体は、任意の `Serialize + DeserializeOwned` 型を返せます。`()` というユニット型は、副作用のためだけに存在するステップで機能します。
- ワークフローコンテキストの外側で呼び出された `#[workflow_step]` 関数は、インラインで実行されます - キャッシュもリプレイもありません。これが、テストがステップの本体を直接動かす方法です。
- ステップキャッシュは `(step_name, step_index)` をキーとします。ステップをリネームする（あるいは呼び出しの順序を変える）と、次のリプレイでそのステップのキャッシュはリセットされます。
- `start_workflow!` は、シリアライズ可能な引数の任意のタプルを受け付けます。タプルは引数の順序を保つため、位置引数のリネームは安全です。引数の型を変えることは、進行中のあらゆるワークフローに対するスキーマの破壊です。
- フレームワークの[可観測性](observability.md)レイヤーは、あらゆる決着の経路で、ワーカーの構造化ログ（`worker_id`、`workflow_id`、`attempts`、`max_attempts`）を捕捉するため、あなたはステップに計装を施さなくても、本番でリトライの予算を監査できます。
