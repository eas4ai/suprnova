# Tipos de TypeScript

`suprnova generate-types` examina tu código fuente en Rust en busca de
structs `#[derive(InertiaProps)]` y `#[derive(Data)]`, y escribe
declaraciones de TypeScript que el frontend puede importar. Ejecútalo
después de cambiar props o rutas; `suprnova serve` lo ejecuta por ti en
el arranque a menos que pases `--skip-types`.

## Qué se genera

Tres archivos, escritos en `frontend/src/types/`:

| Archivo | Contenido |
|---|---|
| `inertia-props.ts` | Un `export interface` por struct de props - siempre se escribe |
| `routes.ts` | Un objeto `controllers` y un mapa de búsqueda nombrado `routes` derivados de `src/routes.rs` - solo se escribe con `--routes` |
| `lang-keys.ts` | Una unión de literales de cadena `MessageKey` con cada id de mensaje de Fluent en el catálogo del locale por defecto, incluidos los locales padre de fallback - solo se escribe cuando `lang/` produce algún id (consulta [Claves de mensaje](#claves-de-mensaje)) |

Los tres empiezan con un comentario de cabecera que los marca como
autogenerados. No los edites a mano - tus cambios se sobrescriben en la
siguiente ejecución.

## Ejecutarlo

```bash
# De una sola vez
suprnova generate-types

# Reemitir en cada cambio de archivo Rust
suprnova generate-types --watch

# Salida personalizada para el archivo de props
suprnova generate-types --output frontend/src/types/props.ts
```

La ruta del archivo de rutas queda fija en
`frontend/src/types/routes.ts` y la del archivo de claves de mensaje en
`frontend/src/types/lang-keys.ts`; solo la ruta del archivo de props es
configurable. El monitor vigila `src/` y regenera el archivo de props
cuando un archivo `.rs` se crea, se escribe o se borra; cuando el
proyecto tiene un directorio `lang/`, vigila también ese árbol y
regenera `lang-keys.ts` ante los mismos tipos de cambio en un archivo
`.ftl`. Las lecturas no cuentan - el generador lee todos los archivos
`.rs` bajo `src/` en cada ejecución, y tratar eso como un cambio haría
que el monitor regenerara para siempre. Una ráfaga de guardados se
agrupa en una única ejecución 500 ms después de la última escritura, así
que un `cargo fmt` o un cambio de rama regenera una sola vez, a partir
del árbol terminado, en lugar de una vez por archivo a partir de uno a
medio escribir.

Cada ejecución escribe un archivo solo cuando el contenido emitido
difiere de lo que ya hay ahí. Una regeneración que no cambió nada
informa `<path> is up to date` y deja el archivo, y su marca de tiempo,
intactos - que es lo que impide que `suprnova serve` reinicie tu backend
por un archivo que decidió no escribir.

## Props de página

La forma esperada: un struct de Rust por página de Inertia, que deriva
`InertiaProps`, emparejado con un componente de página que tipa sus
props a partir de la interfaz generada.

```rust
// src/controllers/home.rs
use suprnova::{InertiaProps, Request, Response, inertia_response};

#[derive(InertiaProps)]
pub struct HomeProps {
    pub title: String,
    pub message: String,
    pub count: i64,
    pub tags: Vec<String>,
    pub avatar_url: Option<String>,
}

pub async fn index(req: Request) -> Response {
    inertia_response!(&req, "Home", HomeProps {
        title: "Welcome".into(),
        message: "Hello".into(),
        count: 3,
        tags: vec!["new".into(), "featured".into()],
        avatar_url: None,
    })
}
```

`suprnova generate-types` emite:

```typescript
// frontend/src/types/inertia-props.ts
// This file is auto-generated by Suprnova. Do not edit manually.
// Run `suprnova generate-types` to regenerate.

export interface HomeProps {
  title: string;
  message: string;
  count: number;
  tags: Array<string>;
  avatar_url: string | null;
}
```

Consúmelo de la misma manera sin importar el framework de frontend - la
línea `import type` es idéntica en Svelte, React y Vue:

```svelte
<!-- frontend/src/pages/Home.svelte (el andamiaje predeterminado) -->
<script lang="ts">
  import type { HomeProps } from '../types/inertia-props'

  let { title, message, count, tags, avatar_url }: HomeProps = $props()
</script>

<h1>{title}</h1>
<p>{message} - {count} items</p>
{#if avatar_url}<img src={avatar_url} alt="" />{/if}
```

Consulta [Componentes de página](frontend-pages.md) para los
equivalentes en React y Vue.

## Mapeo de tipos

| Rust | TypeScript | Notas |
|---|---|---|
| `String`, `&str` | `string` | |
| `i8`..`i128`, `u8`..`u128`, `isize`, `usize`, `f32`, `f64` | `number` | Todos los primitivos numéricos colapsan a `number` |
| `bool` | `boolean` | |
| `Option<T>` | `T \| null` | |
| `Vec<T>` | `Array<T>` | El generador de props emite `Array<T>`; el generador de rutas emite `T[]` para los campos de solicitud de formulario |
| `HashMap<K, V>`, `BTreeMap<K, V>` | `Record<K, V>` | |
| `serde_json::Value` | `JsonValue` | Un alias recursivo que el generador declara una sola vez al principio del archivo, y solo cuando algo lo referencia. Un `Value` a secas también se mapea aquí, salvo que el proyecto defina su propio struct `Value` - ese gana |
| `Field<T>` (de `#[derive(Data)]`) | `field?: T \| null` | El campo es opcional en la red |
| `Prop<T>` (perezoso / diferido) | `field?: T` | Los props perezosos omiten la mitad `null` |
| Cualquier otra cosa | identificador simple | Consulta "Tipos personalizados" más abajo |

## Tipos personalizados

El visitor reconoce los primitivos de la tabla anterior. Todo lo demás
se emite con su nombre de tipo Rust tal cual. De ahí se derivan dos
consecuencias:

**Un struct anidado obtiene su propia interfaz solo si deriva
`InertiaProps` o `Data`.** Un struct `#[derive(Serialize)]` desnudo es
invisible para el generador - la interfaz emitida lo referenciará por
nombre, pero no se produce ninguna declaración:

```rust
use serde::Serialize;
use suprnova::{Data, InertiaProps};

#[derive(Serialize)]
pub struct Address {  // NO se recoge - sin derive de InertiaProps/Data
    pub street: String,
    pub city: String,
}

#[derive(Data)]      // O InertiaProps - cualquiera funciona
pub struct Company {
    pub name: String,
    pub address: Address,
}

#[derive(InertiaProps)]
pub struct ProfileProps {
    pub user_name: String,
    pub company: Company,
}
```

Salida generada:

```typescript
export interface Company {
  name: string;
  address: Address;          // huérfano - no se emite ninguna interfaz Address
}

export interface ProfileProps {
  user_name: string;
  company: Company;
}
```

Para arreglarlo: añade `#[derive(Data)]` (o `InertiaProps`) a
`Address`. El comportamiento de serialización en tiempo de ejecución no
se ve afectado por la elección de derive en el struct anidado -
`serde_json` seguirá emitiendo el struct correctamente - pero
TypeScript necesita la declaración explícita.

**Los argumentos genéricos de tipos personalizados no se recorren
recursivamente.** `chrono::DateTime<Utc>`, `uuid::Uuid`,
`rust_decimal::Decimal`, y cualquiera de tus propios tipos sin derive
se emiten como el identificador principal desnudo (`DateTime`, `Uuid`,
`Decimal`). Se serializan como cadenas JSON en la red, pero la
declaración de TypeScript no lo dirá. Dos formas de manejar esto:

```typescript
// frontend/src/types/runtime-types.ts - escrito a mano junto al archivo generado
export type DateTime = string;        // chrono::DateTime<_> se serializa como RFC 3339
export type Uuid = string;
export type Decimal = string;         // valor por defecto de serde_with; rust_decimal::Decimal
```

Luego, en `tsconfig.json`, asegúrate de que se recojan a través de tu
glob `include`, o usa `import type { DateTime } from './runtime-types'`
donde haga falta. El framework no te entrega estos alias porque la
elección correcta (`string` frente a `number` frente a un tipo branded)
depende de los feature flags de serde que hayas activado.

## Structs genéricos

Un struct de Rust genérico se convierte en una interfaz de TypeScript
genérica:

```rust
use suprnova::{Data, data::Field};

#[derive(Data)]
pub struct Paginated<T>
where
    T: serde::Serialize + for<'de> serde::Deserialize<'de>,
{
    pub items: Vec<T>,
    pub total: usize,
    pub cursor: Field<String>,
}
```

```typescript
export interface Paginated<T> {
  items: Array<T>;
  total: number;
  cursor?: string | null;
}
```

La cláusula `where` se descarta - los genéricos de TypeScript quedan
sin restricciones a menos que digas lo contrario del lado consumidor.

## Dividir interfaces de entrada/salida

Cuando un struct `#[derive(Data)]` mezcla campos `#[data(input_only)]`,
`#[data(output_only)]` o `#[data(lazy)]`, se emiten dos interfaces - la
forma de salida (lo que recibe el frontend) y una contraparte
`<Name>Input` (lo que devuelve):

```rust
use suprnova::Data;
use suprnova::data::Field;
use suprnova::inertia::Prop;
use validator::Validate;

#[derive(Data, Validate)]
pub struct UserDto {
    pub id: i64,
    pub name: String,

    #[data(input_only)]
    #[validate(length(min = 8))]
    pub password: String,

    #[data(output_only)]
    pub computed_handle: String,

    pub bio: Field<String>,

    #[data(lazy)]
    pub favorite_song: Prop<String>,
}
```

Emite ambas:

```typescript
export interface UserDto {              // servidor -> cliente
  id: number;
  name: string;
  computed_handle: string;
  bio?: string | null;
  favorite_song?: string;
}

export interface UserDtoInput {         // cliente -> servidor
  id: number;
  name: string;
  password: string;
  bio?: string | null;
}
```

Los campos `Prop` son de solo salida por naturaleza, así que se
eliminan del tipo de entrada incluso cuando `lazy` no es explícito.
Para el conjunto completo de flags `#[data(...)]` y su semántica de
autoría, consulta [Objetos de datos](data.md).

## Rutas con seguridad de tipos

Con `--routes`, el comando escribe un segundo archivo,
`frontend/src/types/routes.ts`, generado a partir de `src/routes.rs`.
Expone un objeto `controllers` cuyas formas de método reflejan el árbol
de módulos de tu backend, más una búsqueda `routes` indexada por
`.name(...)`:

```rust
// src/routes.rs
use suprnova::routes;

routes! {
    get!("/", controllers::home::index).name("home"),
    get!("/users", controllers::user::index).name("users.index"),
    get!("/users/{id}", controllers::user::show).name("users.show"),
    post!("/users", controllers::user::store).name("users.store"),
}
```

```typescript
// frontend/src/types/routes.ts
import type { Method } from '@inertiajs/core';

export interface RouteConfig<TData = void> {
  url: string;
  method: Method;
  data?: TData;
}

export interface UserShowParams {
  id: string;
}

export const controllers = {
  home: {
    index: (): RouteConfig => ({ url: '/', method: 'get' }),
  },
  user: {
    index: (): RouteConfig => ({ url: '/users', method: 'get' }),
    show: (params: UserShowParams): RouteConfig =>
      ({ url: `/users/${params.id}`, method: 'get' }),
    store: (): RouteConfig => ({ url: '/users', method: 'post' }),
  },
} as const;

export const routes = {
  'home': controllers.home.index,
  'users.index': controllers.user.index,
  'users.show': controllers.user.show,
  'users.store': controllers.user.store,
} as const;
```

`RouteConfig` está deliberadamente moldeado para satisfacer la interfaz
`UrlMethodPair` de Inertia 3, así que encaja en `router.visit`, en el
`submit` de `useForm` y en `<Link href={...}>` sin necesidad de un
adaptador:

```ts
import { router } from '@inertiajs/svelte'   // o /react, /vue
import { controllers, routes } from '../types/routes'

router.visit(controllers.home.index())
router.visit(controllers.user.show({ id: '42' }))
router.visit(routes['users.show']({ id: '42' }))
```

Si una ruta tiene params (`/users/{id}`), la función generada exige el
objeto `Params` tipado - TypeScript detecta claves faltantes o mal
escritas en tiempo de compilación.

## Claves de mensaje

Si la app tiene un árbol de catálogo `lang/`, el generador también
escribe `frontend/src/types/lang-keys.ts`: una unión de literales de
cadena `MessageKey` con cada id de mensaje de Fluent que el frontend
puede resolver. El wrapper `t()` de los starter kits tipa su argumento
de clave como `MessageKey`, así que una clave mal escrita o eliminada
es un error de TypeScript que señala al componente - la misma promesa
que `inertia-props.ts` hace para los props, extendida a las
traducciones.

Los ids vienen de `lang/<APP_LOCALE>/*.ftl`, unidos con los locales
padre de fallback configurados (`APP_LOCALE_PARENTS`) - así que un
catálogo tipo delta que solo contiene las cadenas que sobrescribe
genera igualmente el conjunto completo de claves que lleva el catálogo
servido y aplanado en cadena. `APP_FALLBACK_LOCALE` deliberadamente
*no* se incluye: el catálogo servido tampoco aplana el fallback
terminal, y la unión debe describir exactamente lo que el único
catálogo que el navegador obtiene puede resolver. Consulta
[Localización](localization.md) para la cadena en sí.

El archivo sigue las mismas reglas que los otros dos: ruta fija,
cabecera autogenerada, salida ordenada de forma determinista, nunca
editado a mano. Cuando ningún archivo `.ftl` produce ningún id, el
archivo se elimina en lugar de emitirse vacío - un kit que importa
`MessageKey` entonces falla al compilar hasta que el catálogo vuelva a
tener ids, lo cual es estrepitoso, como cualquier otro desajuste en
este pipeline.

## Cuándo se ejecuta

`suprnova serve` activa `generate-types` en el arranque. El flujo por
defecto:

```
suprnova serve
  ├─ examina src/ buscando structs InertiaProps / Data   → inertia-props.ts
  ├─ examina src/routes.rs buscando definiciones de ruta → routes.ts
  ├─ examina lang/ buscando ids de mensaje de Fluent     → lang-keys.ts
  ├─ inicia el backend
  └─ inicia Vite
```

Pasa `--skip-types` para omitir ambos. Vuelve a ejecutar `suprnova
generate-types` manualmente cada vez que cambies código Rust mientras
el backend está en hot-reload y quieras declaraciones frescas sin
reiniciar el servidor.

### Haz commit de la salida, y espera un diff limpio

`inertia-props.ts` está pensado para que le hagas commit - eso es lo
que permite que un revisor vea un cambio en el contrato de props en el
mismo diff que el código Rust que lo causó, y lo que evita que la CI
necesite una toolchain de Rust para verificar los tipos del frontend.

La generación es determinista: el mismo origen produce una salida
idéntica byte a byte, en cualquier máquina, en cualquier orden en que
los archivos terminen sentados en disco. Así que una ejecución que no
cambia nada no muestra ningún diff, y cualquier diff que veas es un
cambio real de contrato. (No siempre fue así - el ordenamiento se
sembraba a partir del orden de iteración de los hashes, y cada
ejecución reordenaba las interfaces.)

Dos consecuencias que vale la pena internalizar:

- **Ningún otro proceso puede editar ese archivo.** Si un componente
  importa un tipo que el generador no emite, el siguiente
  `generate-types` lo elimina y el frontend deja de compilar. La
  solución es declarar el tipo en Rust, no editar la salida a mano.
- **Una página sin ruta en Rust no tiene ningún tipo generado**,
  porque no hay ningún struct `#[derive(InertiaProps)]` detrás de
  ella. Declara sus props localmente en el componente hasta que exista
  un handler que las posea.

## Por qué Suprnova diverge

Laravel no incluye generación de tipos para Inertia porque PHP está
tipado dinámicamente - no hay nada en el lado del servidor de lo que
extraer un contrato. La comunidad de Laravel para Inertia llenó el
hueco con herramientas de espacio de usuario (Laravel Typed Inertia,
Wayfinder) que leen anotaciones PHPDoc o DocBlock.

Suprnova tiene la información de tipos en tiempo de compilación y en
disco, así que la extraemos directamente. El mismo
`#[derive(InertiaProps)]` o `#[derive(Data)]` que controla la
serialización JSON también dirige la salida de TypeScript - una única
fuente de verdad, nunca desincronizada de lo que serde realmente
emite.
