# TypeScript Types

`suprnova generate-types` durchsucht Ihre Rust-Quellen nach
`#[derive(InertiaProps)]`- und `#[derive(Data)]`-Strukturen und
schreibt TypeScript-Deklarationen, die das Frontend importieren kann.
Führen Sie es aus, nachdem Sie Props oder Routen geändert haben;
`suprnova serve` führt es beim Boot für Sie aus, sofern Sie nicht
`--skip-types` übergeben.

## Was generiert wird

Drei Dateien, geschrieben nach `frontend/src/types/`:

| Datei | Inhalt |
|---|---|
| `inertia-props.ts` | Ein `export interface` pro Prop-Struktur - immer geschrieben |
| `routes.ts` | Ein `controllers`-Objekt und eine `routes`-Namens-Lookup-Map, abgeleitet aus `src/routes.rs` - nur mit `--routes` geschrieben |
| `lang-keys.ts` | Eine `MessageKey`-String-Literal-Union jeder Fluent-Message-ID im Katalog des Standard-Locale, Fallback-Eltern eingeschlossen - nur geschrieben, wenn `lang/` irgendwelche IDs liefert (siehe [Message-Keys](#message-keys)) |

Alle drei beginnen mit einem Kopfkommentar, der sie als automatisch
generiert kennzeichnet. Bearbeiten Sie sie nicht von Hand - Ihre
Änderungen werden beim nächsten Lauf überschrieben.

## Es ausführen

```bash
# Einmalig
suprnova generate-types

# Bei jeder Rust-Dateiänderung neu ausgeben
suprnova generate-types --watch

# Eigene Ausgabe für die Props-Datei
suprnova generate-types --output frontend/src/types/props.ts
```

Der Pfad der Routen-Datei ist fix auf `frontend/src/types/routes.ts`
und der der Message-Key-Datei auf `frontend/src/types/lang-keys.ts`;
nur der Pfad der Props-Datei ist konfigurierbar. Der Watcher
beobachtet `src/` und regeneriert die Props-Datei, wenn eine
`.rs`-Datei angelegt, geschrieben oder gelöscht wird; hat das Projekt
ein `lang/`-Verzeichnis, beobachtet er auch diesen Baum und
regeneriert `lang-keys.ts` bei denselben Arten von Änderung an einer
`.ftl`-Datei. Lesezugriffe zählen nicht - der Generator liest bei
jedem Durchlauf jede `.rs`-Datei unter `src/`, und würde er das als
Änderung werten, regenerierte der Watcher endlos weiter. Eine Folge
von Speicherungen wird zu einem einzigen Durchlauf 500 ms nach dem
letzten Schreibvorgang zusammengefasst, sodass ein `cargo fmt` oder
ein Branch-Wechsel einmal regeneriert, und zwar aus dem fertigen Baum,
statt einmal pro Datei aus einem halb geschriebenen.

Jeder Durchlauf schreibt eine Datei nur dann, wenn sich der ausgegebene
Inhalt von dem unterscheidet, was schon da ist. Eine Regenerierung, die
nichts geändert hat, meldet `<path> is up to date` und lässt die Datei
samt Zeitstempel unangetastet - und genau das hält `suprnova serve`
davon ab, Ihr Backend wegen einer Datei neu zu starten, die es gar
nicht geschrieben hat.

## Seiten-Props

Die erwartete Form: eine Rust-Struktur pro Inertia-Seite, die
`InertiaProps` ableitet, gepaart mit einer Seiten-Komponente, die
ihre Props von der generierten Schnittstelle typisiert.

```rust
// src/controllers/home.rs
use suprnova::{InertiaProps, Request, Response, inertia_response};

#[derive(InertiaProps)]
pub struct HomeProps {
    pub title: String,
    pub message: String,
    pub count: i64,
    pub tags: Vec<String>,
    pub avatar_url: Option<String>,
}

pub async fn index(req: Request) -> Response {
    inertia_response!(&req, "Home", HomeProps {
        title: "Welcome".into(),
        message: "Hello".into(),
        count: 3,
        tags: vec!["new".into(), "featured".into()],
        avatar_url: None,
    })
}
```

`suprnova generate-types` gibt aus:

```typescript
// frontend/src/types/inertia-props.ts
// This file is auto-generated by Suprnova. Do not edit manually.
// Run `suprnova generate-types` to regenerate.

export interface HomeProps {
  title: string;
  message: string;
  count: number;
  tags: Array<string>;
  avatar_url: string | null;
}
```

Konsumieren Sie es auf dieselbe Weise, unabhängig vom
Frontend-Framework - die `import type`-Zeile ist über Svelte, React
und Vue identisch:

```svelte
<!-- frontend/src/pages/Home.svelte (der Standard-Scaffold) -->
<script lang="ts">
  import type { HomeProps } from '../types/inertia-props'

  let { title, message, count, tags, avatar_url }: HomeProps = $props()
</script>

<h1>{title}</h1>
<p>{message} - {count} items</p>
{#if avatar_url}<img src={avatar_url} alt="" />{/if}
```

Siehe [Seiten-Komponenten](frontend-pages.md) für die React- und
Vue-Entsprechungen.

## Typ-Zuordnung

| Rust | TypeScript | Hinweise |
|---|---|---|
| `String`, `&str` | `string` | |
| `i8`..`i128`, `u8`..`u128`, `isize`, `usize`, `f32`, `f64` | `number` | Alle numerischen Primitiven kollabieren zu `number` |
| `bool` | `boolean` | |
| `Option<T>` | `T \| null` | |
| `Vec<T>` | `Array<T>` | Der Props-Generator gibt `Array<T>` aus; der Routen-Generator gibt `T[]` für Form-Request-Felder aus |
| `HashMap<K, V>`, `BTreeMap<K, V>` | `Record<K, V>` | |
| `serde_json::Value` | `JsonValue` | Ein rekursiver Alias, den der Generator einmal am Anfang der Datei deklariert, und nur dann, wenn etwas ihn referenziert. Ein bloßes `Value` wird ebenfalls hierher abgebildet, außer das Projekt definiert eine eigene `Value`-Struktur - die gewinnt |
| `Field<T>` (von `#[derive(Data)]`) | `field?: T \| null` | Field ist auf der Wire-Ebene optional |
| `Prop<T>` (lazy / deferred) | `field?: T` | Lazy Props lassen die `null`-Hälfte weg |
| Alles andere | nackter Bezeichner | Siehe „Benutzerdefinierte Typen“ unten |

## Benutzerdefinierte Typen

Der Visitor erkennt die Primitiven aus der Tabelle oben. Alles andere
wird als nackter Rust-Typname ausgegeben. Zwei Konsequenzen ergeben
sich daraus:

**Eine verschachtelte Struktur bekommt nur dann ihre eigene
Schnittstelle, wenn sie `InertiaProps` oder `Data` ableitet.** Eine
bloße `#[derive(Serialize)]`-Struktur ist für den Generator
unsichtbar - die ausgegebene Schnittstelle referenziert sie
namentlich, aber es wird keine Deklaration erzeugt:

```rust
use serde::Serialize;
use suprnova::{Data, InertiaProps};

#[derive(Serialize)]
pub struct Address {  // wird NICHT erfasst - kein InertiaProps-/Data-Derive
    pub street: String,
    pub city: String,
}

#[derive(Data)]      // ODER InertiaProps - beides funktioniert
pub struct Company {
    pub name: String,
    pub address: Address,
}

#[derive(InertiaProps)]
pub struct ProfileProps {
    pub user_name: String,
    pub company: Company,
}
```

Generierte Ausgabe:

```typescript
export interface Company {
  name: string;
  address: Address;          // hängend - keine Address-Schnittstelle wird erzeugt
}

export interface ProfileProps {
  user_name: string;
  company: Company;
}
```

Zur Behebung: Fügen Sie `Address` `#[derive(Data)]` (oder
`InertiaProps`) hinzu. Das Serialisierungsverhalten zur Laufzeit wird
von der Derive-Wahl auf der verschachtelten Struktur nicht
beeinflusst - `serde_json` gibt die Struktur weiterhin korrekt aus -
aber TypeScript braucht die explizite Deklaration.

**Generische Argumente auf benutzerdefinierten Typen werden nicht
rekursiv verfolgt.** `chrono::DateTime<Utc>`, `uuid::Uuid`,
`rust_decimal::Decimal` und jeder Ihrer eigenen, nicht abgeleiteten
Typen werden als der nackte führende Bezeichner ausgegeben
(`DateTime`, `Uuid`, `Decimal`). Sie serialisieren auf der Wire-Ebene
zu JSON-Strings, aber die TypeScript-Deklaration sagt das nicht. Zwei
Wege, damit umzugehen:

```typescript
// frontend/src/types/runtime-types.ts - handgeschrieben neben der generierten Datei
export type DateTime = string;        // chrono::DateTime<_> serialisiert als RFC 3339
export type Uuid = string;
export type Decimal = string;         // serde_with-Standard; rust_decimal::Decimal
```

Stellen Sie dann in `tsconfig.json` sicher, dass sie über Ihr
`include`-Glob erfasst werden, oder schreiben Sie bei Bedarf `import
type { DateTime } from './runtime-types'`. Das Framework liefert
diese Aliase nicht für Sie mit, weil die richtige Wahl (`string` vs.
`number` vs. Branded Type) von den serde-Feature-Flags abhängt, die
Sie aktiviert haben.

## Generische Strukturen

Eine generische Rust-Struktur wird zu einer generischen
TypeScript-Schnittstelle:

```rust
use suprnova::{Data, data::Field};

#[derive(Data)]
pub struct Paginated<T>
where
    T: serde::Serialize + for<'de> serde::Deserialize<'de>,
{
    pub items: Vec<T>,
    pub total: usize,
    pub cursor: Field<String>,
}
```

```typescript
export interface Paginated<T> {
  items: Array<T>;
  total: number;
  cursor?: string | null;
}
```

Die `where`-Klausel wird verworfen - TypeScript-Generics sind
unbeschränkt, sofern Sie auf der konsumierenden Seite nichts anderes
festlegen.

## Aufgeteilte Input-/Output-Schnittstellen

Wenn eine `#[derive(Data)]`-Struktur `#[data(input_only)]`-,
`#[data(output_only)]`- oder `#[data(lazy)]`-Felder mischt, werden
zwei Schnittstellen ausgegeben - die Output-Form (was das Frontend
empfängt) und ein `<Name>Input`-Gegenstück (was es zurückschickt):

```rust
use suprnova::Data;
use suprnova::data::Field;
use suprnova::inertia::Prop;
use validator::Validate;

#[derive(Data, Validate)]
pub struct UserDto {
    pub id: i64,
    pub name: String,

    #[data(input_only)]
    #[validate(length(min = 8))]
    pub password: String,

    #[data(output_only)]
    pub computed_handle: String,

    pub bio: Field<String>,

    #[data(lazy)]
    pub favorite_song: Prop<String>,
}
```

Gibt beide aus:

```typescript
export interface UserDto {              // server -> client
  id: number;
  name: string;
  computed_handle: string;
  bio?: string | null;
  favorite_song?: string;
}

export interface UserDtoInput {         // client -> server
  id: number;
  name: string;
  password: string;
  bio?: string | null;
}
```

`Prop`-Felder sind ihrer Natur nach nur ausgehend, sodass sie aus dem
Input-Typ entfernt werden, selbst wenn `lazy` nicht explizit gesetzt
ist. Für die vollständige Menge der `#[data(...)]`-Flags und ihre
Autoren-Semantik siehe [Datenobjekte](data.md).

## Typsichere Routen

Mit `--routes` schreibt der Befehl eine zweite Datei,
`frontend/src/types/routes.ts`, generiert aus `src/routes.rs`. Sie
stellt ein `controllers`-Objekt bereit, dessen Methodenformen Ihren
Backend-Modulbaum spiegeln, plus ein `routes`-Lookup, das über
`.name(...)` indiziert ist:

```rust
// src/routes.rs
use suprnova::routes;

routes! {
    get!("/", controllers::home::index).name("home"),
    get!("/users", controllers::user::index).name("users.index"),
    get!("/users/{id}", controllers::user::show).name("users.show"),
    post!("/users", controllers::user::store).name("users.store"),
}
```

```typescript
// frontend/src/types/routes.ts
import type { Method } from '@inertiajs/core';

export interface RouteConfig<TData = void> {
  url: string;
  method: Method;
  data?: TData;
}

export interface UserShowParams {
  id: string;
}

export const controllers = {
  home: {
    index: (): RouteConfig => ({ url: '/', method: 'get' }),
  },
  user: {
    index: (): RouteConfig => ({ url: '/users', method: 'get' }),
    show: (params: UserShowParams): RouteConfig =>
      ({ url: `/users/${params.id}`, method: 'get' }),
    store: (): RouteConfig => ({ url: '/users', method: 'post' }),
  },
} as const;

export const routes = {
  'home': controllers.home.index,
  'users.index': controllers.user.index,
  'users.show': controllers.user.show,
  'users.store': controllers.user.store,
} as const;
```

`RouteConfig` ist absichtlich so geformt, dass es Inertia 3s
`UrlMethodPair`-Schnittstelle erfüllt, sodass es ohne Adapter in
`router.visit`, `useForm`s `submit` und `<Link href={...}>` passt:

```ts
import { router } from '@inertiajs/svelte'   // oder /react, /vue
import { controllers, routes } from '../types/routes'

router.visit(controllers.home.index())
router.visit(controllers.user.show({ id: '42' }))
router.visit(routes['users.show']({ id: '42' }))
```

Hat ein Pfad Parameter (`/users/{id}`), verlangt die generierte
Funktion das typisierte `Params`-Objekt - TypeScript fängt fehlende
oder falsch geschriebene Schlüssel zur Compile-Zeit ab.

## Message-Keys

Hat die App einen `lang/`-Katalogbaum, schreibt der Generator auch
`frontend/src/types/lang-keys.ts`: eine
`MessageKey`-String-Literal-Union jeder Fluent-Message-ID, die das
Frontend auflösen kann. Der `t()`-Wrapper der Starter-Kits typisiert
sein Key-Argument als `MessageKey`, sodass ein verschriebener oder
gelöschter Key ein TypeScript-Fehler ist, der auf die Komponente
zeigt - dasselbe Versprechen, das `inertia-props.ts` für Props macht,
erweitert auf Übersetzungen.

Die IDs kommen aus `lang/<APP_LOCALE>/*.ftl`, vereinigt über die
konfigurierten Fallback-Eltern des Locale (`APP_LOCALE_PARENTS`) -
sodass ein Delta-Katalog, der nur die Strings hält, die er
überschreibt, weiterhin das vollständige Key-Set generiert, das der
ausgelieferte, kettenweise geflachte Katalog trägt.
`APP_FALLBACK_LOCALE` ist bewusst *nicht* eingeschlossen: Der
ausgelieferte Katalog flacht den terminalen Fallback ebenfalls nicht,
und die Union muss genau das beschreiben, was der eine abgerufene
Katalog des Browsers auflösen kann. Siehe [Lokalisierung](localization.md)
für die Kette selbst.

Die Datei folgt denselben Regeln wie die anderen beiden: fixer Pfad,
automatisch generierter Header, deterministisch sortierte Ausgabe,
nie von Hand bearbeitet. Liefert keine `.ftl`-Datei irgendeine ID,
wird die Datei entfernt statt leer ausgegeben - ein Kit, das
`MessageKey` importiert, kompiliert dann nicht mehr, bis der Katalog
wieder IDs hat, was sichtbar ist, wie jede andere Drift in dieser
Pipeline.

## Wann es läuft

`suprnova serve` löst `generate-types` beim Boot aus. Der
Standardablauf:

```
suprnova serve
  ├─ src/ nach InertiaProps-/Data-Strukturen durchsuchen  → inertia-props.ts
  ├─ src/routes.rs nach Routendefinitionen durchsuchen    → routes.ts
  ├─ lang/ nach Fluent-Message-IDs durchsuchen            → lang-keys.ts
  ├─ das Backend starten
  └─ Vite starten
```

Übergeben Sie `--skip-types`, um beide zu überspringen. Führen Sie
`suprnova generate-types` jederzeit manuell erneut aus, wenn Sie
Rust-Code ändern, während das Backend Hot-Reload macht, und frische
Deklarationen wollen, ohne den Server neu zu starten.

### Committen Sie die Ausgabe, und erwarten Sie einen sauberen Diff

`inertia-props.ts` ist dafür gedacht, eingecheckt zu werden - das ist
es, was einen Reviewer eine Änderung des Prop-Vertrags im selben Diff
wie den Rust-Code sehen lässt, der sie verursacht hat, und was
verhindert, dass CI eine Rust-Toolchain braucht, um das Frontend
typzuprüfen.

Die Generierung ist deterministisch: dieselbe Quelle erzeugt
byteidentische Ausgabe, auf jeder Maschine, in jeder Reihenfolge, in
der die Dateien zufällig auf der Platte liegen. Ein Lauf, der nichts
ändert, zeigt also keinen Diff, und jeder Diff, den Sie sehen, ist
eine echte Vertragsänderung. (Das war nicht immer so - die Sortierung
speiste sich aus der Hash-Iterationsreihenfolge, und jeder Lauf
mischte die Schnittstellen neu durch.)

Zwei Konsequenzen, die es wert sind, sich einzuprägen:

- **Nichts anderes darf diese Datei bearbeiten.** Importiert eine
  Komponente einen Typ, den der Generator nicht ausgibt, löscht der
  nächste `generate-types`-Lauf ihn, und das Frontend kompiliert
  nicht mehr. Die Lösung ist, den Typ in Rust zu deklarieren, nicht
  die Ausgabe von Hand zu bearbeiten.
- **Eine Seite ohne Rust-Route hat keinen generierten Typ**, weil
  keine `#[derive(InertiaProps)]`-Struktur dahintersteckt.
  Deklarieren Sie ihre Props lokal in der Komponente, bis ein Handler
  existiert, der sie besitzt.

## Warum Suprnova abweicht

Laravel liefert keine Typgenerierung für Inertia, weil PHP dynamisch
typisiert ist - es gibt serverseitig nichts, aus dem sich ein Vertrag
extrahieren ließe. Inertias Laravel-Community hat die Lücke mit
Userland-Tools (Laravel Typed Inertia, Wayfinder) gefüllt, die
PHPDoc- oder DocBlock-Annotationen lesen.

Suprnova hat die Typinformation zur Compile-Zeit und auf der Platte,
daher extrahieren wir sie direkt. Dasselbe `#[derive(InertiaProps)]`
oder `#[derive(Data)]`, das die JSON-Serialisierung steuert, treibt
auch die TypeScript-Ausgabe an - eine einzige Quelle der Wahrheit,
nie außer Sync mit dem, was serde tatsächlich ausgibt.
